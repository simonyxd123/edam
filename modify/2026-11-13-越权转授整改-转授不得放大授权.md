## 1. 漏洞是什么

### 1.1 原来的判定

`canDistribute()` 只检查**一个**条件 —— 持有 `distribute` 位：

```java
// backend/.../service/DocPermissionService.java（修复前）
public boolean canDistribute(DocResource doc, Long userId) {
    if (doc == null || userId == null) return false;
    if (CurrentUser.isAdmin()) return true;
    if (userId.equals(doc.getUploaderId())) return true;
    return (effectiveActions(doc.getId(), userId) & ACTION_DISTRIBUTE) != 0;
}
```

而 `grant()` 对**要授出去的位掩码**只校验"是不是合法位"：

```java
if (actions == 0) { throw ... }
if ((actions & ~ACTION_ALL) != 0) { throw ... }   // 只查"有没有未知位"
// ❌ 没有任何一行检查：actions 是否是 grantedBy 自己持有的位的子集
```

视频侧 `VideoPermissionService.grant()` **完全同构**。

### 1.2 攻击路径

```
1. 上传者 A 上传一份 L3 文档，给同事 B 授权 view|distribute（17）
   —— 这是"允许 B 转发"的常规操作
2. B 调 POST /documents/batch-permission，body:
   {"doc_id": 42, "user_ids": [C], "actions": 63}
3. 后端：canDistribute(B) → B 有 distribute 位 → 放行；
        grant(42, [C], 63) → 63 & ~63 == 0 → 写库
4. C 现在拿到了这份 L3 文档的下载、编辑、删除、打印权
   —— 而 A 从头到尾只给过 B "看 + 转发"
```

**B 的权限被放大了 3.7 倍。**

### 1.3 为什么在防泄密系统里格外严重

| 位 | 后果 |
| --- | --- |
| **download** | 拿到原文。L3 文档原文出了系统就是一次实打实的泄密事件 |
| **delete** | 销毁证据。B 把 A 的文档授权给 C，C 再删掉 —— 审计链上留下的是"C 删的" |
| **distribute** | 传播链可以拉长：拿到 download 位的人如果同时有 distribute 位（`ACTION_ALL` 里有），就能把 download 继续转授出去 |

### 1.4 方案书早就写了这条

`DocPermissionService` 自己的注释里就写着：

> 「不能拿着别人的授权去扩大授权范围」

**但代码只挡住了"完全没有 distribute 位的人"**，
没挡住"distribute 位比要授出的位小"的人。

## 2. 修法

### 2.1 规则

**要授出的权限不得超过授权人自己持有的权限。** 两个维度都要卡：

| 维度 | 规则 | 越权示例 |
| --- | --- | --- |
| **位掩码** | `actions & ~own_bits == 0` | B 持有 17，却想授出 63 ⇒ 下载/编辑/删除/打印位全部越权 |
| **有效期** | `expire_at` 不得晚于授权人自己那份额权的到期时间 | B 自己那份 30 天后到期，却授出"永不过期" |

**有效期这一条是报告没提的**，但它是同一个漏洞的另一个面 ——
位掩码挡住了"授出自己没有的位"，有效期却还能让授权**活得比授权人自己更久**。
30 天后 B 失去了访问权，C 却永久保留 —— 同样是"拿着别人的授权去扩大授权范围"。

### 2.2 `own_bits` 怎么算

```
own_bits = 授权人的显式授权位 ∪ 密级兜底位
```

**为什么要算上密级兜底**：否则会出现"能转发却不能转授 view"这种自相矛盾 ——
一个持有 `distribute` 位的 L2 文档被授权人，转手授出去时连对方"看"都不行
（而对方本来就能看，因为 L2 谁都能看）。

| 密级 | 兜底位 | 依据 |
| --- | --- | --- |
| L1 / L2 | view | 方案书 6.3.1：任何登录用户可见 |
| L1 | download | 方案书 5.6.1【例外】"L1 公开资源允许下载" |
| L3 | 无（同部门可见不构成"可转授的位"） | |
| L4 | 无 | |

### 2.3 例外：管理员与上传者本人

不受限制。上传者对**自己上传的文档**天然全权（`canView` 的判定顺序就是这么写的），
管理员本来就是全权。限制他们反而会让"上传者忘了先给自己授权"这种死锁无解。

### 2.4 落在哪一层 —— 写入点，不是 Controller

规则实现在 `grant()` 里（权限写入的**唯一入口**），而不是 Controller：

- Controller 里**已经**查过 `canDistribute`，但那只是"有没有转发资格"
- 规则要落在**写入点**：将来多一个调用方（或有人注释掉 Controller 的检查）时，这道闸还在
- 服务层还**再查一次** `canDistribute`（纵深防御）——
  授权人自己必须持有 distribute 位

### 2.5 两侧共用一份规则

新增 `backend/src/main/java/com/example/edam/security/GrantScope.java`：

```java
public static void assertCanGrant(int ownBits, OffsetDateTime ownExpireAt,
                                  int requestedBits, OffsetDateTime requestedExpireAt,
                                  String[] bitNames, String resourceDesc)
```

文档侧与视频侧都调它 —— **不各写一遍**。
第四轮 §6.4 记过"可见性判定 4 份实现无共享代码"的结构性隐患，
这条新规则不能再复制两份。

## 3. 回归测试

### 3.1 服务层：`PrivilegeEscalationTest`（11 条）

| 用例 | 断言 |
| --- | --- |
| 持 view\|distribute 的人授出 ACTION_ALL | **403**，且错误信息点名"下载"位，**且没写库** |
| 持 distribute-only 的人授出 download | **403**，没写库 |
| 视频侧同构 | **403**，没写库 |
| 上传者授出全部权限 | **允许**（上传者天然全权） |
| 持 view\|distribute\|download 的人授出 view\|download | **允许**（不放大） |
| 持 view\|distribute 的人授出 view\|distribute | **允许**（转发不放大） |
| 完全没有 distribute 位的人调 grant | **403**（纵深防御） |
| L2 文档：密级兜底让 B 天然能看 | B **可以**把 view 授出去 |
| L3 文档：没有 view 位的人授出 view | **403**（密级不兜底） |
| 不能授出比自己那份更长期限的授权 | 授出"永不过期" ⇒ **403**；授出更晚 ⇒ **403**；不晚于自己 ⇒ 允许 |
| `GrantScope.excessBits` | 位运算正确 |

### 3.2 端点层：`PrivilegeEscalationEndpointTest`（2 条）

**接的是真实的 `DocPermissionService`**（只 mock repository），
走完整的「HTTP → Controller → Service 校验 → 写库」链路。

> **为什么不用 mock 的 service**：
> `DocPermissionControllerTest` 把 service mock 掉了，
> 所以它**测不到这个漏洞** —— mock 不会执行真正的校验逻辑。
> 这正是第三轮 §1 那个 bug 能活下来的原因之一。

断言：
- 越权转授 ⇒ **403** + 响应体带 `detail`（前端靠它告诉用户哪里越界）+ **没写库**
- 正常转发 ⇒ **200** + `granted_count=1`（不被误伤）

### 3.3 验证测试真的能抓住漏洞

摘掉 `grant()` 里的校验后（**用副本跑的，没动仓库里的文件**）：


## 4. 顺带修的

### 4.1 前端 403 提示看不出哪里越界

`web/src/api/client.ts` 的 403 分支原来统一弹：

```js
ElMessage.error('没有权限执行该操作');
```

后端返回的 `detail` 被丢掉了。而 403 的 detail 往往是**可操作的**信息 ——
"不能授出自己没有的权限：下载、打印（只能转授自己持有的权限）"，
用户一看就知道该勾哪些权限。

⇒ 改成 `ElMessage.error(data?.detail || '没有权限执行该操作')`。

### 4.2 ShareDialog 同一条消息弹两遍

拦截器弹一次，组件的 catch 又弹一次
（`ShareDialog.vue` 的 grant/revoke 两处）。
⇒ 两处都加上 `if (!e?.__handled)` 守卫 ——
`__handled` 是拦截器打的标记，`Documents.vue` / `Videos.vue` 已经在用这个约定。

### 4.3 顺带发现的**另一个漏洞形态**（已一并修）

有效期也能被放大（§2.1）。B 自己那份 30 天后到期，却能授出"永不过期" ——
30 天后 B 失去访问权，C 却永久保留。

本地跑 `mvn test` 有 6 条 `ApplicationStartupTest` 报错，根因是
`Communications link failure` —— **本机没有 MySQL**，
该测试是 `@SpringBootTest` + 真 MySQL（Flyway 迁移 + 上下文启动）。

**已证明与本次改动无关**：上一轮（第四轮 P0 整改）已用 `git worktree` 在

CI 里这个 job 有 `mysql:8.0` service ⇒ 会正常跑。

> ⚠️ 这也意味着：**本次改动没有在真 MySQL 上验证过**。
> 授权写入走的是 `doc_permission` / `video_permission` 两张表，
> 修复只涉及位掩码计算与异常抛出，不涉及表结构 ⇒ 真 MySQL 上跑一次
