## 一、目标

### 1.1 峰值档（W1 D4，peak-test.js）

**核心目标**：

1. **验证弹性**：HPA 在 500 QPS 压力下能否自动扩容
2. **验证告警**：CPU > 70% / 内存 > 80% / P99 > 500ms 等告警正确触发
3. **验证资源峰值**：500 QPS 下 CPU/内存/连接池的峰值水位
4. **放宽阈值对照**：P50<150ms / P95<300ms / P99<800ms / 失败率<2%

### 1.2 极限档（W1 D5，stress-test.js）

**核心目标**：

1. **找 QPS 拐点**：首个错误率 > 5% 的 QPS 阈值（即系统容量上限）
2. **找 P99 拐点**：首个 P99 > 1s 的端点
3. **找资源瓶颈**：首个打满的组件（CPU / 内存 / DB / Redis）
4. **验证降级**：核心业务是否不受影响 + 非核心业务是否合理降级

### 1.3 与负载测试的关键差异

| 维度 | 负载档 (W1 D2-D3) | 峰值档 (W1 D4) | 极限档 (W1 D5) |
| --- | --- | --- | --- |
| **QPS** | 200 | 500 | 1000 |
| **SLO** | 严格 | 放宽 | **不设阈值** |
| **核心验证** | SLO 达标 | 弹性 + 告警 | 找瓶颈 |
| **持续时间** | 10min | 10min | 5min |
| **场景覆盖** | 10 类全场景 | 10 类全场景 | **仅 5 类核心** |

## 七、未达标时的回退路径

### 7.1 峰值档未达标

| 症状 | 行动 |
| --- | --- |
| HPA 未扩容 | 调小 `averageUtilization` 阈值（70% → 60%） |
| 告警未触发 | 检查 rule 文件 + Prometheus 抓取 |
| P99 > 800ms | 加缓存 / 拆分慢接口 |
| 错误率 > 2% | 调大 DB 连接池 / Tomcat maxThreads |

### 7.2 极限档紧急回退

```bash
# 立即停止压测
pkill -f "k6 run.*stress-test"

# 紧急降低 QPS
curl -X POST http://api-gateway/admin/ratelimit/global \
  -H "Content-Type: application/json" \
  -d '{"enabled":true,"qps":300}'

# 回滚到上一个稳定版本（如需）
kubectl rollout undo deployment/edam-backend -n edam-staging
```

## 八、风险与回滚

### 8.1 风险

| 风险 | 严重度 | 缓解 |
| --- | --- | --- |
| **R-1**：HPA 扩容失败导致 OOM | 高 | 启用 HPA 限速 + PodDisruptionBudget |
| **R-2**：告警风暴淹没值班组 | 中 | Alertmanager `inhibit_rules` + 路由分组 |
| **R-3**：MySQL 连接耗尽影响其他服务 | 中 | 独立 staging DB + 连接池监控 |
| **R-4**：极限档压垮 staging | 中 | 提前通知 + 限流开关准备 |
| **R-5**：极限档发现严重 bug 但生产未发版 | 低 | 仅 staging，发现问题不立即回滚 |

### 8.2 回滚

如本指南需回滚（仅修改文档）：

```bash
git revert <commit-hash>
```

**回滚影响面**：仅 md 文档，无运行时影响。
