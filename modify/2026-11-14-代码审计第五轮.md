## 1. 【high】账号锁定永不解锁 —— 而且能被用来锁死别人的账号

### 1.1 现象

"连续 5 次密码错误 → 锁定 30 分钟"这条防护，此前**只有"锁"，没有"解"**：

- `LoginAttemptService.recordFailure` 达到阈值 → `user.setStatus(3)`（locked）
- `sys_user` 表里**没有任何"锁定到什么时候"的字段**
- 全仓库**没有任何定时任务或逻辑**把 `status` 从 3 改回 1

⇒ **一次误输 5 次密码 = 账号永久锁死**，只能由管理员逐个手工改库恢复。

而对外的说法一直是"锁定 30 分钟"：
`AccountLockedException` 甚至把 `LOCK_DURATION_MINUTES * 60`（1800 秒）
当作"剩余秒数"报给客户端 —— 那是个**假承诺**，等 30 分钟并不会自动解锁。

### 1.2 为什么这条比"体验问题"严重得多

它可以被**主动利用**：

| 步骤 | 攻击者做什么 | 结果 |
| --- | --- | --- |
| 1 | 知道工号（工号通常可枚举：`E0001` / `E0002` …） | —— |
| 2 | 对该工号连输 5 次错误密码 | 该账号 `status=3` |
| 3 | —— | 受害者**三条登录路径全进不去**：密码 / WebAuthn / SSO 都走 `assertLoginAllowed` |
| 4 | 重复第 2 步，换下一个工号 | **逐个锁死 ⇒ 全员锁死** |

不需要知道密码，也不需要拿到任何凭据 —— 这是一个纯 **DoS** 攻击面。

而合法用户自己也会中招：手滑连错 5 次 = 永久锁死。

### 1.3 修法

新增迁移 `V20261114_1000__account_lock_expiry.sql`（**只增不改**）：

```sql
ALTER TABLE sys_user
    ADD COLUMN locked_until DATETIME(3) NULL
        COMMENT '锁定到期时间（NULL = 管理员手动锁定，不自动解锁）' AFTER failed_login_count;
```

语义变成"**有时间窗的状态**"：

| 场景 | `locked_until` | 行为 |
| --- | --- | --- |
| 连续失败触发的自动锁定 | `now + 30 分钟` | 到期**自动解锁**并清零失败计数 |
| 管理员手动锁定（`UserController` 置 status=3） | `NULL` | **不自动解锁**，必须人工恢复 |

两个实现细节：

1. **自动解锁必须走独立事务**。
   `assertLoginAllowed` 与解锁写库在同一个 bean 里，自调用不走代理 ⇒
   `@Transactional(REQUIRES_NEW)` 失效 ⇒ 解锁会被外层登录事务的回滚一起带走
   （用户到期后第一次登录如果密码又输错 ⇒ 回滚 ⇒ 账号继续锁着 ⇒ **锁永远到期不了**）。
   ⇒ 用 `TransactionTemplate` + `PROPAGATION_REQUIRES_NEW` 显式开事务。

2. **管理员改状态时要配套维护 `locked_until`**：
   手动锁定 ⇒ 置空；改回 active ⇒ 清空并把失败计数归零
   （否则下次被自动锁定时会残留一个旧的到期时间）。

### 1.4 契约同步

`GlobalExceptionHandler` 此前写死 `"账号已被锁定 30 分钟"` —— 现在报**真实**状态：
自动锁定报真实剩余秒数（并带 `Retry-After` 头），管理员手动锁定报"需联系管理员"，
并新增 `permanent: true` 字段区分两者。

## 2. 【high】`/watermarks/extract` 无体积上限 ⇒ 普通员工可 OOM 打挂后端

### 2.1 现象

```java
// WatermarkController:77
byte[] content = file.getBytes();     // ← 整个文件进 JVM 堆
```

全局 multipart 上限是 **8GB**（视频需要），而这个端点：
- 权限是 `watermark:read` —— **在普通员工的白名单里**
  （`EmployeePermissions.READ_ONLY` 第 4 条）
- 把整个文件 `getBytes()` 读进堆

⇒ **任何一个普通员工**，上传一个 1GB 的文件，就能把后端 Pod 的堆打爆 ⇒
Pod 被 OOMKill ⇒ **全站不可用**（不只是这个接口）。

Worker 那边有 50MB 上限（`internal.py` 的 `MAX_EXTRACT_BYTES`），
但后端是**先读进堆、再转发**的 —— Worker 的限制根本来不及生效。

### 2.2 修法

1. **在 `getBytes()` 之前**判体积（50MB，与 Worker 对齐）⇒ 超了 413，
   根本不会进内存、不会占用 Worker。
2. **类型白名单**（`image` / `pdf`，与 Worker 的 `supported` 集合一致）⇒
   不支持的类型直接 400。
   顺带修掉一个语义错误：此前 Worker 的 400（"不支持的类型"）会被后端
   包装成 **503**（Worker 不可用）—— 客户端错误被报成服务端故障。

## 3. 【medium】溯源指纹可伪造 —— 能让无辜员工被指认"泄密"

### 3.1 现象

盲水印文本格式（Worker `document.py`）：`{uploader_id}|{doc_id}|{timestamp}`。

后端反查时**只按 `doc_id` 查文档**，然后把**该文档的上传者**报成泄密者：

```java
Long docId = Long.valueOf(parts[1].trim());   // ← 指纹里的文档 ID
DocResource doc = docResourceRepository.selectById(docId);
matched.add(... uploader.getEmployeeNo() ...);  // ← 直接指认这个人
```

而**指纹是文件内容的一部分**，任何人都能用开源的 blind-watermark 库
自己写进去。于是：

> 攻击者把一张图片用 `{受害者ID}|{受害者的文档ID}|…}` 嵌好水印，
> 交给运维说"这是外泄文件" ⇒ 系统输出
> **"受害者 外泄了《受害者的文档》"**。

在一个用于**追责**的系统里，这是能拿来冤枉人的。

### 3.2 已修的部分

加**一致性校验**：指纹里的 `uploader_id` 必须与库里该文档的上传者一致，
否则**不给匹配用户**（只记 warn 日志）。

这挡住了"随手伪造一个指针"和"uploader 与 doc 对不上"的伪造。

### 3.3 残留缺口（要彻底堵住，需要另做登记）

**知道目标 `doc_id` 与 `uploader_id` 的人仍能伪造出一致的指纹** ——
因为系统里**没有"这份文档当初嵌的是哪串文本"的登记**。

现成的 `watermark_cache` 表**至今没有任何写入方**（`WatermarkController.listCache`
的注释里就写着这件事）。彻底堵住的方案：

1. Worker 嵌入水印时，把**实际嵌入的文本**随 `PATCH /documents/{id}/status` 回写后端；
2. 后端落进 `watermark_cache`（resource_type=document, resource_id=doc_id, 指纹文本）；
3. 提取时拿提取到的文本去比对这份登记 ⇒ 对不上就是伪造。

这套改动跨 Worker → 后端 → 库三处，且会**改变已有数据的语义**，
不适合塞进一轮以"修 bug"为主的审计里 ⇒ 单独记在这里，作为下一轮的候选。

### 3.4 顺带修：指纹里的时间戳是硬编码常量

```python
# worker/src/edam_worker/processors/document.py（改前）
watermark_text = f"{uploader_id}|{doc_id}|2026-08-12T14:00:00Z"
```

**所有**文档的指纹第三段完全一样 ⇒ 指纹不携带任何时间信息：
既看不出文件何时入库，也无法用时间佐证样本来源。
⇒ 改为真实的嵌入时刻（UTC ISO-8601）。

## 4. 【medium】播放日志 `play_log` 零校验 —— 溯源链最后一环可以随手编

### 4.1 现象

`POST /playback/{video_id}/log` 此前只检查"session_id 非空"：

```java
if (request.getSessionId() == null || request.getSessionId().isEmpty()) { ... }
// 然后 session_id / event / progress_sec 全部照单全收
```

⇒ 任何登录用户都能往 `play_log` 里写任意内容：
编一个别人的 session、声称自己"看完了某个机密视频"、给自己造一堆"正在播放"的记录。

而 `play_log` 是**溯源链的最后一环**（方案书 §7.1，留 **365 天**，比操作日志还长）——
一张能被随手伪造的表，作为追责证据是站不住的。

> 讽刺的是：`doc/openapi.yaml` 里**早就写着**
> "服务端校验：JWT 中的 user_id_hash 与 session_id 必须匹配 active session" ——
> 这句话当时**只存在于文档里**，代码里一行都没有。

### 4.2 修法

上报必须带**播放 token**（`POST /playback/{id}/token` 签发的那张），服务端校验四件事：

1. token 有效且绑定到**本视频**；
2. token 的 subject 就是**当前用户**（不能用同事的 token 冒名上报）；
3. 请求体里的 `session_id` 与 token 里的 `session_id` **一致**
   （session 由服务端签发，不是客户端编的）；
4. 该用户**此刻**仍然看得到这个视频（拿 token 之后授权被撤销的，也要挡住）。

前端（`VideoDetail.vue`）同步带上 token；openapi 补上 `token` 查询参数。

## 5. 【medium】外发审批状态机是 check-then-act ⇒ 并发审批产生两条矛盾决策

### 5.1 现象

`decide()` / `revoke()` 都是"读状态 → 判状态 → `updateById` 写状态"：

```java
DistributionApproval approval = approvalRepository.selectById(approvalId);
if (approval.getStatus() != STATUS_PENDING) { throw 409; }   // ← 检查
...
approval.setStatus(newStatus);
approvalRepository.updateById(approval);                        // ← 行动（无条件按 id 写）
```

两个审批人同时点"批准"和"驳回"：
两边都读到 pending、都通过校验、都写一条决策流水 ⇒
**后写的覆盖先写的状态，而流水表里留下两条互相矛盾的决策**。

决策流水是"谁批的、批了什么"的**唯一证据链** —— 对不上账就等于没有证据。

### 5.2 修法

把"当前仍是 pending"写进 UPDATE 的 WHERE，由数据库保证只有一个并发者能改成功：

```java
int rows = approvalRepository.update(null,
    new LambdaUpdateWrapper<DistributionApproval>()
        .eq(DistributionApproval::getId, approvalId)
        .eq(DistributionApproval::getStatus, STATUS_PENDING)
        .set(DistributionApproval::getStatus, newStatus)
        .set(DistributionApproval::getFinalDecisionAt, decidedAt));
if (rows == 0) { throw 409 "该申请已被其他人处理"; }
```

`revoke()` 同理（`status IN (pending, approved)`）。

## 6. 【medium】nginx 访问日志把 `?token=` 原样记下来

### 6.1 现象

播放链路的凭据是走 query 传的：`playlist.m3u8?token=` / `segment?token=` / `key?token=`。

nginx 默认的 `combined` 日志格式记的是 `$request`（**含完整 URI + query string**）
⇒ **播放 token 原样进访问日志**。

那张 token 10 分钟内可以直接换到该视频的 **AES 解密密钥**。
项目约定「日志中不得打印 token 本身（连哈希都不打）」——
后端确实没打印，但**网关打印了**，凭据照样落到日志采集系统（ELK / Loki）里。

### 6.2 修法

helm 的 nginx 配置里自定义日志格式，用 `$uri`（不含 args）代替 `$request`：

```nginx
log_format edam_no_query '$remote_addr - $remote_user [$time_local] '
                         '"$request_method $uri $server_protocol" $status $body_bytes_sent '
                         '"$http_referer" "$http_user_agent"';
access_log /var/log/nginx/access.log edam_no_query;
```

访问分析需要的"哪个路径、什么方法、什么状态码"全在，
丢掉的只有 query string —— 那正是唯一不该落盘的部分。

## 7. 【low】`/preview/*` 两个预览端点安全响应头不一致

`/documents/{id}/preview` 设了 `nosniff` / `X-Frame-Options` / `Cache-Control: private`，
而**同一份 service** 的 `/preview/{id}` 与 `/preview/{id}/download` **一个都没设**。

⇒ 同一个功能、两个端点、安全头不一样（典型的行为漂移）。
本轮把三个端点统一。

> 注：这不是可利用的 XSS —— 文档的 MIME 是**按文件名后缀**推导的
> （`DocumentService.resolveMimeType`），SVG / 未知类型一律落
> `application/octet-stream`，且非白名单类型一律 `Content-Disposition: attachment`
> （浏览器下载而不渲染）。它是一处**加固缺口**，不是漏洞。
