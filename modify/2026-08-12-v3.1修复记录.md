## 二、P0 修复（5 项，影响生产部署）

### ✅ P0-1 OpenAPI 健康检查细化为 4 端点

**文件**：`doc/openapi.yaml`

**修改**：

| 端点 | 用途 | K8s 对应 |
| --- | --- | --- |
| `/health` | 总体健康检查（兼容旧版） | — |
| `/health/live` | 仅判断进程存活 | `livenessProbe` |
| `/health/ready` | 检查依赖就绪（含 MySQL/Redis/MinIO/Vault/RabbitMQ） | `readinessProbe` |
| `/health/components` | 各依赖组件详细状态（管理员用） | 自定义监控 |

**新增 Schema**：`ComponentsHealth`（含 MySQL 连接池、Redis 内存、MinIO 磁盘、Vault sealed 状态、RabbitMQ 队列深度）。

### ✅ P0-2 OpenAPI 增加 WebSocket 接口

**文件**：`doc/openapi.yaml`

**新增端点**：`/ws/notifications`

**协议要点**：
- WSS（WebSocket over TLS）
- 鉴权：JWT 作为 query 参数传入（浏览器 API 限制）
- 心跳：客户端 30s ping，服务端 pong
- 重连：客户端按指数退避，最大 5 分钟
- 推送事件类型：`approval.decided` / `key.revoked` / `driver.offline` / `compliance.alert` / `system.broadcast`

### ✅ P0-3 OpenAPI 版本策略文档化

**文件**：`doc/openapi.yaml`（`info.description`）

**策略摘要**：
- v1 至少维护 12 个月
- 破坏性变更发布 v2，旧版本并行运行 6 个月
- 弃用 API 在响应头增加 `Sunset: <date>` + `Deprecation: true`
- 客户端应在 6 个月内迁移
- 详细变更记录：`CHANGELOG.md`（按 SemVer 2.0）

### ✅ P0-4 OpenAPI 登录限流策略

**文件**：`doc/openapi.yaml`（`/auth/login` 接口描述）

**限流策略**：
- 单 IP 每分钟 5 次（429 拒绝）
- 单工号每分钟 3 次（429 拒绝）
- 单 IP 单日 100 次后要求图形验证码（响应头 `X-Captcha-Required: true`）
- 连续 5 次密码错误 → 账号锁定 30 分钟（423 状态码）

### ✅ P0-5 数据库迁移规范章节

**文件**：`doc/database_schema.md`（新增第 10 节）

**规范要点**：
- **工具选型**：首选 Flyway（Spring Boot 原生集成），备选 Liquibase
- **命名规范**：`V<YYYYMMDD>__<description>.sql`（如 `V20260812__add_driver_status_table.sql`）
- **禁用操作**：
  - DROP COLUMN → 标记 deprecated → 多版本兼容 → 后续版本移除
  - MODIFY COLUMN → 新建列 → 双写 → 数据迁移 → 切换 → 删旧列
  - 大表 ADD INDEX → 使用 gh-ost 或 pt-online-schema-change
  - 一次性 UPDATE 大表 → 分批更新（1 万行/批 + sleep 100ms）
- **灰度发布**：本地验证 → staging → 生产灰度（1 分片 → 1 小时观察 → 全量）
- **回滚脚本**：配套 `U<version>__<description>.sql`（Flyway `repair` 命令记录）

**新增 Schema**：`Backup`

### ✅ P1-6 `/playback/{video_id}/log` 上报鉴权加强

**修改**：`doc/openapi.yaml` `/playback/{video_id}/log` 描述

**鉴权要求**（v3.1 加强）：
- 必须携带 JWT（继承全局 security）
- 服务端校验：JWT 中的 user_id_hash 与 session_id 必须匹配 active session
- 频率限制：每用户每分钟 60 次（429 拒绝）
- 失败重试：客户端使用指数退避
- **安全警示**：此接口是溯源系统的审计通道，未授权或异常请求将触发告警

### ✅ P1-7 时区与精度统一规范

**文件**：`doc/database_schema.md`（新增第 11 节）

**规范分层**：
- **数据库层**：`DATETIME(3)` 毫秒精度、UTC、utf8mb4
- **应用层**：Spring Boot `jackson.time-zone: UTC`、Jackson `@JsonFormat(timezone="UTC")`
- **前端层**：dayjs / luxon，ISO-8601 + UTC 显示
- **API 层**：`2026-08-12T14:00:00.000Z`（后端不自动转换，前端按用户时区渲染）

### ✅ P1-8 sys_user 表应用层加密策略

**文件**：`doc/database_schema.md`（新增第 12 节）

**加密分层**：
- **应用层字段加密**：PII 字段（`real_name`、`email`、`phone`、`mfa_secret`）通过 Vault Transit 加解密
- **数据库层 TDE**：MySQL Enterprise / 文件级加密（防磁盘失窃）
- **备份加密**：AES-256-GCM，密钥存 Vault
- **传输加密**：TLS 1.2+

**密钥轮转**：
- KEK（主密钥）：每 90 天轮转
- DEK（数据密钥）：每 365 天轮转
- 旧密钥保留：轮转后保留 180 天（解密历史数据）
- 多版本解密：`pii-key:v1`、`pii-key:v2`，按版本路由

**PII 字段访问审计**：需记录到 `operation_log`，`operation_type = view_pii`。

### ✅ P1-9 distribution_approval 紧急撤销审计

**文件**：`doc/database_schema.md`（`distribution_approval` 表新增字段）

**新增字段**：

- `revoke_reason VARCHAR(512)`（撤销原因，合规审计必填）

### ✅ P2-3 Cursor-based 与 page-based 分页统一

**说明**：当前实现 `page-based`（`page` + `page_size`），`info.description` 已明确：
> "分页：page-based（管理后台），cursor-based（前端列表）"

**v3.1 处理**：暂保留 page-based；cursor-based 在 v3.2 引入（需前端配合重构）。

### ✅ P2-4 Error schema 增加 trace_id

**修改**：`Error` Schema 增加必填字段 `trace_id`：

```yaml
Error:
  type: object
  required: [type, title, status, trace_id]
  properties:
    trace_id:
      type: string
      description: |
        服务端追踪 ID（与日志关联）。
        用户报告问题时附带此 ID，可快速定位服务端日志。
```

### ✅ P2-5 索引使用率监控

**文件**：`doc/database_schema.md`（新增第 14 节）

**监控指标**：
- 索引使用率：`performance_schema.table_io_waits_summary_by_index_usage`（30 天未使用告警）
- 慢查询：`slow_query_log`（`long_query_time = 1s`，每小时 > 100 条告警）
- 索引基数：`INFORMATION_SCHEMA.STATISTICS`（cardinality < 行数 1% 提示失效）

**维护策略**：
- 每周日 03:00 自动 `ANALYZE TABLE`
- 碎片率 > 30% 时执行 `OPTIMIZE TABLE`（业务低峰）
- 每季度 SRE + DBA 联合审查

### ✅ P2-6 乐观锁字段

**文件**：`doc/database_schema.md`（`sys_user`、`distribution_approval` 等表增加 `version` 字段；新增第 13 节）

**规范**：
```sql
version INT UNSIGNED NOT NULL DEFAULT 0
```
```java
@Version
private Integer version;
```

**SQL 模式**：
```sql
UPDATE video_resource
SET ..., version = version + 1
WHERE id = ? AND version = ?
```

**应用层**：捕获 `OptimisticLockingFailureException` 后重试（最多 3 次），避免并发覆盖。

### ✅ P2-7 软删除策略规范
