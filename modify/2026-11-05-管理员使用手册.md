# EDAM 管理员使用手册（v3.4.2）

> 适用对象：admin 角色用户，或 dept_manager（部门管理员，权限子集）
> 文档版本：v3.4.2 / 2026-11-08
> 配套：普通员工使用手册（必读，避免误操作）

## 1. 管理员角色矩阵

| 角色 | 默认可见菜单 | 主要能力 |
|---|---|---|
| admin | 全部 8 个 | 全部功能 + RBAC + 备份恢复 |
| dept_manager | 7 个（无「角色权限」） | 本部门视频/文档上传、编辑、审批、删除、查审计 |
| auditor | 6 个（无上传、审批、用户管理） | 查所有审计日志 + 导审计报表 |
| **employee** | 5 个（无「角色权限」） | **只读**：看 + 播放 + 预览（**不能上传 / 删除**） |

> 角色权限矩阵详细：见 [`2026-11-05-employee-readonly-role.md`](2026-11-05-employee-readonly-role.md)
> 与 `doc/openapi.yaml` 里各端点的 `x-required-permission`（46 条权限码）。

## 2. 快速导航

管理员专属菜单（在侧边栏底部）：

外发审批
审计日志
角色权限  ← RBAC 管理
设置 → 系统配置 Tab（仅 admin）

普通员工 + 部门管理员 + 审计员使用「角色权限」菜单会被 v-permission 指令自动隐藏（前端菜单过滤 + 后端 @PreAuthorize 双层防护）。

> **v3.4 的角色变更**：
> - `employee`（普通员工）收敛为**只读** —— 不再能上传 / 删除；
> - `dept_manager` 补上了 `video:delete` / `document:delete`
>   （原先能上传却删不掉自己传的东西）。
>
> 权限是**数据**（`sys_role_permission` 表），不是代码 —— 在「角色权限」页勾两下
> 就能改一个角色能干什么，**代码里没有任何东西会"编译报错"提醒你**。
> 改完请跑一遍抽查 SQL 确认（见 §14）。

## 3. RBAC 用户与角色管理（admin 专属）

入口：左侧「角色权限」

### 3.1 4 个 Tab

#### Tab 1: 用户管理

| 字段 | 说明 |
|---|---|
| 用户名 | 登录名（唯一） |
| 工号 | 员工号（E\d+，唯一） |
| 姓名 | 真实姓名 |
| 邮箱 | 通知邮箱 |
| 状态 | active / disabled / locked |

按钮：
- 新增用户：弹窗填 username / password（≥6位）/ 工号 / 姓名 / 邮箱
- 编辑：改姓名 / 邮箱
- 重置密码：重置后必须 must_change_password=true（下次登录强制改密）
- 分配角色：弹窗多选（employee / dept_manager / auditor / admin，可多选）
- 删除（软删除 = status=2）：admin 自身不能删（按钮 disabled 防误操作）
- Excel 导入：批量导入用户 + 角色绑定（详见 §3.2）

#### Tab 2: 角色管理

| 字段 | 说明 |
|---|---|
| 角色代码 | admin / dept_manager / employee / auditor / 自定义 |
| 角色名 | 显示名 |
| 权限数 | 该角色拥有的权限码数量 |
| 权限代码 | 详细列表（tag 显示） |

按钮：
- 新建角色：定义 code + name + 选权限（弹窗里按 resource_type 分组的 el-checkbox-group）
- 编辑：调权限集（admin 自带 *:* 不可改；自定义角色可改）
- 删除：软删除（is_system=true 的不能删）

#### Tab 3: 权限目录（只读）

所有 **46 条**权限码列表，按 resource_type 分组展示。
每条权限码带一个 `action` 字段（read / upload / edit / delete / download / print /
share / approve / manage / audit_export）—— **这个字段是普通员工只读基线的判据**。

> ⚠️ **不是每一条权限码都对应一道门**（2026-11-08 查清）。
>
> 46 条里有 **25 条**真正挂在端点上（`@PreAuthorize`），
> 另外 **21 条**目前**没有任何端点读取** —— 典型的是
> `mfa:manage` / `system:manage` / `leak:manage` / `sso:manage` /
> `document:download` / `document:print` / `video:download` /
> `report:read` / `notification:manage` 等。
>
> 这意味着：**在「角色权限」页把某条码勾给一个角色，并不会让那个角色多出对应能力** ——
> 因为根本没有端点去检查它。勾选这些码目前是无害的（不产生权限），
> 但也**不是**授权手段。
>
> 为什么留着它们：权限目录是**面向未来**的清单，功能长出来时直接挂上去即可；
> 删掉反而要改迁移。要让某条码真正生效，得在对应端点上写 `@PreAuthorize`。
>
> 判断某条码是否真的生效，看 `doc/openapi.yaml` 里那个端点的
> `x-required-permission` 字段 —— 那里记的是**实际生效**的门。

#### Tab 4: 我的角色

当前登录用户拥有的角色。

### 3.2 Excel 批量导入用户

「用户管理」Tab → 「Excel 导入」按钮。

模板格式：username / employee_no / real_name / email / password / role_codes
示例：zhangsan / E000020 / 张三 / zhangsan@example.com / Init@123 / employee

校验规则：
- username 必填
- employee_no 必填且匹配 E\d+
- password ≥ 6 位（缺省 Init@123）
- role_codes 用逗号分隔多个 role code

不覆盖原用户：工号已存在则跳过并记入 errors 列表

## 4. 外发审批（dept_manager / admin 可见）

入口：左侧「外发审批」

### 4.1 业务场景

员工把受控文档发到外部：
1. 员工提交外发申请（针对**自己看得见**的文档）
2. 部门管理员审核
3. 同意 / 驳回 —— 决定写进**审批决策流水**
4. 外发渠道由业务方线下/其他系统执行

> ⚠️ **v3.4.2 起要知道的事：本版本只做「审批」，不做「外发链接」。**
>
> 早先版本的这份手册写着"同意 → 颁发外发链接（带过期 token）"，
> 并给出链接格式 `https://EDAM/external/token?doc_id=N`。
> **那个端点在代码里从来不存在** —— 没有 `/external/*` 路由，
> `external_doc_view_log` 表也没有任何写入方。
> 也就是说：审批通过之后，**不会**自动产生一个能给外部接收方用的下载链接。
>
> 现在真实的能力边界是：
> - ✅ 发起申请、审批（同意 / 驳回）、撤销、留痕、查决策流水
> - ❌ 不签发外发链接、不记录外部接收方的访问、不统计打开次数
>   （`max_open_count` / `current_open_count` 字段存在但恒为初值）
>
> 需要真正的外发通道时，走线下交付或另建系统 —— **不要**以为点完"同意"
> 链接就自动发出去了。

### 4.2 列表字段

| 字段 | 含义 |
|---|---|
| 申请 ID | 数字 |
| 文档名 | 哪个文档 |
| 申请人 | 工号 + 姓名 |
| 接收方 | 邮箱 / 组织 |
| 理由 | 业务说明 |
| 有效期 | 申请上填的时效（小时，默认 24）—— **目前只是审批单上的一个字段，不驱动任何自动行为** |
| 状态 | pending / approved / rejected / expired / revoked |
| 创建时间 | 申请时间 |

### 4.3 审批操作

- **同意**：弹窗确认 → 记录 `approved_at` + 审批人 + 审批意见
- **驳回**：**必须填理由**（后端强制，空理由返回 400）→ 记录 `rejected_at` + 理由
- **撤销**（紧急）：把 approved / pending 的单子置为 revoked，可填原因

三条硬约束（2026-11-08 起生效）：

| 约束 | 行为 |
|---|---|
| **状态机** | 只有 `pending` 能审批；已处理过的再提交返回 **409** |
| **不可自审自批** | 审批人不能是申请人本人，否则 **403** —— 否则有审批权的人能给自己开外发口子 |
| **驳回必填理由** | `decision=reject` 时 `comment` 为空 → **400** |

### 4.4 审批留痕

每次决策写两条记录：

- `distribution_approval` —— 单子的**当前状态**
- `distribution_approval_decision` —— **决策流水**（谁批的 / 什么时候 / 批语是什么）

查流水：`GET /api/v1/distribution/approvals/{id}/decisions`
（申请人本人和有审批权的人都能看。）

> v3.4.1 之前 `comment` 收了却从不保存，决策表也没有任何写入方 ——
> **谁批的、什么时候批的、批语是什么，全都查不到**。外发审批是
> "把资产送到公司外面"这道闸，闸门每次开合必须留痕。

每次操作还写 audit_log：operation_type=distribution:approve / distribution:reject / distribution:revoke

## 5. 审计日志

入口：左侧「审计日志」

> **需要 `audit:read` 权限**（admin / auditor / dept_manager 有；普通员工没有）。
> 2026-11-08 起后端补上了这道门 —— 此前审计日志接口对**任何登录用户**敞开，
> 绕过菜单直接调 API 就能拉到全公司的操作痕迹（谁在哪个 IP 预览了哪个 L4 文档）。
> 审计日志本身就是最敏感的数据，能看它必须是**显式授予**的能力。

### 5.1 列表字段

| 字段 | 说明 |
|---|---|
| 时间戳 | 操作发生时间（CST） |
| 操作者 | user_id |
| 工号 | JOIN sys_user 拼 |
| 操作类型 | login / logout / preview / create / update / delete / assign_role 等 |
| 资源类型 | auth / user / role / video / document / distribution |
| 资源 ID | 具体资源的 id |
| 结果 | success / failure / denied |
| IP | 真实客户端地址：对端在受信代理名单里才采信转发头（X-Forwarded-For 从右往左取、X-Real-IP 兜底），否则取 TCP 对端地址 |
| User-Agent | 浏览器 / 客户端 |
| 详情 | 人读字符串 |

### 5.2 过滤

支持按 操作者 / 操作类型 / 时间段查询。

### 5.3 导出

```
POST /api/v1/audit/logs/export
Content-Type: application/json

{
  "start_time": "2026-11-01 00:00:00",
  "end_time":   "2026-11-08 23:59:59",
  "mfa_code":   "123456",
  "filter": { "operation_type": "login", "resource_type": "video" }
}
```

返回 **CSV 文件**（UTF-8 BOM，Excel 双击直接能开，不用手动转码）。

- 过滤口径与审计日志列表**完全一致**（同一个查询构造）
- 单次上限 **50000 行**，超过会返回 400，让你缩小时间范围
- **MFA 二次校验**：你的账号开了 MFA 时必须带 `mfa_code` ——
  导出审计日志 ≈ 把全公司的行为画像一次性搬走

> ⚠️ **2026-11-08 之前这个接口是假的**：它返回的是一个指向
> `https://api.example.com/api/v1/audit/exports/...` 的伪造下载链接，
> 而那个路由根本不存在，点开永远是 404。
> 现在改成同步返回真的文件。
>
> 另外：**前端目前还没有「导出」按钮**（审计页面上找不到入口）——
> 上面这个接口要手工用 curl / Postman 调。补按钮是前端待办。

## 6. 备份与恢复（admin 专属）

入口：左侧「设置」→ 「系统配置」Tab → 「备份」

### 6.1 触发备份

- 选备份类型（full / incremental）
- 填 MFA 动态令牌
- 点「触发备份」→ 后端异步执行
- 返回 task_id

### 6.2 恢复

- 选备份 ID
- 填 MFA + 审批 token + confirm=true
- 点「恢复」→ 后端先停服务 → 恢复 DB → 恢复 MinIO → 重启

二次确认 是合规要求：MFA 证明是本人 + 审批 token 证明有上级授权。

## 7. 视频 / 文档高级管理（admin / dept_manager）

普通员工只「看 + 播放 + 预览」（**v3.4 起不能上传 / 删除**），admin 额外能：

### 7.1 视频

- 删除：硬删除
- 批量删除：多选 + 一次性删除
- 批量权限：跨用户 / 跨部门分配视频访问权（video_permission 表）
  - 列：用户 ID / 部门 ID / 角色 code / 操作（view / download / share）
  - 过期时间（expires_at）

### 7.2 文档

同视频，还有「预览日志」可查（谁看了什么、什么时候）。

### 7.3 密级：服务端会裁决，不是你说了算（v3.4.1 起）

上传时你填的密级是**申请值**，最终落库的是**服务端裁决后的值**：

> **最终密级 = max(服务端基线, 你填的值)**
> —— 你可以往严里选，不能往松里选。

服务端基线来自三处：文件名关键词、文件大小、**上传者所在部门**。

| 现象 | 说明 |
|---|---|
| 你填 L1，系统按 L3 存 | 文件名 / 部门命中了更严的规则；前端会弹提示告知实际密级 |
| 填了 L9 之类的非法值 | 直接 **400 拒绝**，不会像从前那样悄悄当成 L1 |
| 想把一份被自动判严的文件调松 | 走下面的**人工调整**，有审计留痕 |

> **L4 绝密只能由人显式声明** —— 自动识别最高只到 L3（机密）。
> 否则一个 6GB 的培训视频会被自动判成谁也看不见的资产。
> 确实需要 L4 时，在上传时直接填 L4。

**人工调整密级**（需要 `classification:manage` 权限，默认只有 admin 有）：

```
PATCH /api/v1/classification/videos/{video_id}
PATCH /api/v1/classification/documents/{doc_id}
Content-Type: application/json

{ "classification_lv": "L2", "reason": "该文件已脱敏，可降为内部" }
```

- `reason` **必填** —— 没有理由的降级等于审计形同虚设
- 每次调整都写 `data_classification_audit`（谁 / 何时 / 从什么改成什么 / 为什么）
- 这是**唯一**能把密级往低调的路径 —— 上传时的裁决只允许往严调

**注意**：自动识别是**启发式**，不是内容分析。文件名和大小都由客户端可控，
把它们当基线只是"便宜的启发式"；真正的内容级识别需要文档分析引擎，尚未实现。
部门是当前唯一不可伪造的基线信号。

## 8. 安全管理

### 8.1 重置用户密码

用户管理 → 选用户 → 「重置密码」按钮 → 弹窗输入新密码 → 保存。
- 系统自动 must_change_password=1（下次登录强制改）
- 写 audit reset_password

### 8.2 撤销密钥（紧急吊销）

用户管理 → 选用户 → 「紧急吊销」按钮

效果：
- 该用户**全部 refresh_token 立即作废** → 他**立刻**换不到新的 access_token
- `sys_session.revoked = 1`（DB 留痕）
- 写 audit revoke_keys

> **能吊销什么、不能吊销什么**（2026-11-08 写准）：
> 已经签发出去的那张 **access_token 不会立刻消失** —— 它是无状态 JWT，
> 服务端没有黑名单，只能活到自己的 TTL（默认 **10 分钟**）为止。
> 这是 JWT 无状态的固有代价，不是实现偷懒。
>
> 所以准确的说法是：**「续期通道立刻断掉，已有会话最多再活 10 分钟」**。
> 对离职场景够用 —— 10 分钟后他手里的任何凭证都换不出新 token。
>
> v3.4.1 之前这个按钮**背后是空的**：端点只打了一条日志就返回 204，
> token 一个都没作废，界面上却弹「成功」。现在是真的了。

适用场景：员工离职、密码泄露、离职交接期。

### 8.3 角色权限热更新

改了某用户的角色后，该用户需要重新登录才生效（token 里的 roles claim 是登录时快照）。
- 例外：admin 操作 assign_roles 后，建议在用户档案加 TODO 通知他重新登录

## 9. 系统配置

左侧「设置」→ 「系统配置」Tab（仅 admin）

### 9.1 当前可配项

| 配置 | 默认 | 含义 |
|---|---|---|
| 是否强制 MFA | true | L3+ 资源登录必填动态令牌 |
| 会话超时（秒） | 600 | token TTL |
| 文件大小上限（视频 MB） | 8192 | 超过上传被拒（8GB） |
| 文件大小上限（文档 MB） | 50 | 同上 |
| 密码最小长度 | 6 | 少于这个数注册被拒 |
| 登录失败锁定阈值 | 5 | 连续 5 次后锁定 30 分钟 |
| 是否记录 IP | true | audit 写 ip / ua 字段 |

> ⚠️ **本版本没有配置持久化端点**（2026-11-08 写准）。
> 上表是后端 `application.yml` 的**当前值**，不是页面上能改的东西 ——
> 「系统配置」Tab 里点「保存配置」会明确提示
> "系统配置暂未开放持久化，请通过后端配置文件调整"，**改完要重启后端**。
>
> 早先版本的这份手册写着"修改后点保存 → 重启后端生效"，
> 让人以为页面上就能改 —— 实际上页面上改不了。
> 需要调整：改后端配置文件 → 重启 / 重新部署。
>
> 另外这一页的可见性由 `system:read` 控制，但该权限码目前**没有端点读取**
> （见 §3.3 的说明），所以实际是靠前端的 `v-if` 过滤。

## 11. 数据库操作（最高权限，慎用）

直接连 MySQL 容器（docker exec -it edam-mysql mysql -uroot -p edam）：

| 表 | 用途 |
|---|---|

| sys_role | 4 个预置角色 |

## 12. 故障排查

### 12.1 用户登录后看不到菜单
→ 检查 sys_user_role 表 + sys_role.is_system + 角色是否被软删

### 12.2 用户上传后看不到自己上传的视频
→ 检查 video_resource.deleted_at IS NULL + classification_lv 是否在用户可看范围内

### 12.3 L4 视频上传失败
→ 检查文件大小（<8GB）+ 后端 L4 权限白名单

### 12.4 审计日志 IP 是 127.0.0.1
→ 反向代理（或 vite dev server）没把真实地址传下来
→ 检查链路末端有没有补转发头：nginx 的 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`；
  本地开发走 vite 代理，已默认开启 `xfwd: true`
→ 检查后端的受信代理名单 `edam.security.trusted-proxies`（环境变量 `TRUSTED_PROXIES`）：
  **对端不在名单里 ⇒ 转发头一律不采信**，直接记 TCP 对端地址
→ 开发环境：`TRUSTED_PROXIES=127.0.0.1/32,::1/128`（默认值）
→ K8s 生产：**留空即可** —— Pod 网段会被自动探测（`AUTO_TRUST_POD_NETWORK=true`），
  容器网卡上带着自己的地址和前缀长度，由它推出的就是 CNI 分配的 Pod CIDR
→ 注意：后端**不**使用 Spring 的 `server.forward-headers-strategy`（必须保持 none）——
  它会无条件采信 X-Forwarded-For 并改写 getRemoteAddr()，等于让客户端自己决定"我是不是受信代理"，
  白名单会形同虚设

### 12.4.1 审计日志里内网用户和外网用户记成了同一个 IP
→ 受信代理名单画得太宽了（典型：填了整个 `10.0.0.0/8`）
→ 名单里的每一项都会被当成"我们自己的一跳代理"跳过 ⇒ **内网用户的地址也被跳过**
  ⇒ 审计里内网用户全记成网关 IP，而外网用户是对的
→ 正确做法：名单只写**我们自己那几跳代理**的网段，不要写整个内网
→ K8s 里 Pod 网段会自动探测（不用填）；前面还有 CDN / 云 LB 时，
  把它们的网段补进 `TRUSTED_PROXIES`（例如 "13.32.0.0/15"）
→ 排查办法：把日志级别调到 DEBUG，看 `client_ip_resolved` 那行 ——
  它会打印对端地址、XFF 原文和最终采用的值

### 12.5 前端 401 跳不到 /login
→ 清 Vite 缓存 + Ctrl+Shift+R 硬刷
→ 检查 Console 是否有 [global] / [global-xhr] 日志（说明 wrapper 已加载）

### 12.6 RBAC 接口 403 Forbidden
→ 用户的 token 里没那个权限
→ 重新登录让 token claim 刷新（或者 admin 给该用户分配权限）

## 13. 紧急响应流程

### 13.1 密码泄露

1. 立即 PUT /users/{id}/revoke-keys 吊销该用户所有 token
2. PUT /users/{id} 修改密码
3. audit_log 查所有最近登录的 IP / UA
4. 通知 IT 升级 RBAC 规则

### 13.2 离职员工账号

1. DELETE /users/{id}（软删除 = status=2 禁用，保留审计）
2. 不要物理删除！审计 + 责任追溯依赖这条
3. 如要清 token：POST /users/{id}/revoke-keys

### 13.3 数据泄露事件

1. audit_log 查 operation_type='preview' + 时间段 → 找可疑用户
2. audit_log JOIN sys_user → 拿到可疑员工
3. 追溯具体文档 / 视频 → 走公司安全事件流程

### 14.1 改完权限后必做：抽查 SQL

权限是**数据**，改错了不会报错 —— 只能查出来。在生产库跑：

```sql
-- 普通员工的权限应当**全部是只读**（期望 10 行，action 全是 'read'）
SELECT r.code AS role_code, p.code AS perm_code, p.action
FROM sys_role_permission rp
JOIN sys_role r       ON r.id = rp.role_id
JOIN sys_permission p ON p.id = rp.permission_id
WHERE r.code = 'employee'
ORDER BY p.code;
```

只要结果里出现 `action` 不是 `read` 的行，就是配错了 ——
先在「角色权限」页把多余的勾去掉。

> **改了权限还要让用户重新登录**：JWT 里的权限码是**登录时**签发的，
> 改完数据库后旧 token 仍带旧权限，要等 token 过期或用户重新登录才生效。
