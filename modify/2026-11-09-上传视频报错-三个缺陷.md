> 日期：2026-11-09
> 触发：用户反馈「登录后上传视频报错」，提供后端日志
>   `C:\Users\yuxd\Desktop\fsdownload\log_202611090936.txt`
> 方案书章节：§7.1 核心数据表（operation_log）/ §14.3 STRIDE / Repudiation /
>   §5.4 细粒度权限与外发管控（视频上传入库链路）

## 0. 先说日志里到底有什么

日志只有 165 行，全部是**一次登录请求**的记录：

```
09:30:32.034 INFO  [] AuthService - 用户登录成功: employee_no=E000101, ... roles=[admin, employee]
09:30:32.035 DEBUG [] AuditAspect - audit_detail_eval_failed, expr=employee_no=#request.employeeNo
  SpelEvaluationException: EL1009E: Property or field 'employee_no' cannot be set on null
```

**上传请求本身在日志里一个字都没有。** 这不是"上传没到后端"的证据 ——
审计记录（operation_log）写的是**数据库表**不是日志文件，
而 `video_uploaded` / `video_upload_failed` 两条 INFO 也没出现，
说明这份日志是**按级别/关键字筛过的片段**，不是完整 stdout。

所以：**不能靠这份日志定位上传失败**，得从代码 + 运行时行为两头夹。
下面三个问题都是这样查出来的，其中第 1 个正是日志里那条报错本身。

## 1. 审计 detail 表达式 —— 全仓 40 多处全部求值失败（日志里的那条）

### 现象

`AuditAspect.buildDetail()` 把 `@AuditOp(detail = "...")` 整串丢给
`parser.parseExpression()` 求值。而 SpEL 把 `=` 解析成**赋值运算符**：

| detail 写法 | SpEL 的理解 | 结果 |
|---|---|---|
| `employee_no=#request.employeeNo` | 把 `#request.employeeNo` **赋给** `employee_no` | `EL1009E: cannot be set on null` |
| `title=#title, classification_lv=#classificationLv` | 赋值 + 逗号 | `EL1041E: After parsing a valid expression, there is still more data` |

用真实的 spring-expression 6.1.8 跑一遍（临时脚本，已删）可复现全部两种报错。

### 影响

**全仓 40 多处 `@AuditOp(detail=...)` 的补充说明一直是空的。**
而这恰恰是审计日志最该有的部分 —— 操作了哪个对象、什么密级、批量处理了几条。
`operation_log.detail` 里只剩参数摘要和失败原因。

（`resourceId` / `userId` 两个属性不受影响：它们本来就是**单个**表达式，
`#videoId`、`#result?.body?.get('user_id')`，SpEL 解析得动。）

### 修法

`detail` 的语义是「`k=v, k2=v2` 模板」，不是单个 SpEL 表达式。改成：
按 `,` 切段 → 每段按第一个 `=` 切成键和值 → **只有值**拿去求值（键是字面量）。
值求不出来（引用了不存在的变量）时**保留原文**而不是整段丢弃 ——
宁可记下 `employee_no=#request.employeeNo` 让人知道这里本该有值，也好过留白。

### 关联发现

`AuditOp` 的 javadoc 举的例子 `detail = "title=#video.title"` **本身就是错的**
（`title=#video.title` 同样是赋值）。已一并改正。

### 测试

`AuditAspectTest` 新增 2 条用例：
- `detailTemplateIsEvaluated` —— 断言 detail 求值成实际值（`level=L2`）
- `detailKeepsUnresolvableValue` —— 断言求不出的值保留原文

两条都验证过**回退修复后立刻变红**（`Failures: 2`），确认锁的是真 bug。

## 2. 前端上传 —— 实例级 30s 超时回灌，大文件必被掐断

### 根因

`api.upload()` 没有覆盖 `timeout`，而 axios 的 `mergeConfig` 里
`timeout` 走 `defaultToConfig2`：**请求没显式给就沿用实例的**。
于是 `axios.create({ timeout: 30000 })` 的 30 秒泄进了上传请求。

而 axios 的 XHR `timeout` 是**总时长**上限（从 `send()` 算起），
**不是**「空闲多久」—— 传字节的整个过程都算在里面。
所以任何传超过 30 秒的视频都会被浏览器单方面掐断，
哪怕每秒都在稳定收到数据。

代码里那套「连续 5 分钟无进展才中止」的 AbortController 逻辑
（`UPLOAD_IDLE_TIMEOUT_MS`）**根本没机会生效** —— 30s 的 XHR 超时先到了。

这是 `265abbd`（上传上限 2GB → 8GB）引入的回归：那次把
`timeout: uploadTimeoutFor(size)` 换成了 AbortController 方案，
却漏了 `timeout: 0`，实例级的 30s 就回来了。

用真实 axios 1.20.0 探测确认（临时脚本，已删）：

```
config.timeout : 30000   ← 实例级 30s 泄进来了
```

### 修法

`upload()` 里显式 `timeout: 0`（关掉 XHR 的总时长限制），
让 AbortController 的「5 分钟无进展」成为唯一的那道闸。

### 顺带澄清：multipart 边界**不是**问题

`headers: { 'Content-Type': 'multipart/form-data' }` 这个手设头看着可疑
（不带 boundary），但 axios 在浏览器里会**删掉**它（`resolveConfig` 里
`headers.setContentType(undefined)`），由浏览器自己补 boundary。
用真实 axios 的 fetch adapter 验证过：

```
最终 Content-Type : "multipart/form-data; boundary=----formdata-..."
```

所以手设 Content-Type 无害，**不要**去动它。（历史上 `f9de4d5` 删过一次，
后来 `b4ed471` 又 revert 了 —— 现在这个写法是对的。）

### 测试

`client.spec.ts` 新增 2 条用例：断言 `upload()` 传下去的 config 里
`timeout === 0`、且带 `signal.__idleTimeout` 标记。
同样验证过回退修复后变红。

## 3. nginx 网关 `/api/` 缺代理超时 —— 网关比后端先返回 504

### 根因

`helm/edam/values.yaml` 的 nginx 网关配置里，`location /api/` 只有一行
`proxy_pass`，**三个超时全走 nginx 默认值（60s）**：

| 超时 | 默认 | 管什么 | 8GB 上传时的后果 |
|---|---|---|---|
| `proxy_read_timeout` | 60s | 等**后端响应** | 后端收完文件还要算 SHA-256 + 传 MinIO + 落库 + 发 MQ，远超 60s ⇒ 网关先返回 504，**后端还在闷头干活** |
| `proxy_send_timeout` | 60s | 往**后端写请求体**的间隔 | 慢链路上传被掐断 |
| `client_body_timeout` | 60s | 收**客户端请求体**的间隔 | 同上 |

同文件里 `location /ws` 反而写了 `proxy_read_timeout 300s`，
说明是**漏了**而不是有意为之。

### 修法

三个超时都显式设成 `{{ .Values.nginx.config.apiProxyTimeout }}`（默认 `21600s`），
与 ingress 的 `proxy-*-timeout: 21600` 注解保持一致。

已核对 `gitops/overlays/{dev,staging,prod}/values.yaml`：
**没有任何 overlay 覆盖 `nginx.config`**，base 的新值直接生效
（符合"改 Helm values 前必查 overlay"这条规矩）。

## 4. 部署版本落后于代码库

日志里 `roles=[admin, employee]` 这行格式来自 `8c62e24`，
而 `TokenIssuanceService` 的 `token_issued` 日志（来自更晚的 `1dfc773`）
**没有出现** ⇒ **线上跑的不是当前 HEAD 的版本**。

这意味着：线上那个版本里，前端上传超时、审计 detail 全空、
网关缺超时，**三个问题都同时存在**。

⚠️ 部署前需要重新构建后端 + 前端 + worker 镜像，否则修好的代码不生效。
