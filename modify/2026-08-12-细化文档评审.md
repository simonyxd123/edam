## 三、OpenAPI 规范评审（30 个 API + 26 个 Schema）

### 3.1 优势

✅ **认证机制清晰**：`bearerAuth` 全局 + 公开端点 `security: []` 覆盖良好
✅ **错误响应统一**：`RFC 7807 Problem Details` 标准
✅ **核心模型完整**：JWT、Token、审批、水印提取等关键业务模型齐全
✅ **PII 处理得当**：`/auth/me` 接口单独说明"Token 中不携带 PII"
✅ **二阶段审核流**：`/approvals/{id}/decide` + `/approvals/{id}/revoke` 完整

### 3.2 🔴 P0 级（4 项）

#### P0-1 缺少 `/system/health` 详细健康检查

- **现状**：`/health` 简单返回 status，但**未包含各依赖组件状态**。
- **风险**：无法做细粒度监控；故障定位慢。
- **建议**：增加 `/health/ready`、`/health/live`、`/health/components`：
  ```yaml
  /health/ready:
    get:
      summary: 探针就绪（k8s readinessProbe）
  /health/live:
    get:
      summary: 探针存活（k8s livenessProbe）
  /health/components:
    get:
      summary: 各组件健康状态（DB/Redis/MinIO/Vault/RabbitMQ）
      responses:
        '200':
          schema:
            $ref: '#/components/schemas/HealthCheck'
  ```

#### P0-2 缺少 WebSocket / SSE 接口（实时通知）

- **现状**：所有 API 为 REST 风格，但**没有实时通知接口**。
- **风险**：外发审批结果、密钥吊销、驱动心跳异常等需要实时通知用户/管理员。
- **建议**：增加：
  ```yaml
  /ws/notifications:
    get:
      summary: WebSocket 长连接（实时通知）
      description: 审批结果 / 密钥告警 / 驱动异常实时推送
  ```

#### P0-3 缺少 API 版本管理策略

- **现状**：URL 前缀 `/api/v1/`，但文档中**未说明版本兼容与弃用策略**。
- **风险**：未来 v2.0 升级时无明确规范，可能导致客户端兼容性问题。
- **建议**：在 info.description 增加：
  ```yaml
  description: |
    API 版本策略：
    - v1 至少维护 12 个月
    - 破坏性变更发布 v2，旧版本并行运行 6 个月
    - 弃用 API 在响应头增加 Sunset: <date> + Deprecation: true
    - 客户端应在 6 个月内迁移
  ```

#### P0-4 `/auth/login` 缺少限流与暴力破解保护

- **现状**：`/auth/login` 仅有 429 响应引用，但**未说明限流策略**。
- **风险**：未限流的登录接口容易被暴力破解（即使有 failed_login_count 也是事后处理）。
- **建议**：
  ```yaml
  /auth/login:
    post:
      description: |
        限流策略：
        - 单 IP 每分钟 5 次
        - 单工号每分钟 3 次
        - 单 IP 单日 100 次后要求图形验证码
      x-rate-limit:
        - scope: ip
          limit: 5
          window: 1m
        - scope: employee_no
          limit: 3
          window: 1m
  ```

### 3.3 🟡 P1 级（6 项）

#### P1-1 缺少批量操作 API

- **现状**：单条资源的 CRUD 完整，但**无批量操作**。
- **场景**：
  - 批量删除视频/文档（管理员清退）
  - 批量分配权限（部门经理分配权限给全组）
  - 批量启动/终止异步任务
- **建议**：
  ```yaml
  /videos/batch-delete:
    post:
      summary: 批量删除
      requestBody:
        content:
          application/json:
            schema:
              type: object
              properties:
                video_ids:
                  type: array
                  items: { type: integer }
                  maxItems: 100
                reason: { type: string }
  /videos/batch-permission:
    post:
      summary: 批量授权
  ```

#### P1-2 缺少搜索 API（全文检索）

- **现状**：视频/文档列表仅有过滤参数，**无搜索能力**。
- **风险**：万级资源下用户无法找到目标。
- **建议**：基于 Elasticsearch 集成：
  ```yaml
  /search/videos:
    get:
      parameters:
        - q: { type: string, description: 全文检索关键字 }
        - highlight: { type: boolean, default: true }
  /search/documents:
    get:
      parameters:
        - q: { type: string }
  ```

#### P1-3 缺少标签管理 API

- **现状**：Video/Document schema 都有 tags 数组，但**无标签 CRUD 接口**。
- **建议**：
  ```yaml
  /tags:
    get: ...
    post: ...
  /tags/{tag_id}:
    delete: ...
  /videos/{video_id}/tags:
    post: {summary: 给视频添加标签}
    delete: {summary: 移除视频标签}
  ```

#### P1-4 缺少通知/消息 API

- **现状**：6.4 节消息队列定义事务通知与广播，但**无消费端 API**。
- **建议**：
  ```yaml
  /notifications:
    get:
      summary: 用户通知列表（已发送给我的）
  /notifications/{notif_id}/read:
    post:
      summary: 标记已读
  /notifications/unread-count:
    get:
      summary: 未读数量
  ```

#### P1-5 缺少备份与恢复 API

- **现状**：方案第九章 9.4 提到备份，但**无备份/恢复操作接口**。
- **建议**：
  ```yaml
  /admin/backups:
    get: ...
    post: {summary: 触发备份}
  /admin/backups/{backup_id}/restore:
    post: {summary: 从备份恢复（高危操作，需多因素认证）}
  ```

#### P1-6 `/playback/{video_id}/log` 上报缺少鉴权

- **现状**：路径未明确鉴权要求，可能被滥用（伪造日志攻击溯源系统）。
- **风险**：恶意员工伪造播放日志扰乱溯源；或 DoS 攻击日志系统。
- **建议**：必须校验：
  - JWT 中的 user_id_hash 与 session_id 匹配
  - 频率限制：每分钟 60 次
  - 服务端验证 session 实际存在

### 3.4 🟢 P2 级（4 项）

#### P2-1 缺少 API 响应示例

- **影响**：开发对接时缺少示例，影响效率。
- **建议**：每个 response 增加 `example`：
  ```yaml
  responses:
    '200':
      content:
        application/json:
          schema: ...
          example:
            access_token: eyJhbGciOiJIUzI1NiIs...
            token_type: Bearer
            expires_in: 600
  ```

#### P2-2 缺少 webhook 回调

- **场景**：外发文档打开时回调；驱动心跳丢失时回调。
- **建议**：增加 `/webhooks` 注册与 `/webhooks/{id}/deliveries` 查询。

#### P2-3 Cursor-based 分页与 page-based 分页混用

- **现状**：OpenAPI 同时提到两种，但只实现了 page-based。
- **建议**：要么都实现，要么只保留一种（推荐 cursor-based，更稳定）。

#### P2-4 错误响应缺少 trace_id

- **影响**：生产故障排查效率低。
- **建议**：Error schema 增加 `trace_id`：
  ```yaml
  Error:
    properties:
      trace_id: {type: string, description: 服务端追踪 ID}
  ```

## 四、ER 字段文档评审（18 张表）

### 4.1 优势

✅ **字段定义详尽**：每张表含类型/约束/默认值/说明
✅ **索引策略合理**：覆盖唯一键、查询键、外键
✅ **PII 标注清晰**：每个 PII 字段单独标注
✅ **数据生命周期明确**：每张审计表标注保留时长
✅ **性能基线量化**：每张表标注 P99 查询延迟

### 4.2 🔴 P0 级（1 项）

#### P0-5 缺少数据库迁移策略

- **现状**：字段定义完整，但**无迁移脚本规范**。
- **风险**：版本演进时无规范可循，容易引发线上故障。
- **建议**：增加迁移章节：
  - 工具选型：Flyway（推荐，Spring Boot 集成友好）
  - 命名规范：V<version>__<description>.sql（如 V20260812__add_driver_status_table.sql）
  - 禁用操作：删除列、修改列类型（必须分步骤：建新列→双写→迁移数据→切换→删旧列）
  - 灰度发布：大表 ALTER TABLE 必须使用 gh-ost 或 pt-online-schema-change

### 4.3 🟡 P1 级（3 项）

#### P1-7 缺少时区与时间精度统一规范

- **现状**：DATETIME(3) UTC 但**未说明应用层如何转换**。
- **风险**：跨时区用户访问时时间显示错误。
- **建议**：增加时区规范章节：
  - 数据库存储：UTC DATETIME(3)
  - 应用层：Spring Boot 时区设为 UTC，Jackson 序列化 ISO-8601 带 Z
  - 前端：使用 moment-timezone 或 dayjs 转为本地时区显示
  - API：所有时间字段统一 ISO-8601 + UTC（`2026-08-12T14:00:00Z`）

#### P1-8 sys_user 表缺少数据加密策略

- **现状**：PII 字段标注了"加密存储"，但**未说明加密粒度**。
- **建议**：
  - 应用层加密：`real_name`、`email`、`phone`、`mfa_secret` 在应用层用 Vault transit 加密后存储
  - 数据库层加密：TDE（MySQL Enterprise）或文件级加密
  - KMS key 轮转：每 90 天，应用层需支持多版本解密

#### P1-9 distribution_approval 缺少"紧急撤销"审计

- **现状**：有 `/revoke` 操作但无对应日志表字段。
- **建议**：增加 `revoked_by`、`revoke_reason` 字段。

### 4.4 🟢 P2 级（3 项）

#### P2-5 缺少索引使用率监控

- **建议**：定期运行 `SHOW INDEX_STATISTICS`，删除 30 天未使用的索引。

#### P2-6 缺少乐观锁字段

- **影响**：并发更新可能覆盖。
- **建议**：每张业务表增加 `version INT UNSIGNED NOT NULL DEFAULT 0`，配合 MyBatis-Plus @Version 注解。

#### P2-7 缺少软删除策略规范

- **现状**：video_resource / doc_resource 有 deleted_at，但 sys_user / sys_role 缺失。
- **建议**：统一软删除策略；FK 关联使用 `ON DELETE RESTRICT` + 应用层处理。

## 五、drawio 源文件评审（4 个）

### 5.1 优势

✅ **可在 diagrams.net 直接编辑**：标准 mxfile 格式
✅ **配色与 PNG 一致**：保留原色系
✅ **结构完整**：含参与者、消息、关系

### 5.2 🟡 P1 级（2 项）

#### P1-10 style 字符串属性重复

- **现状**：每个 cell 的 style 字符串含 `rounded=1;whiteSpace=wrap;html=1;rounded=1;...`（双倍前缀）。
- **影响**：文件 size 多 2 KB；不渲染失败但视觉略不一致。
- **示例**：
  ```xml
  style="rounded=1;whiteSpace=wrap;html=1;rounded=1;whiteSpace=wrap;html=1;fillColor=#f5f5f5;..."
  ```
- **建议**：修复生成脚本，去除重复前缀。

#### P1-11 缺少图例的样式定义

- **现状**：4 张图都有图例说明，但 drawio 中**图例只是文字**，未用形状表达。
- **建议**：将图例改为带颜色块的样式（图例形状 = 文字 + 小色块）。

### 5.3 🟢 P2 级（2 项）

#### P2-8 ER 图 drawio 关系连线无箭头方向

- **现状**：drawio 中 relationship 用 `endArrow=none`，但实际 DB 关系是 1:N 有方向性。
- **建议**：使用 `endArrow=ERmany` 表示 N 端，`startArrow=ERone` 表示 1 端。

#### P2-9 时序图生命线为曲线而非虚线

- **现状**：XML 中已设置 `dashed=1`，但 drawio 渲染可能仍显示为实线（取决于版本）。
- **建议**：手动编辑时确认 dashed=true；或在文件中加 `dashPattern=8 8`。
