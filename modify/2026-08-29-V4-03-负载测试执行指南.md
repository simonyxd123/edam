## 一、目标

### 1.1 主要目标

1. **验证 v3.3 SLO 达标**：在 200 QPS 稳态负载下，确认 **P50<100ms / P95<200ms / P99<500ms / 错误率<1%**
2. **建立端点级延迟基线**：8 大类场景的独立 P50/P95/P99，作为后续性能回归的对照
3. **识别 200 QPS 下的瓶颈**：DB 连接池 / Redis 命中率 / 慢查询 / JVM GC / 线程池
4. **输出单 Pod QPS 上限**：为容量规划提供数据

### 1.2 与烟囱测试的关键差异

| 维度 | 烟囱测试 (W1 D1) | 负载测试 (W1 D2-D3) |
| --- | --- | --- |
| **VU/QPS** | 10 VUs | 200 QPS |
| **持续时间** | 5 min | 10 min（爬升 1min + 稳态 8min + 降回 1min）|
| **SLO 阈值** | 放宽（P99<800ms）| **严格**（P99<500ms）|
| **监控要求** | 基础健康检查 | **全链路监控**（JVM + DB + Redis + MQ）|
| **期望产出** | 验证脚本链路 | **SLO 达标证明 + 容量基线** |

#### 3.3 200 QPS 特有的故障排查

| 症状 | 可能原因 | 排查步骤 |
| --- | --- | --- |
| **P99 飙升至 1s+ 但 P50/P95 正常** | 慢查询 / 锁等待 | `SHOW PROCESSLIST` / `EXPLAIN` 慢查询 |
| **错误率突增至 5%+** | DB 连接池耗尽 | `SHOW STATUS LIKE 'Threads_connected'` |
| **Redis 命中率 < 80%** | 缓存击穿 | 检查缓存预热 / TTL 配置 |
| **JVM GC 暂停 > 200ms** | 堆配置不足 / 内存泄漏 | `jstat -gcutil <pid>` |
| **HTTP 502/503** | 上游服务超时 | 检查 MySQL/Redis 健康状态 |
| **登录失败率 > 0%** | Bucket4j 限流命中 | 调大限流配置或分散 VU |

## 六、未达标时的回退路径

### 6.1 P99 > 500ms

| 严重度 | 行动 |
| --- | --- |
| P99 500-800ms | 优化 MySQL 索引 + Redis 缓存预热，重跑 |
| P99 800ms-2s | 分析慢查询 Top 10，加索引或重写 SQL |
| P99 > 2s | 拆分慢接口 / 加缓存层 / 限流降级 |

### 6.2 错误率 > 1%

| 严重度 | 行动 |
| --- | --- |
| 1-3% | 调大 DB 连接池 / Tomcat maxThreads |
| 3-10% | 检查限流配置 / 区分业务错误与限流错误 |
| > 10% | 立即停止，回滚到上一版本 |

### 6.3 资源耗尽

| 资源 | 行动 |
| --- | --- |
| CPU > 80% | 副本数从 N → 2N，重跑 |
| 内存 > 90% | JVM 堆从 2G → 4G，重跑 |
| DB 连接池 > 90% | 调大 `maxPoolSize`，重跑 |
