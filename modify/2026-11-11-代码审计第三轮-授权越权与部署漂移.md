## 1. 【critical】再分享可以"越权转授"—— 拿着 distribute 位就能发 download 位

### 1.1 问题

`DocPermissionService.canDistribute()` 只检查**一个**条件：

```java
// backend/.../service/DocPermissionService.java:228
public boolean canDistribute(DocResource doc, Long userId) {
    if (doc == null || userId == null) return false;
    if (CurrentUser.isAdmin()) return true;
    if (userId.equals(doc.getUploaderId())) return true;
    return (effectiveActions(doc.getId(), userId) & ACTION_DISTRIBUTE) != 0;
}
```

只要持有 **`distribute` 位（16）**，就能调
`POST /documents/batch-permission` 授权给别人。而 `grant()` 对
**要授出去的位掩码**只校验"是不是合法位"，**完全不校验授权人自己有没有这些位**：

```java
// backend/.../service/DocPermissionService.java:88-95
if (actions == 0) { throw ... }
if ((actions & ~ACTION_ALL) != 0) { throw ... }   // 只查"有没有未知位"
// 没有任何一行检查：actions 是否是 grantedBy 自己持有的位的子集
```

视频侧 `VideoPermissionService.grant()`（:100-106）**完全同构**，同样的问题。

### 1.2 触发场景

1. 上传者 A 上传一份 L3 文档，给同事 B 授权 `view|distribute`（actions = 1|16 = 17）
   —— 这是"允许 B 转发"的常规操作
2. B 调 `POST /documents/batch-permission`，body:
   ```json
   {"doc_id": 42, "user_ids": [C的id], "actions": 63}
   ```
   `63 = ACTION_ALL`（view|download|edit|delete|distribute|print）
3. 后端：`canDistribute(B)` → B 有 distribute 位 → **放行**；
   `grant(42, [C], 63, ...)` → `63 & ~ACTION_ALL == 0` → **写库**
4. C 现在拿到了这份 L3 文档的**下载、编辑、删除、打印**权
   —— 而 A 从头到尾只给过 B "看 + 转发"

**B 的权限被放大了 3.7 倍。** 这正是方案书 §5.4「越权分享自动阻断」要防的事：
"不能拿着别人的授权去扩大授权范围" —— 注释里写了这句话，
但代码只挡住了"完全没有 distribute 位的人"，**没挡住"distribute 位比要授出的位小"的人**。

### 1.3 为什么在防泄密系统里这条格外严重

- **download 位 = 拿到原文**。L3 文档原文出了系统就是一次实打实的泄密事件
- **edit 位 = 改元数据**。密级字段不在 edit 范围内（`grant` 只写 `doc_permission`），
  但标题、部门这些都算
- **delete 位 = 销毁证据**。B 可以把 A 的文档授权给 C，C 再删掉 —— 审计链上留下的是"C 删的"
- 传播链可以拉长：拿到 download 位的人如果同时有 distribute 位（`ACTION_ALL` 里有），
  就能把 download 继续转授出去

### 1.4 修复

在 `grant()` 里加一道**子集校验**：

```java
// 非 admin 且非上传者时，要授出的位必须是授权人自己持有的位的子集
if (!CurrentUser.isAdmin() && !userId.equals(doc.getUploaderId())) {
    int own = effectiveActions(docId, grantedBy);
    if ((actions & ~own) != 0) {
        throw new AccessDeniedException(
            "不能授出自己没有的权限位（自己持有=" + own + "，要授出=" + actions + "）");
    }
}
```

**先查 `own` 再判**：`own` 里必须含 `ACTION_VIEW`，否则连"看都看不到的人"也能被授权 —— 
所以还要补一条"要授出 view 位时，授权人自己必须能 view"。

视频侧同样修（`VideoPermissionService.grant()`）。

**回归测试**：加两条 —— 持 distribute-only 的人授 download ⇒ 403；
持 view|distribute 的人授 view|distribute ⇒ 200。

## 2. 【high】Docker 后端镜像的 HEALTHCHECK 探活端口是错的

```dockerfile
# docker/backend.Dockerfile:50
HEALTHCHECK ... CMD curl -fsS http://localhost:8080/api/v1/health/live || exit 1
# docker/backend.Dockerfile:65
EXPOSE 8080
```

而后端实际监听 **8092**（`application.yml:5`，全链路统一端口）。

**后果**：任何用 `docker build` + `docker run` 起后端的地方，
healthcheck **永远失败** ⇒ 容器被标 `unhealthy` ⇒
`depends_on: condition: service_healthy` 的编排会**永远等下去**。

**为什么没被发现**：K8s 部署用的是 `helm/edam/templates/deployment.yaml` 里的
livenessProbe/readinessProbe（走 `backend.service.port`，值是对的），
**Dockerfile 里的 HEALTHCHECK 在 K8s 下被忽略** —— 所以生产没事。
但 `dev/docker-compose.yml` 里根本没有 backend 服务（后端是本机 `mvn spring-boot:run` 起的），
所以开发环境也碰不到。**只有"直接 docker run 后端镜像"这条路会炸**，
而 CI 的 `docker-build` job 恰好就是干这个的 —— 只是 CI 只 build+push，不 run。

**修复**：改成 8092（并把 `EXPOSE` 一起改）。

> 顺带：`dev/db/_validate_ports.py` 的 9 处端口来源里**没有 Dockerfile**，
> 所以这个漂移不会被端口一致性校验挡住 —— 这也是它能活到现在的原因。

## 8. 【medium】ExternalSecret 与 Helm 模板争抢同一个 Secret，且漏了 `worker-token`

```yaml
# gitops/argocd/external-secrets.yaml:36-45, 60, 80
target:
  name: edam-secret
  creationPolicy: Owner
```

Helm 模板也渲染同名 Secret：

```yaml
# helm/edam/templates/secret.yaml:11-16
db-password: ...
vault-token: ...
jwt-secret: ...
worker-token: ...     # ← ESO 完全没有同步这个 key
admin-password: ...
```

两个问题：

1. **同名争抢**：ESO 用 `creationPolicy: Owner`，Helm 也管这个 Secret。
   ArgoCD 的 `prune: true` + ESO 的 Owner 策略会互相覆盖 ——
   谁后写谁赢，**db-password 在 Vault 真值与 Git 里的 `REPLACE_FROM_VAULT` 之间来回跳**。
   最坏情况：Helm 把 `REPLACE_FROM_VAULT` 写回去 ⇒ 后端用错密码连不上库。
2. **`worker-token` 没人管**：ESO 只同步 `db-password` / `db-username` /
   `jwt-secret` / `vault-token` 四个 key，**没有 `worker-token`**。
   而 `worker-token` 是 Worker → Backend 回调的共享密钥
   （后端 `edam.worker.token` 与 worker 的 `WORKER_TOKEN` 必须一致），
   `gitops/overlays/prod/values.yaml:85` 里它的值是字面量 `"REPLACE_FROM_VAULT"`。

   ⇒ **生产环境 Worker 与后端的回调密钥就是字符串 `REPLACE_FROM_VAULT`** ——
   一个公开在 Git 里的常量。任何拿到仓库的人都能伪造 Worker 回调
   （`PATCH /videos/{id}/status`），把任意视频标成 ready 或改写 `hls_path`。

**修复**：
- ESO 补 `worker-token`（和 `admin-password`）两个 key
- Secret 改名分开：ESO 管 `edam-secret`，Helm 模板不要再渲染同名 Secret
  （或给 Helm 模板加 `helm.sh/resource-policy: keep`）
- 生产 `worker-token` 必须是 Vault 里的真值
