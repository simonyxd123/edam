# 上传上限从 2GB 提升至 8GB

- **日期**：2026-10-20
- **需求**：有大视频素材，单文件上限从 2GB 提升到 8GB
- **前置**：`modify/2026-10-20-修复视频上传超时.md`（本次是那次的延续）
- **关联方案书**：视频上传入库 + 秒传去重（file_hash）+ 异步转码触发

---

## 一、为什么不止是改一个数字

2GB → 8GB 会连带触发四个原本不成立的约束，逐个说明：

### 1. 上传超时策略失效

上一轮定的「按文件大小动态估算，总时长上限 2 小时」在 8GB 下直接失效：

```
8 GiB ÷ 500 KB/s ≈ 4.7 小时 > 上限 2 小时
```

结果是传满 2 小时照样被掐断。另外固定总时长对大文件本身就是错的做法 —— 慢但在传会被误杀，真卡死又只能干等满总时长。

**改为「无进展超时」**：`AbortController` + 每次 `onUploadProgress` 重置计时器，连续 5 分钟收不到任何字节才 abort。慢链路可以一直传完，卡死的连接 5 分钟内报错。

配套要处理一个坑：主动 abort 在 axios 里表现为 `cancel`，而拦截器原本把 `cancel` 当「用户主动取消」**静默处理** —— 那会导致无进展超时后页面毫无反应。解决方式是在 `signal` 上打 `__idleTimeout` 标记，拦截器据此区分并提示用户。

### 2. 数据库事务被慢上传长期占用

`VideoService.upload` / `DocumentService.upload` 原本是 `@Transactional`，而 MinIO 上传包在事务里。8GB 可能传十几分钟，期间一直占着 Hikari 连接（池 20~50，`connection-timeout` 仅 30s）。并发几笔就能把池打满，把列表、鉴权这些普通接口一起拖死。

**改为三段式**，用 `TransactionTemplate` 显式划界：

```
hash（流式，无事务）
  → 秒传查询（短只读事务）
  → MinIO put（无事务、不占连接）← 唯一慢步骤，移出事务
  → 落库 + 发 MQ（短事务，毫秒级）
```

落库与发 MQ **仍在同一个短事务内**：`RabbitTemplate.convertAndSend` 默认异步投递不等待 confirm，在事务里执行几乎不耗时，保住「有记录必有 MQ 消息」的一致性 —— MQ 投递失败会连同 INSERT 一起回滚，不会留下永远不会被转码的视频。

已知残留风险：MinIO 上传成功但事务提交失败时会留下孤儿对象。这在改之前也一样（MinIO 本就不在数据库事务内），本次未扩大该风险。

### 3. 堆内存

`docker/backend.Dockerfile` 的堆是 `-Xmx2g`。原先 `digest.digest(file.getBytes())` 一次读整个文件进堆 —— 旧的 2GB 上限在 2GB 堆下本来就必然 OOM。

现在整条链路都不进堆：Spring multipart `file-size-threshold: 0` 一律落盘、SHA-256 用 8KB 缓冲流式、MinIO 从磁盘流式读取。因此 8GB 上传**不需要动堆配置**。

### 4. MinIO 从单次 PUT 切成分段上传

S3 协议单次 PUT 上限 5 GiB。8 GiB 超过该阈值，SDK 会自动从单次 PUT 切成分段上传（8 GiB ÷ 最小 5 MiB ≈ 1638 段，低于 10000 段上限）。

`partSize` 刻意保持 `-1`（自动）不改：显式 `partSize` 会触发 SDK 对「输入流必须可 reset」的校验，而 `MultipartFile` 的流来自 Tomcat 临时文件，reset 行为随容器版本而异，反而可能把现在能跑的路径弄坏。

## 二、改动清单

### 大小上限（2GB → 8GB）

| 文件 | 改动 |
|---|---|
| `web/src/views/Videos.vue` | 新增 `MAX_UPLOAD_BYTES = 8 * 1024^3` / `MAX_UPLOAD_LABEL = '8 GB'`，校验、报错文案、UI 提示统一引用 |
| `backend/.../application.yml` | `max-file-size` / `max-request-size` → `8GB` |
| `backend/.../GlobalExceptionHandler.java` | 413 文案 →「超过服务端上限（8GB）」 |
| `backend/.../VideoController.java`、`FileHashUtils.java` | 注释同步 |
| `dev/waf/nginx-modsecurity.conf` | `client_max_body_size 2g → 8g`；代理超时 3600s → 21600s |
| `helm/edam/values.yaml` | `clientMaxBodySize 2g → 8g`；ingress `proxy-body-size` → `8g`，超时 → `21600` |
| **`gitops/overlays/prod/values.yaml`** | **`proxy-body-size 500m → 8g`，`proxy-read-timeout 300 → 21600`，补 `proxy-send-timeout`** |

> **重要发现**：prod overlay 用 Helm 合并语义**覆盖** base values 的同名注解。
> 上一轮只改了 base `helm/edam/values.yaml`，而 prod overlay 一直钉死 `500m` / `300` ——
> **意味着上一轮的修复在生产环境根本没生效**，>100MB 的文件照旧被 ingress 挡掉。
> 本次已一并修正。dev / staging overlay 无 ingress 注解覆盖，不受影响。

### 超时策略

`web/src/api/client.ts`

- 删除 `UPLOAD_TIMEOUT_MAX_MS` / `uploadTimeoutFor()`（总时长方案作废）
- 新增 `UPLOAD_IDLE_TIMEOUT_MS = 5 * 60 * 1000`
- `upload()` 改用 `AbortController`，`onUploadProgress` 中 `resetIdleTimer()`，`finally` 里清理计时器防泄漏
- `signal.__idleTimeout = true` 标记
- 响应拦截器新增 `isUploadIdleAbort` 分支（优先于 `isCanceled`），提示「上传超过 5 分钟无进展，已中止」

### 事务边界

`VideoService.java`、`DocumentService.java`

- 去掉 `upload()` 上的 `@Transactional`
- 新增 `findExistingForDedup()`（只读事务）、`persistAndPublish()`（短事务）
- 注入 `PlatformTransactionManager txManager`

### 显式落盘

`application.yml` 新增 `file-size-threshold: 0`。Spring 默认值本来就是 0，这里写出来是为了**防止后人「优化」成内存缓冲** —— 8GB 文件一旦进 2GB 堆必 OOM。

## 四、待验证与风险

### 必须做的冒烟测试

1. **8GB 真实视频上传**。造文件：
   ```bash
   # 有 ffmpeg 的话，造一段真视频（HLS 转码也需要真视频）
   ffmpeg -f lavfi -i testsrc=size=1920x1080:rate=25 -t 3600 -c:v libx264 -b:v 8M /tmp/big.mp4
   ```
   或先拿 500MB 验证链路，再上 8GB。
2. 确认 MinIO **分段上传**真的工作（对象 >5 GiB 走 multipart，这是本次新路径）。
3. `MinIO` 侧确认对象大小与 SHA-256 一致（可用 `mc stat` / `mc cat --pipe | sha256sum`）。

### 部署前必须确认的容量

| 项 | 要求 | 现状 |
|---|---|---|
| 应用临时目录磁盘 | **≥ 8GB 可用**（multipart 落盘） | 默认 `java.io.tmpdir`，容器内通常 64GB 限制，**需实测** |
| MinIO 存储 | 视频总量 + 单对象 8GB | 需按总量评估 |
| JVM 堆 | 保持 2GB 即可 | ✅ 无需改（已全链路流式） |
| 数据库连接池 | 无需改（MinIO 已移出事务） | ✅ |

`application.yml` 里留了注释掉的 `location:` 配置，生产建议 `-Djava.io.tmpdir=/data/edam/tmp` 指向数据卷。

### 其他风险

- **单机并发 8GB 上传**会吃满磁盘 IO 与网卡带宽。多用户同时传大文件时体验会明显下降 —— 真正要扛这个量级得上分片/断点续传或客户端直传 MinIO 预签名 URL，那需要新增上传任务表与状态机，属独立需求。
- **HLS 转码耗时**：8GB 视频的转码远超 `VideoController` 里 `estimated_processing_sec: 60` 的估计，该字段只是给前端的提示值，未随上限调整。
