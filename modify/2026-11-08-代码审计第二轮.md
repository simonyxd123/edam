## 2. SSO：部门被每次登录重置成「总公司」

### 2.1 问题

`SsoUserProvisioning.updateExistingUser()` 里：

```java
if (userInfo.getDepartment() != null) {
    user.setDeptId(resolveDeptId(userInfo.getDepartment()));
}
```

而 `resolveDeptId()` 是这么写的：

```java
private Long resolveDeptId(String deptCode) {
    // 实际生产：sys_dept 表查询
    // 简化实现：返回固定 dept_id（外部用户）
    return 1L;
}
```

**它忽略了自己的入参，恒返回 1L**（`sys_dept.id=1` = 总公司）。

⇒ **每登一次 SSO，用户的部门就被重置成「总公司」。**

### 2.2 为什么这不只是显示难看

密级基线是按**部门名**判定的（`DataClassificationService.classifyByDept`）：

```java
if (containsAny(d, "hr", "人力", "人事", "法务", "legal", "审计", "audit")) return L3;
```

「总公司」一个都不命中 ⇒ 基线掉到 L1。
而最终密级 = **max(服务端基线, 客户端声明)** —— 客户端声明 L1 就是 L1。

也就是说：**一个法务部的员工，只要用 SSO 登一次，他之后上传的资产就可以声明成 L1 公开**，
直到他的部门被改回去。

同一条链上还有第二个后果：L3「同部门可见」按部门圈人，部门变了可见范围也变了。

### 2.3 修法

- `resolveDeptIdByName(name)` —— 按名字**精确查** `sys_dept`，查不到返回 `null`
- `updateExistingUser`：查得到就改，**查不到就保持原部门不动**并告警
  —— 宁可用旧部门信息，也不能让一次登录把权限基线改小
- `createNewUser`：优先用 IdP 给的部门，对不上才落到兜底部门
- `resolveDefaultDeptId()`：兜底部门优先按 `edam.sso.default-dept-code` 查名字，
  查不到才用 `sys_dept.id=1`
  —— 这个配置**此前根本没被用过**（`resolveDeptId` 忽略了自己的入参），现在它真的是兜底部门
- 新增 `SysDeptRepository.findByName`

## 3. SSO：IdP 没映射工号 ⇒ 500 而不是能看懂的错

`provision()` 直接拿 `userInfo.getEmployeeNo()` 去查库。IdP 的属性映射里
**没配工号**时它是 null：

- `findByEmployeeNo(null)` → 查不到 → 走"新建用户"分支
- 往 `sys_user.username` / `employee_no`（都是 NOT NULL）插 null → **500**

错误信息完全指不到根因，看起来像"数据库炸了"。

现在在 `provision()` 入口就拦下来：`"IdP 未返回工号（employee_no）—— 请检查 SSO 的属性映射配置"`。

## 4. SSO：OIDC 侧的两个 HTTP 问题

| 问题 | 后果 | 修法 |
|---|---|---|
| `HttpClient` **没设请求超时** | IdP 挂住时，SSO 回调线程被一直占着，state 还在 Redis 里等着（10 分钟 TTL） | 两个请求都加 10 秒超时 |
| `fetchUserInfo` **不看状态码**就拿 body 当 userinfo 用 | IdP 返 401/500 时 body 是错误 JSON ⇒ 所有属性解析成 null ⇒ 拿 null 工号去建账号（500） | 状态码不是 200 就抛异常；token 响应缺 `access_token` 也明确报错（原先是 NPE） |

## 5. 其它四处

### 5.1 WebAuthn：clientDataJSON 是子串匹配

```java
if (!clientDataJson.contains(expectedChallenge)) ...      // challenge
if (!clientDataJson.contains("webauthn.get")) ...          // type
if (!clientDataJson.contains(properties.getRpOrigin())) ... // origin
```

只要这三段文本**出现在 JSON 里**就算过。于是
`origin` 写成 `https://evil.com/?x=https://ours.example.com` 也能过。

现在用 Jackson 解出 JSON 逐字段**相等**比较。

> 注：这不是 WebAuthn 的完整校验 —— 真正的根基是 assertion 的签名验证
> （`verifyAssertionSignature` 仍然**未实现、fail-closed**）。
> 这处是修掉一个"等签名验证接上之后就会变成真漏洞"的陷阱。

### 5.2 RBAC：`POST /roles/{id}/permissions` 能改系统角色

`updateRole` / `deleteRole` 都挡了 `is_system=true`，
**只有 `assignPermissions` 没挡** ⇒
"编辑角色"页面点不动 `employee`，但分配权限的接口能把它的权限集整个换掉，
把普通员工的只读白名单改成有上传权。

现在三个入口口径一致。同时补了**权限 id 存在性校验**
（原先传错 id ⇒ 撞外键 ⇒ 500，现在 400 并指出是哪个 id）。

### 5.3 审计导出：整个是假接口

```java
String downloadUrl = String.format(
    "https://api.example.com/api/v1/audit/exports/%s/download?token=%s", ...);
return ResponseEntity.status(HttpStatus.ACCEPTED).body(response);
```

- 仓库里**没有** `/audit/exports/**` 路由 ⇒ 那个 URL 点开永远是 404
- 仓库里**没有**任何导出任务机制（无任务表、无调度器）⇒ "异步"是假的
- 但接口返回 202 + 一个**看起来很像样**的签名 URL
- 前端**根本没有**导出按钮；管理员手册却写着"生成 Excel 文件，MFA 二次校验"

现在改成**同步返回真的 CSV**（UTF-8 BOM，Excel 直接能开）：

- 过滤口径与 `GET /audit/logs` **完全一致**（抽出了共用的查询构造）
- 单次上限 **50000 行**，超过返回 400 并提示"缩小时间范围"
- **MFA 二次校验**：操作者开了 MFA 时必须带 `mfa_code`
  （导出审计日志 ≈ 把全公司的行为画像一次性搬走）
- 响应 `Cache-Control: no-store`
- **CSV 注入防护**：单元格以 `= + - @` 开头时会被 Excel 当公式执行，
  而审计的 detail 字段是**用户可控**的（文件名、理由…）⇒ 这类单元格加 `'` 打断公式
- 单元格里的引号按 CSV 规范转义、换行压平（否则一行日志会变成多行，打乱列对齐）

### 5.4 国密链路

| 问题 | 修法 |
|---|---|
| `parseToken` 里 `if (exp instanceof Number ...)` —— **exp 缺失时整段被跳过**，等于"没有过期时间的 token 也认"（fail-open） | exp 缺失 / 不是数字 ⇒ **直接拒** |
| 错误信息写着"edam.jwt.algorithm 与 edam.worker.token 需一致" —— `edam.worker.token` 是 Worker 回调密钥，跟 JWT 毫无关系（复制粘贴留下的） | 改成只提 `edam.jwt.algorithm` |
| `SM3Util` 上的 `@Deprecated("当前未被任何业务代码引用")` —— 已经过时：它经 `AlgorithmRouter` 被 `SmJwtTokenProvider` 实际调用 | 移除注解，注释改成"已接线" |

**其余部分核过、没问题**：claims 集合与 HS256 侧完全对齐
（`sub` / `user_id_hash` / `session_id` / `roles` / `permissions` / `scope` / `video_id` / `iat` / `exp`）；
算法派发按 token header 的 `alg` 走，**不存在算法混淆**
（伪造 GS256 header 会被路由到 SM3-HMAC 验签，HS256 签名过不了那一关）；
签名比较用 `MessageDigest.isEqual`（常量时间）。

> **已知残留**：`edam.jwt.algorithm=GS256` 只是让**新签发**的 token 用国密，
> 验签端**仍然接受 HS256**（按 header 派发）。
> 这是为了切换期间不踢在线用户下线，但要知道：
> **开了 GS256 不等于"不再接受 SHA-256 签的 token"**。

## 6. Webhook：SSRF 守卫的四个缺口

原先的 `assertPublicUrl` 只查 IPv4 字面量：

| 缺口 | 绕过写法 | 后果 |
|---|---|---|
| IPv6 只查了 `::1` | `http://[fc00::1]/`、`http://[fe80::1]/`、`http://[::ffff:169.254.169.254]/` | 扫内网 / 打云元数据 |
| **不解析主机名** | `http://metadata.internal/`（解析到 10.x） | 同上 |
| 十进制 / 十六进制 IP | `http://2130706433/`（= 127.0.0.1）、`http://0x7f000001/` | 回环 |
| 没显式禁止重定向 | 公网地址 302 → `169.254.169.254` | 云凭据泄露 |

现在：

- 抽出 `SsrfGuard` 统一实现：协议白名单 → 字面量判定（IPv4 + IPv6 + 数字写法）
  → **解析主机名，每个解析结果都再判一遍**
- **投递前再查一次**（注册时查过一次，中间隔了很久；DNS 可能已改）
  —— 检查失败**不投**（fail-closed），不能"检查失败就当没事"
- `HttpClient` 显式 `followRedirects(NEVER)`（写出来是为了明确意图）
- 响应体从 `BodyHandlers.ofString()` 改成**流式限量读**（最多 64KB）：
  原先那个 handler 会把**整个**响应读进内存，而"截断到 1KB"是读完之后才做的
  —— 一个返回 1GB body 的回调目标就能把后端 OOM 掉

**已知残留**：DNS 重绑定（检查在解析时刻，连接时刻可能解析出不同 IP）。
彻底解决要自己实现 DNS 解析 + 直连目标 IP，本仓库不做。

## 6.6 审计切面（AOP）：逐行核过，**没找到真缺陷**（编号随 §7 一起顺延）

审计切面是合规红线，所以这一块专门逐行看了一遍。结论是**没找到真缺陷**，
以下六点是核过的：

1. **审计记录不随业务事务回滚** —— 切面 `order = HIGHEST_PRECEDENCE` ⇒
   它在事务拦截器**外层**，`finally` 里写审计时业务事务已经结束；
   而且写入走 `@Async("auditExecutor")` ⇒ 独立线程、独立事务。
   这正是合规想要的：**被回滚的写操作也必须留痕**。
2. **不只看异常，也看状态码** —— 本项目相当一部分接口是
   `return ResponseEntity.status(FORBIDDEN)` 而不是抛异常；
   `classify()` 把 401/403 归成 `denied`、≥400 归成 `failure`，
   不会出现"用户看到 403、审计页显示成功"。
3. **`hideParams=true` 时完全不记参数**；敏感键按**名字**脱敏（与值长什么样无关），
   值截断 120 字符、最多 8 项；失败原因走 `AuditDetail.scrub()` 再脱敏一遍。
4. **审计写失败只记日志，不影响业务响应**（切面 + AuditService 两层兜底）。
5. **队列满不丢记录** —— `auditExecutor` 用 `CallerRunsPolicy`（宁可请求慢一点）
   + `waitForTasksToCompleteOnShutdown`（优雅停机不丢尾巴）。
6. **不重复记账** —— 兜底过滤器只补"没进控制器"的 401/403，
   靠请求属性去重。

## 7. Worker：FFmpeg / ffprobe / LibreOffice 三处子进程**没有超时**

### 问题

三处子进程调用都是裸等：

```python
proc = await asyncio.create_subprocess_exec(*cmd, ...)
stdout, stderr = await proc.communicate()      # ← 没有超时
```

一个 pathological 的输入就能让协程**永远不返回**：

- 损坏 / 特制的视频文件让 FFmpeg 卡死
- 畸形 docx 让 LibreOffice headless 挂住（它本来就爱挂）
- 半截网络流上的文件让 ffprobe 读不完

而 worker 的 `prefetch_count=10` ⇒ **10 个卡死的任务就把整个 worker 堵死**：
队列不再消费、CPU 被占满、**没有任何异常、没有任何日志**
（进程还"活着"，`/health/worker` 照样返回 `overall_ok` —— 运维看不出来）。

### 修法

- 新增 `edam_worker/procutil.py`：
  - `kill_process(proc)` —— `terminate()` → 给 5 秒优雅退出窗口 → 不行就 `kill()`
    （只 terminate 不够：挂在 I/O 上的进程收不到 SIGTERM，会继续吃 CPU）
  - `run_with_timeout(cmd, timeout)` —— 带超时的执行，超时抛 `TimeoutError`
    且**保证进程被杀掉**
- 三处调用全部改用它们：
  - ffprobe → `FFPROBE_TIMEOUT_SEC`（默认 120s）
  - FFmpeg HLS 转码 → `FFMPEG_TIMEOUT_SEC`（默认 3600s）
  - LibreOffice 转 PDF → `LIBREOFFICE_TIMEOUT_SEC`（默认 600s）
- 超时都**记日志并抛异常**（ffprobe 抛的是"取不到时长"，
  FFmpeg / LibreOffice 抛的是任务失败）—— 不静默吞掉。

### 顺带

- `FastAPI(version="3.4.1")` 写死 → 改成跟包版本走（`__version__`）。
  发版时漏改版本号这件事已经发生过一次。

### 核过、没问题的

- **MinIO 对象名没有路径穿越**：上传的对象名是
  `uploads/{uploaderId}/{UUID}.{fileType}` —— 用 UUID 而不是用户可控的文件名，
  `fileType` 来自白名单映射（`detectFileType`），拼不出 `../`
- **回调后端的状态码语义正确**：401/403 → `PermanentWorkerError`（不重试），
  5xx / 网络异常 → 退避重试；**回调失败会 raise**，不会静默成功
- **文档处理的路径上报与实际对象名一致**（`documents/{id}/watermarked{ext}`）
- **工作目录清理完整**：整个 `work_dir` 递归删（原先只删原文件，
  `.wm` / `.pdf` 中间产物全泄漏在磁盘上）
- **队列消费的 message 处理正确**：payload 非法 → ACK 掉并告警（不 requeue）；
  处理失败 → NACK；`CancelledError` 直接向上抛，不当成"任务失败"去重试
  （否则优雅关闭被反复拖延，MinIO 上留半成品目录）

## 8. 模型 ↔ 数据库列 的系统对账

写了个脚本把 **24 个 Java model 的每个字段** 与 **35 张迁移建出来的表**逐列对账
（处理 `ADD COLUMN` / `CHANGE COLUMN` / `DROP COLUMN`）：

- **0 处不匹配** —— model 里的每一列在迁移里都存在。
  （顺带确认了一个疑点：`sys_user_role.expires_at` 在 init 迁移里建的是 `expire_at`，
  但 `V20260830_0100__align_model_columns.sql` 用 `CHANGE COLUMN` 把它改名了 ——
  第一次对账没处理改名，误报了一次。）
- **7 列"库里有、model 里没有"** —— 逐个查了 Java 侧的引用，其中：

### 8.1 `webhook_delivery.retry_count` / `next_retry_at` —— 已接上

表里从建表起就有这两列，但 `WebhookDelivery` model **一直没映射**：

- `retry_count` 恒为 0 ⇒ 投递历史里"失败了 3 次然后成功"和"一次就成功"
  **长得一模一样**，运维看不出哪条是重试
- `next_retry_at` 恒为 NULL ⇒ **看不出"这条还在等重试"**

现在 model 补上这两个字段，`deliver()` 写 `retryCount = attempt`，
`scheduleRetry()` 把 `next_retry_at` 回写到那条投递记录上，
列表接口一并返回。

### 8.2 `sys_user.default_classification` —— **未接线，已写进文档**

列的注释是"用户上传默认密级（按部门）"，但 Java 侧**零引用** ——
管理员在库里把它改成 L3，该用户之后上传的文件**不会**默认成 L3。

实际上"按部门定密级"这条规则**已经实现了**，只是走的是
`ClassificationEnforcement` 现算的基线（文件名 / 大小 / **上传者所在部门**），
而不是这一列。所以这一列是**冗余且未接线**的。

已在 `doc/database_schema.md` 写明"改了也没用"，并给出两个方向
（接上成"用户级默认密级，优先于部门基线" / 承认是历史遗留）。
**没有直接删列** —— 迁移只增不改，删列要新迁移，而这一列无害
（`NOT NULL DEFAULT 'L1'`）。

### 8.3 `sys_user.pwd_history` —— 历史遗留，已写进文档

真正的密码历史在独立的 `password_history` 表（带 FK 与清理任务）。
`sys_user` 上这个 JSON 列是建表时多写的，**零引用**，已在 schema 文档标注可忽略。

### 8.4 `sys_role_permission.version` / `sys_user_role.version`

乐观锁列，model 里的 `@Version` 是**故意注释掉的**（MyBatis-Plus 3.5.7 的
`updateById` 乐观锁 bug）。**已知且有意为之**，不属缺陷。

## 9. 明确没做的事

| 项 | 为什么 |
|---|---|
| **`/internal` 端点的 chunked 上传绕过大小上限** | `Content-Length` 检查挡得住普通大文件，但 `Transfer-Encoding: chunked` 不带 Content-Length 时检查被跳过，而 body 会被整体读进内存。端点有 `WORKER_TOKEN` 保护、唯一调用方是后端（后端自己限了 50MB），风险低；彻底解决要改成流式读并边读边计数，会改端点签名 |
| **前端补「审计导出」按钮** | 后端接口已经真了，但前端审计页还没有导出入口。本轮只改了后端契约 + 手册，UI 是独立一件事 |
| **前端补 Webhook 投递历史的重试信息展示** | 后端已经返回 `retry_count` / `next_retry_at`，前端表格还没加这两列 |
| **国密：切到 GS256 后彻底禁用 HS256 验签** | 会把在线用户全部踢下线（access token 10 分钟一跳，refresh token 7 天）。要停用得先有"只接受新算法"的开关 + 灰度方案 |
| **SSRF：DNS 重绑定彻底解决** | 需要自己实现 DNS 解析 + 直连目标 IP，工程量大；当前用"投递前重查"把窗口压到最小 |
| **存储层按密级切 SM4** | 方案书要求，但属于独立一版（`AlgorithmRouter.selectSymmetric` 已有钩子，调用方还没接） |
