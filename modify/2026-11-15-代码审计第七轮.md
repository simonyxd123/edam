## 1. 【high】External Secrets 链路从未被 ArgoCD 下发过

### 现象

生产要用的密钥在 Vault 里，代码在 `gitops/argocd/external-secrets.yaml` 里定义了 ExternalSecret，
`gitops/README.md` 也画了完整的流程图 —— 但**这套东西从来没有到过集群**。

### 根因（三处各自都足以让它失效）

1. **没有任何 Application 引用它。**
   `gitops/argocd/applications/` 下只有 `edam-dev.yaml` / `edam-staging.yaml` / `edam-prod.yaml`，
   三个的 `source` 都是 `path: .` + `chart: helm/edam` —— 它们部署的是 **helm chart**，
   仓库里那份 `.yaml` 不在渲染范围内。`gitops/README.md` 的"安装 ArgoCD"步骤里
   也只 apply 了 project + 3 个 application，**没有它**。
2. **AppProject 白名单里没有 `external-secrets.io`。**
   `namespaceResourceWhitelist` 只列了 ConfigMap / Secret / Service / ServiceAccount /
   Deployment / StatefulSet / HPA / PDB / Ingress / ServiceMonitor / PrometheusRule ——
   就算把清单接进 Application，ArgoCD 也会以
   `resource not permitted in project` 拒绝同步。
3. **命名空间写死 `edam`。**
   清单里 `metadata.namespace: edam` 硬编码，而 dev / staging 部署在 `edam-dev` / `edam-staging`
   —— 即便它被应用了，也只服务 prod。

### 后果

ESO 从没写进过 Secret ⇒ **生产实际生效的就是 helm 渲染出来的占位符**：

| 密钥 | 占位符 | 泄漏后果 |
|---|---|---|
| `jwt-secret` | `REPLACE_FROM_VAULT` | JWT 是无状态自证的 ⇒ 任何能读到这个仓库的人可以自己签出 `{"sub":"1","permissions":["*:*"]}` 的**管理员 token**，整个鉴权被绕过 |
| `worker-token` | `REPLACE_FROM_VAULT` | 可伪造文档 / 视频状态回调（详见 §2） |
| `db-password` | `REPLACE_FROM_VAULT` | 数据库连不上（唯一"安全"的一个 —— 它只是起不来） |
| `vault-token` | `REPLACE_FROM_VAULT` | Vault 侧鉴权失效 |

而且 `REPLACE_FROM_VAULT` 这个字符串就写在 `gitops/overlays/prod/values.yaml` 里。

### 修法

**把 ExternalSecret 移进 helm chart**（`helm/edam/templates/external-secret.yaml`）：

- 命名空间跟着 release 走 —— 一套模板三环境通用，dev/staging/prod 各用自己的 namespace；
- AppProject 白名单补上 `external-secrets.io` 的 `ExternalSecret` / `SecretStore`；
- `gitops/argocd/external-secrets.yaml` **删除**（内容已进 chart）。
  留着它有两个害处：① 它是另一个"看起来在管密钥、实际没人部署"的陷阱；
  ② 它和 chart 里的 ExternalSecret **都指向 `edam-secret`** 且都是 `creationPolicy: Owner`
  —— 两个 owner 共享一个 target，删掉任意一个都会把整个 Secret 连带另外几个的密钥一起带走。

**顺带解决"两个控制器抢同一个 Secret"的经典问题**：
ESO 管理的 `edam-secret` 现在**完全不由 helm 渲染**（`externalSecrets.enabled=true` 时），
helm 只管 `edam-admin-secret`（admin 初始密码，生产为空 ⇒ 不建默认账号）。
每个 Secret 只有一个写者 ⇒ 没有字段归属之争，也不会有"ArgoCD 同步时把占位符回灌"的事。

### 部署前置条件（必须先满足，否则同步会失败）

1. 集群装了 **External Secrets Operator**（没装的话 ArgoCD 报 `no matches for kind ExternalSecret`
   —— **同步失败**，不会静默退回占位符，这正是我们要的行为）；
2. Vault 里补齐 5 个路径（`edam/database`、`edam/jwt`、`edam/vault`、`edam/worker`）
   —— `edam/worker` 是**新加**的，见 §2；
3. Vault 的 k8s 认证 role `edam-backend` 与 ServiceAccount `edam-backend` 对上。

## 2. 【high】Worker 共享密钥没有 ExternalSecret ⇒ 可伪造溯源结论

### 现象

`edam.worker.token` 是 Worker → Backend 的共享密钥（两边读同一个 Secret 键）。
原来的 ExternalSecret 清单只管了 db / jwt / vault 三样，**worker-token 根本没有对应的条目**；
staging overlay 连 `workerToken` 这一行都没写 ⇒ 直接继承 helm base 的 `change-me-in-production`。

而 `secret.workerToken` 这个值**两边都读到同一个公开字符串** ⇒ 校验自然通过 ⇒
"Worker 与 Backend 必须一致"这个约束反而把**公开值坐实成了生产实际使用的值**。

### 这个密钥能干什么

`PATCH /api/v1/documents/{id}/status`（`DocumentController.updateStatus`）只校验这一个头。
拿到它就能对**任意** doc_id：

1. 把 `watermark_status` 改成 `2`(ready)
   ⇒ 一份**根本没有水印**的文档被标记成"已加水印"放行，
   **溯源链断裂，而系统自己还认为它是完好的**；
2. 写入任意 `watermark_fingerprint` ⇒ 落进第六轮新加的 `watermark_cache` 指纹登记表
   ⇒ 事后提取比对时"对不上" ⇒ **真的泄密被判定为"伪造"而洗白**；
   或者反过来，**栽赃**给一个无辜员工。

### 修法

1. ExternalSecret 增加 `worker-token` 条目（Vault 路径 `edam/worker`）；
   staging / prod overlay 补上 `workerToken` 那一行；
2. **新增 `WorkerTokenGuard`**（`backend/.../security/WorkerTokenGuard.java`）：
   非开发 profile 下密钥命中仓库里公开的占位符 ⇒ **拒绝启动**；
   短于 16 字节（128 bit）⇒ 拒绝启动；
   空值 ⇒ 只告警（回调本来就会被 `WorkerTokenVerifier` 一律拒绝，fail-closed）；
3. Worker 侧同样加守卫（见 §5）；
4. 占位符清单抽成公共类 `KnownSecretPlaceholders`（后端）与 `config.KNOWN_SECRET_PLACEHOLDERS`（Worker），
   **两边必须同步** —— 复制两份清单，迟早只改一处。

> 为什么"拒绝启动"而不是"打个警告"：这个密钥的权限太大（能改写溯源结论），
> 而占位符在 Git 里公开。**宁可起不来，也不要"能跑但溯源结论可被随便改写"。**
> 这与项目既有的 fail-closed 惯例一致（admin 密码留空 ⇒ 不建默认账号）。

## 3. 【medium】staging 其实是自动同步的

`gitops/argocd/applications/edam-staging.yaml`：

```yaml
automated: {}  # 禁用自动同步，需手动
```

**`automated: {}` 不是"禁用自动同步"。** ArgoCD 里 `automated` 是个结构体，
写成 `{}` 就是"**开启**自动同步 + 默认参数"（`prune` 默认 `true`、`selfHeal` 默认 `false`）。
真正禁用要写 `automated: null` —— prod 就是这么写的。

于是 staging 每一次 `main` 分支推送都会自动同步**并自动 prune**。
`gitops/README.md` 里那张表也写着 staging 是"手工" —— **注释、README、YAML 三处，
两处都以为它是手工的**。

叠加 §1：同步会把 Secret 重新 apply 成仓库里的公开占位符。

**已修**：`automated: null`，并在注释里写清楚"`{}` 是开启不是关闭"。

## 4. 【medium】JWT 密钥守卫把 staging 当成"非生产"

第六轮加的 `JwtSecretGuard` 判定"是否生产"的方式是
`profile 名里含 "prod"` —— 于是 `staging` 落进"非生产"分支，
命中占位符时**只打一条 WARN 就放行**。

而 staging 不是开发环境：它连着真实依赖（RabbitMQ / MySQL / MinIO / Vault），
`targetRevision: main`，随时会被人访问。拿着公开的 JWT 密钥 =
任何人都能伪造管理员 token 打进去。

**已修**：判定改成**白名单**语义 —— 只有 `dev` / `local` / `test` 放行公开密钥，
其余（`production` / `staging` / **任何没听说过的**）一律按生产对待。
加新环境时默认是"严"，要放宽得显式写进 `LAX_PROFILES`。

> 白名单而不是黑名单的理由，同 CLAUDE.md 里员工权限那条一样：
> 减法只能挡住**已知**的坏 profile；新增一个环境类型时，黑名单默认放行 ⇒ 又漏一个。

## 5. 【medium】Worker 侧没有占位符守卫

Worker 的启动自检只检查"token 配没配"，**不检查配的是不是仓库里公开的值**。
而后端侧的守卫（§4）在 staging/prod 确实会拒绝启动 —— 但 Worker 是**独立的 Deployment**，
后端起不来不代表 Worker 起不来。两边都要守。

**已修**：

- `worker/src/edam_worker/config.py` 新增 `EDAM_ENV`（默认 `dev`）与
  `known_placeholder()` / `KNOWN_SECRET_PLACEHOLDERS`；
- `main.py` 启动时：非开发环境命中占位符 ⇒ `raise RuntimeError` 拒绝启动；
  `OPS_TOKEN` 同理（helm 里 `OPS_TOKEN` 映射的是同一个 `worker-token` 键）；
- helm 的 worker Deployment 注入 `EDAM_ENV`，取值与后端的 `SPRING_PROFILES_ACTIVE` 一致。

## 6. 【medium】WebSocket 订阅只校验形状，不校验角色

`WebSocketAuthInterceptor.requireAllowedSubscription` 只检查目的地的**形状**
（是不是 `/topic/notifications/...`），**不检查角色**。

而 `websocket/NotificationController.broadcastLeakAlert` 把整个 `LeakDetection` 对象
原样广播到 `/topic/notifications/leak` —— 里面含
**疑似泄露用户 ID、泄露文件路径、匹配会话 ID、置信度**（不是脱敏摘要）。

于是任何一个登录用户（包括只有 `notification:read` 的普通员工）都能订阅这个 topic，
实时收到别人的疑似泄露信息。STOMP 的 SUBSCRIBE 帧不过 Servlet 层的
`JwtAuthenticationFilter`（那是 HTTP 握手层的事），所以通道上必须自己判权限。

**已修**：敏感 topic 增加权限校验 —— `/topic/notifications/leak` 需要 `leak:read`
（口径与前端 `hasPermission` 一致：`*:*` 全通、`*:<action>` 该动作全通、否则精确匹配）。
权限码签在 JWT claims 里，不需要查库。

## 7. 【medium】前端路由守卫无限重定向 ⇒ 白屏

`web/src/router/index.ts` 的守卫遇到没权限的目标时一律
`next({ name: 'Dashboard' })`。**如果用户连 `dashboard:read` 都没有**，
跳过去会再次进入守卫 → 再次判定无权限 → 再跳 Dashboard ……
Vue Router 检测到"重定向到同一个位置"会抛
`Detected an infinite redirection in a navigation guard`，**导航直接失败**，
用户看到的是白屏，连"无权限"的提示都收不到。

触发路径很现实：管理员在 RBAC 管理界面把 `dashboard:read` 从某个角色上摘掉
（权限是数据不是代码，改错了不会编译报错）⇒ 这个角色的所有人立刻白屏。

**已修**：

- 新增 `/forbidden` 路由与 `web/src/views/Forbidden.vue`；
- 守卫的落点改成 `forbiddenRedirect(userStore)`：
  有 `dashboard:read` ⇒ 回仪表板；没有 ⇒ 去"无权限"页；
- router 抽成 `createAppRouter()` / `registerAuthGuard()` 工厂，测试能造全新实例。

**回归测试**（`web/src/router/index.spec.ts`）把两条落点都钉死，
并**验证过它确实能抓住旧行为**：把 `forbiddenRedirect` 临时改回"一律回仪表板"，
用例立刻失败并打印 `Detected a possibly infinite redirection in a navigation guard`。

> 附带修的坑：vitest 收集用例时 element-plus 的 ESM 入口会 import 它的 CSS，
> 而 vitest 默认把 node_modules 里的依赖外置给 Node 原生加载，Node 不认 `.css` ⇒
> `ERR_UNKNOWN_FILE_EXTENSION`。已在 `web/vite.config.ts` 的 `test.server.deps.inline`
> 里把 element-plus 标成 inline。

## 8. 【medium】Webhook 投递侧四个缺陷

这一节的原始发现来自本轮唯一那路 agent，我逐条复核了代码路径才动手。

### 8.1 读响应体没有独立超时（已修）

`HttpRequest.timeout(30s)` **只覆盖到响应头** —— 用 `BodyHandlers.ofInputStream()` 时，
返回头之后读 body 是调用方自己的事，不受那个超时约束。
而 `readNBytes(64KB)` 会一直读到 EOF 或凑满 64KB：
一个返回 `200` + 少量字节然后**保持连接不断**的对端（slow-loris）就能把投递线程**永久**卡住。
`webhookExecutor` 上限 16 线程 ⇒ 16 个挂死后全部 webhook 投递停摆。

**修法**：把"读 body"丢进独立的小线程池（`webhookReadExecutor`，4~8 线程，
拒绝策略 `AbortPolicy`），用 `Future.get(10s)` 兜住；超时 ⇒ 记一次失败、走重试。
**不用 `CallerRunsPolicy`** —— 那会让调用线程自己读，又回到"永久卡住"的老问题。

### 8.2 退避档位与 max-attempts 脱钩（已修）

退避档位只有 5 个，每个档位对应**一个声明出来的延迟队列**
（`edam.webhook.retry.delay.{n}`），而重试是按"当前失败次数"选档位的。
`max-attempts` 是个可配置项 —— 配成 7，第 6 次失败要用第 6 档，
而第 6 档队列**没有声明也没有绑定** ⇒ broker 静默丢弃 ⇒
既不重试也不进 DLQ，运维在库里查不到任何痕迹。

**修法**：`getEffectiveMaxAttempts()` 把配置值**夹到 `档位数 + 1`**（= 6）。
顺带修掉一个 off-by-one：原来默认 `max-attempts=5`，于是
"第 5 次失败 → 12 小时后重试"这一档（`backoffMillis[4]`）**永远用不到** ——
第 5 次失败直接进 DLQ。默认改成 6 之后，5 个档位才与类注释里写的策略一致。

### 8.3 签名不含时间戳 ⇒ 可无限重放（已修）

原来只对 payload 签名，`X-EDAM-Timestamp` 是个"装饰性"的头：
抓包拿到一次合法回调后可以**原样无限重放**，而接收端没有任何办法判断这条是不是新事件
（payload 里也没有 event_id / delivery_id 可供去重）。

**修法**：签名改为 `HMAC-SHA256(secret, timestamp + "." + payload)`，
接收端验签时一并校验时间戳窗口即可防重放，也能用 `(webhook_id, timestamp)` 做幂等键。

> 签名方案此前只在代码里定义、没有写进任何文档 ⇒ 改它不影响既有接收端。

### 8.4 其它三条（**未修**，记为待办）

| 问题 | 后果 | 为什么没修 |
|---|---|---|
| **明文 secret 随重试消息进入 RabbitMQ 持久化队列** | 任何有 broker 读权限的人（管理插件 / 队列镜像 / 运维账号 / 备份里的 mnesia 文件）能取出该 secret，用来伪造 `X-EDAM-Signature` | 要根治得把 secret **加密**存进 `webhook` 表（加列 + 迁移），重试消息只带 `webhook_id`。这是 §10 的"整体未接线"的一部分，一起做更合适 |
| **注销 webhook 不取消在途重试** | 用户注销（想止损或轮换密钥）后，旧地址仍会被带着签名密钥的请求继续 POST 最多 5 次、跨越 12 小时以上 | 需要在投递前查一次 webhook 是否仍存在 —— 属于同一个"接线"改造 |
| **投递结果没有可查询的状态** | `webhook_delivery` 表里没有 success/fail 列（失败只写 `response_status=0`）、`webhook.fail_count` 恒为 0、`last_delivered_at` 恒为 null | 需要加列（迁移）+ 改 model，同样属于同一个改造 |

### 8.5 复核确认：SSRF 与签名比较**没问题**

- `SsrfGuard` 覆盖协议白名单、IPv4 + IPv6 私网/回环/CGNAT/链路本地拦截、
  注册时与**每次投递前**各校验一次、`HttpClient.Redirect.NEVER` 明确禁用重定向；
- 仓库内唯一的入站令牌校验 `WorkerTokenVerifier` 正确使用 `MessageDigest.isEqual`
  （常量时间），secret 未明文入库、未打印日志。

## 9. 【low】两处对不上

### 9.1 镜像 tag 与 registry 三处不一致（未修）

| 位置 | 值 |
|---|---|
| CI（`.github/workflows/ci.yml`） | 推 `edam/backend:${{ github.sha }}` 与 `:latest` 到 **Docker Hub**（`docker/login-action` + `DOCKERHUB_USERNAME`） |
| ArgoCD prod（`edam-prod.yaml`） | 拉 `ghcr.io/example/edam` + `backend.image.tag: v3.4.1` |
| helm base（`values.yaml`） | `edam/backend` + `tag: "3.4.2"` |

⇒ **registry、仓库名、tag 三处都不同** ⇒ prod 用的镜像不由这条 CI 产出。
（`targetRevision` 也是固定的 tag `v3.4.1`，而 CI 按 git sha 打标签。）

**没改**：这涉及发布流程与制品仓库权限，得运维/产品定 —— 统一 registry + tag 命名规则，

### 9.2 `db-username` 写进了 Secret 却没人消费（已修）

原来的 ExternalSecret 写了 `db-username` 这个键，但**没有任何地方消费它** ——
`application.yml` 里是 `${MYSQL_USER:edam}`，一直用硬编码默认值。
运维改了 Vault 里的库用户名也不生效（而且悄无声息）。

**修法**：ESO 保留这个键；Deployment 增加 `MYSQL_USER` 环境变量从它读（`optional: true`，
没配时仍走默认值，不至于起不来）。

## 10. 复核确认：三条"功能根本没接线"的旧账

agent 报的三条 high 我逐条复核，**确认属实，且 README 的已知限制里已经写着**
（不是本轮新问题，本轮只是再次确认并补了证据）：

| 功能 | 复核结论 |
|---|---|
| **Webhook 首次投递没有生产者** | `deliver()` 的唯一调用方是 `WebhookRetryConsumer`；全仓库没有 `@Scheduled` 扫描、没有事件发布器。而重试消息本身是投递失败后才发的 ⇒ **没有任何路径能触发首次投递**。更根本的是：库里只存 secret 的**哈希**（`WebhooksController` 里 `sha256Hex`），投递端**连明文 secret 都拿不到去签名** |
| **站内通知没有生产者** | 全仓库没有一处 `new Notification()` / `notificationRepository.insert` ⇒ `GET /notifications` 永远返回空 items、`unread_count` 恒为 0 |
| **泄露告警 handler 没有调用方** | `LeakDetectionAlertService.handleDetectionResult` **无任何调用方**，该 Service 甚至没被注入到任何地方 ⇒ worker 检出泄露时 `leak_detection` 表里不会有记录，安全团队也永远收不到 P1 告警 |

> 这三条的"何时触发"（哪些事件算泄露、通知给谁、告警发到哪）都是**产品决策**，
> 不是纯技术问题 —— 所以没有"顺手接上"，而是留在已知限制里等决策。

## 14. 与方案书 / 前几轮的关系

- **方案书 §5.2 身份认证 / §14.3 STRIDE**：§1、§2、§4、§5、§6 都在这一章
  （密钥管理、认证、Spoofing / Information Disclosure）。
- **方案书 §6.3 密级模型 / §7.1 核心数据表**：§2 的"可改写溯源结论"落在
  密级与审计的证据链上 —— 指纹登记表（`watermark_cache`，第六轮新增）在这里被当成
  权威依据，所以它的写入口必须守住。
- **方案书 §5.4 细粒度权限与外发管控**：§6 的 `leak:read` 是角色层权限码，
  与 `sys_permission` 目录一致。

  §2 是同一套思路的延伸（Worker 密钥同样要守）。
- **第六轮 §2（指纹登记表）**：本轮 §2 说明了那张表为什么必须守住写入口 ——
  它的写入方（Worker 回调）只靠一个共享密钥鉴权。
