## 1. [P0-1] MyBatis-Plus 分页插件从未注册

### 1.1 根因

MP 的 `selectPage(IPage, Wrapper)` **本身不做 LIMIT** —— LIMIT 是
`PaginationInnerInterceptor` 在 SQL 拦截层改写出来的。
没有拦截器时它退化成普通 `selectList`：

- 返回**全表**，`page_size` 参数彻底失效
- `total` 恒为 0 ⇒ 前端分页器显示"共 0 条"

而 MP 的自动装配（`MybatisPlusInnerInterceptorAutoConfiguration`）带
`@ConditionalOnBean(InnerInterceptor.class)` ——
**应用不自己声明 bean，它就不会被创建**。

### 1.2 修法

**新增 `backend/src/main/java/com/example/edam/config/MybatisPlusConfig.java`**：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.MYSQL);
    pagination.setMaxLimit(MAX_QUERY_ROWS);   // 1000 —— 兜底闸门
    pagination.setOverflow(false);             // 页码越界返回空，不回退首页
    interceptor.setInterceptors(List.of(pagination));
    return interceptor;
}
```

**新增 `backend/src/main/java/com/example/edam/util/PageParams.java`**：
`clampPage` / `clampSize`（1~100），9 处 `selectPage` 调用点全部改用它。

### 1.3 实证：新发现的坑 —— `maxLimit` 会把审计导出截断

报告 §1.8 建议 `setMaxLimit(1000L)`。**照做会引入一个新 bug**：

审计导出走 `Page(1, MAX_EXPORT_ROWS + 1)`（50001 行），
而全局 `maxLimit=1000` 会把它**截断成 1000 行** ⇒
「5 万行上限保护」变成「最多只能导出 1000 行，**而且不报错**」。

实测（H2 + 仓库同一份 `mybatis-plus-extension-3.5.7.jar`）：

```
[maxLimit=1000    ] Page(1,50001) -> records=1000   ← 被截断（静默）
[maxLimit=100000  ] Page(1,50001) -> records=2000   ← 全取到
```

**修法**：`Page.setMaxLimit()` 的优先级高于拦截器的全局值（实测确认），
所以导出处显式覆盖：

```java
Page<OperationLog> page = new Page<>(1, MAX_EXPORT_ROWS + 1);
page.setSearchCount(false);
page.setMaxLimit((long) MAX_EXPORT_ROWS + 1);   // ← 覆盖全局闸门
```

⇒ 导出的内存占用仍然有界（最多 50001 行），
但不再被全局闸门砍到 1000 行。

### 1.4 顺带修掉：Webhook 投递历史的分页公式

`WebhooksController.deliveries` 原来写的是：

```java
int size = Math.min(100, Math.max(1, 20 * Math.max(1, page)));
```

**每页条数随页码线性增长**。这个公式只有在分页失效时才能"看起来对"
（插件没注册 ⇒ selectPage 忽略 page/size 直接返回全量，那个 size 是死数字）。

插件补上后它会真的生效，而 `size = 20 * page` 配合 `offset = (page-1) * size`
会算出乱七八糟的偏移：**page=2 ⇒ size=40, offset=40 ⇒ 第 21~40 条被整段跳过**。

⇒ 改成常规的 `page` + `page_size`（新增 `page_size` 参数，夹在 1~100）。

### 1.5 回归测试

**新增 `backend/src/test/java/com/example/edam/config/MybatisPlusConfigTest.java`（10 条）**

关键点：**用生产代码里的那个配置类**（`new MybatisPlusConfig().mybatisPlusInterceptor()`），
不是在测试里另写一份拦截器 —— 否则"生产配置被改坏了"照样测不出来。

用 **H2** 而不是真 MySQL：验证的是"分页机制本身"（LIMIT 有没有被下推到 SQL），
不涉及 MySQL 方言。H2 让它**不需要外部服务**就能跑 ——
而"CI 里跑不起来"的测试等于没有测试。
真 MySQL 上的 Flyway 迁移验证由 `ApplicationStartupTest` 负责。

**验证测试真的能抓住这个 bug**（把插件摘掉，测试必须变红）：

```
摘掉插件后：Tests run: 10, Failures: 6, Errors: 1
  selectPageActuallyPaginates:  expected: <10> but was: <2000>   ← 全表返回
  secondPageReturnsDifferentRows: expected: <10> but was: <2000>
  maxLimitCapsOversizedPage: 期望 ≤1000，实际 2000
  ...
```

恢复后：10 条全绿。

### 1.6 端点影响

10 处 `selectPage` 现在真的分页了 ⇒ **10 个端点的返回条数会变**（变小）。
这是修复，不是回归 —— 但**上线后前端分页器会开始显示真实总数**，
之前一直显示"共 0 条"。

## 2. [P0-2] iOS SDK 编译不过 + CI 编译门

### 2.1 报告记的两个编译错误

| 位置 | 错误 | 修法 |
| --- | --- | --- |
| `EDAMPlayer.swift:124` | `avPlayerLayer = = nil`（多一个 `=`） | `avPlayerLayer = nil` |
| `EDAMPlayer.swift:178` | 用了不在作用域的 `accessToken` | 见 §2.2 —— 改用后端签发的**播放 token** |

第三处：`Package.swift` 声明的 `testTarget` 指向**不存在的 `EDAMPlayerTests/` 目录** ——
SwiftPM 在**解析 manifest 时**就报错，整个包根本构建不了。
该 testTarget 从来没有对应的测试代码 ⇒ 移除。

### 2.2 报告建议的修法不对，我改了

报告 §2.4 说"把 `accessToken` 传进去"。**那样做是错的**，理由两条：

1. **没用** —— 后端的 `playlist.m3u8` / `segment` / `key` 三个端点是
   `permitAll`，**只读 URL 上的 `?token=`**，根本不读 `Authorization` 头。
2. **危险** —— `AVURLAssetHTTPHeaderFieldsKey` 是 **Apple 未公开的私有 API**
   （提交 App Store 有被拒风险），而且往里塞**登录 JWT** 会让这个
   长期有效（可被 refresh_token 续期）的凭据跟着媒体请求到处走。

正确做法：**什么都不塞**。播放 token 已经在 `m3u8_url` 的 query 里了。

⇒ `setupPlayer(in:session:)` 改成只接 `session`，不再需要 `accessToken`。

### 2.3 顺带发现：SDK 与后端的解码契约**根本对不上**

`PlaybackSession` 声明了 `userId: Int64`（非可选）和 `expiresAt: Date`，
但后端 `/playback/{video_id}/token` 实际返回的是：

```json
{ "session_id", "m3u8_url", "token", "expires_at", "key_url", "watermark_template" }
```

- **没有 `user_id`** ⇒ 非可选字段解码**必然抛错**
- `expires_at` 是 **ISO-8601 字符串**（`Instant.ofEpochSecond(...).toString()`），
  而 JSONDecoder 默认按**数字**（时间戳）解码 ⇒ **也抛错**

⇒ 即便编译过了，**每次播放都会在解码时失败**。

修法：显式 `CodingKeys` + 自己解析 ISO-8601（两种格式都试，
带小数秒的变体用默认 formatter 会返回 nil）。

**新增 `PlaybackControllerTest` 的 2 条契约测试**（共 17 条），
把跨语言契约钉死：字段名固定、`expires_at` 必须是字符串、
**不要**加 `user_id`（留着只会诱导客户端再写一个解码必错的字段）。

### 2.4 顺带发现：水印显示的是 `USER_0`

`refreshWatermark` 原来用 `currentSession?.userId` ——
而那个字段压根不存在（见 §2.3）⇒ **水印永远显示 "USER_0"**。

水印看着在，其实在骗人：**视频外泄后拿到的水印指不出是谁**。

⇒ 改用工号（`/auth/me` 的 `employee_no`），与前端一致
（`web/src/views/VideoDetail.vue:457` 用 `currentEmployeeNo`）。
取不到就退化成 `session_id`。

### 2.5 顺带发现：移动端播放日志**从来没上报过**

`reportPlaybackProgress` / `reportScreenshotEvent` 原来只 `print` 一行。
前端早就接了 `/playback/{id}/log`（`VideoDetail.vue:338`），
**移动端是空白** ⇒ 视频从手机外泄，`play_log` 里查不到任何记录。

方案书 §7.1 把 `play_log` 与 `operation_log` 并列为"审计与溯源"两张核心表，
§7.3 更是规定播放日志保留 **365 天**（比操作日志的 180 天更长）。

⇒ 已接上（失败不影响播放，旁路调用）。

### 2.6 顺带发现：两个资源泄漏

| 位置 | 问题 | 修法 |
| --- | --- | --- |
| `setupPlayer` | `addPeriodicTimeObserver` 的句柄没存 ⇒ AVPlayer 持有 observer 强引用 ⇒ **player 永远不会被释放**（每次 stop() 泄漏一个 AVPlayer + 一个回调） | 存句柄，`stop()` 里 `removeTimeObserver` |
| `stop()` | `avPlayerLayer = nil` 但没从 `container.layer` 移除 ⇒ **图层留在视图上** | `removeFromSuperlayer()` |

### 2.7 顺带发现：m3u8 是相对路径

后端返回的 `m3u8_url` 是**根相对**的
（`/api/v1/playback/{id}/playlist.m3u8?token=...`），
直接 `URL(string:)` 得到的是没有 scheme/host 的 URL，**AVURLAsset 拉不到内容**。

⇒ 新增 `resolveURL(_:against:)`，用 `URLComponents` 显式拼
（语义与前端 `window.location.origin + tk.m3u8_url` 一致）。

### 2.8 CI 编译门（**最关键的一步**）

**新增 `.github/workflows/ci.yml` 的 `mobile-sdk-ios` job**：

```yaml
mobile-sdk-ios:
  runs-on: macos-latest
  steps:
    - uses: actions/checkout@v4
    - name: 显示 Xcode 版本
      run: xcodebuild -version
    - name: 列出可用 scheme
      working-directory: mobile-sdk/ios
      run: xcodebuild -list
    - name: 编译 iOS SDK
      working-directory: mobile-sdk/ios
      run: |
        xcodebuild build -scheme EDAMPlayer \
          -destination 'generic/platform=iOS' \
          CODE_SIGNING_ALLOWED=NO -quiet
    - name: 校验 Package.swift
      working-directory: mobile-sdk/ios
      run: swift package describe --type json > /dev/null && echo "Package.swift OK"
```

> ⚠️ **不能用 `swift build`**：它默认按**宿主平台**（macOS）编译，
> 而本 SDK 依赖 UIKit / AVKit / WebKit —— 这些框架在 macOS 上不存在，
> 会报 `no such module 'UIKit'`。那是命令选错了，不是 SDK 的问题。

代价：macos runner 比 linux 贵。报告 §2.4 已记下这个权衡 ——
**iOS SDK 只能这么验**。

### 2.9 顺带修：Android 灰度哈希 + iOS `abs(Int.min)`

**Android**（`GrayReleaseConfig.kt`）：Kotlin 的 `%` **保留被除数的符号**
⇒ 负 hash 得到负 bucket，而 `bucket < percentage` 对负数**恒为真**。
`stableHash` 取 SHA-256 前 4 字节拼 Int，最高位为 1 时就是负数
⇒ **约一半**用户的 bucket 是负数。

报告 §8.5 实测：`percentage=10` 时 10000 个工号命中 **5543 个（55.4%）**，
期望约 1000（10%）⇒ 灰度比例实际是 55%，不是 10%。

⇒ `Math.floorMod(stableHash(userId), 100)`。

**iOS**（`GrayReleaseConfig.swift`）：`abs(Int.min)` 在 Swift 里是
**precondition 失败（直接崩溃）**，而 djb2 变体在极端输入下确实能算出 `Int.min`
⇒ 那个 userId 一调用就崩。

⇒ `stableHash` 去掉 `abs`，改用显式的无符号/回绕运算符
（`&<<` 掩码移位、`&+` 回绕加法 —— 它们按定义不会 trap），
取模用 `UInt(bitPattern:) % 100`。

### 2.10 顺带修：iOS 文档预览的缓存命中分支

```swift
// 原来
webView.load(cached.data.flatMap { String(data: $0, encoding: .utf8).map(URL.init) } ?? url)
```

把**响应体**（文档内容本身）当成 URL 字符串去解析：
解析失败就 fallback 到 `url`（于是缓存命中反而**又发了一次网络请求**，缓存形同虚设）；
万一文档内容碰巧长得像 URL，就直接加载到错误的地方。

⇒ `webView.load(cached.data, mimeType:..., characterEncodingName:..., baseURL: url)`。

### 2.11 顺带修：SDK README 的能力表全是假的

`mobile-sdk/README.md` 原来把**全部能力都标成 ✅**，但其中三项当时**根本没实现**：

| 声称 | 实际 |
| --- | --- |
| Android HLS 安全播放 | `mobile-sdk/android/` 下**只有** `EDAMDocumentViewer` / `EDAMSecurityGuard` / `GrayReleaseConfig` 三个类，**没有任何播放器**（grep `ExoPlayer\|Media3\|PlayerView` 零命中） |
| Android 动态水印 | 同上，grep `watermark` 零命中 |
| Session Token 刷新 | 一直只有声明，没有实现 |

⇒ 按**代码里实际有什么**重标。这正是本轮的教训：
README 把一个**根本编译不过**的 SDK 写成"全绿"的能力表。

## 3. [P0-3] SVG 存储型 XSS

### 3.1 攻击路径

1. 攻击者（有 `document:upload`）上传 `payload.svg`，`Content-Type: image/svg+xml`，内容含 `<script>`
2. 分享给受害者（`view` 位即可）
3. 受害者打开预览 ⇒ 脚本在**后端域名**下执行
4. 受害者浏览器里有 `access_token` / `refresh_token`（`stores/user.ts` 存在 localStorage）⇒ **JWT 被直接偷走**

⇒ 这条链比一般的存储型 XSS 严重，因为它落在**持有令牌的认证域**上。

### 3.2 三个修复点（缺一不可）

**① 上传白名单排除 SVG**（`DocumentController.isAllowedDocumentType`）

> ⚠️ **后缀检查必须放在 MIME 分支前面**。
> 原来的结构是"MIME 命中就 `return true`"，后缀分支根本没机会执行 ——
> 于是 `Content-Type: image/png` + 文件名 `payload.svg` 就能混进来
> （客户端完全可以谎报 Content-Type）。
> ⇒ 改成：**危险信号先判**（后缀），再走放行逻辑（MIME），最后后缀白名单兜底。

同时排除了 `text/*`（`text/html` 是最经典的 XSS 载体）和 `.html/.htm/.xhtml`。

**② 落库 MIME 由服务端判定**（`DocumentService.resolveMimeType`）

原来存的是 `file.getContentType()` —— **客户端说了算**。
而预览端点用它决定 `Content-Type` 与是否 inline。

⇒ 改成按**文件后缀**判定。SVG 没有对应项 ⇒ 落到 `application/octet-stream`
（浏览器只当二进制下载，不解析）。

**③ 预览 inline 白名单改成精确枚举**（`DocumentPreviewService.isInlineSafe`）

```java
// 原来：前缀匹配
boolean inline = mime.startsWith("application/pdf") || mime.startsWith("image/")
                || mime.startsWith("text/");

// 现在：精确枚举
switch (base) {
    case "application/pdf": case "image/png": case "image/jpeg":
    case "image/gif": case "image/webp": case "image/bmp":
        return true;
    default:
        return false;   // image/svg+xml / text/html / 其它一律不 inline
}
```

> 为什么 `nosniff` 挡不住：它只防"声明类型与实际内容不符"，
> 而 SVG 的声明类型（`image/svg+xml`）**就是**浏览器会执行脚本的类型。

### 3.3 前端这一层更关键（报告没写到）

前端预览走 `fetch → blob → URL.createObjectURL → iframe`，
**完全绕过了服务端的 `Content-Disposition`** ——
后端就算回了 `attachment`，前端照样把字节塞进 iframe 里渲染。

而且 **Blob URL 的 origin 继承自当前页面** ⇒
SVG 里的脚本就在**本站 origin** 下执行 ⇒ 直接读 localStorage 里的 JWT。

⇒ 抽出 `web/src/utils/previewMime.ts`（精确枚举 + `safePreviewMime`），
`Documents.vue` 改用它。**三处**都要收紧：

1. `canPreviewInline` —— 精确枚举
2. **Blob 的 MIME** —— `safePreviewMime(doc.mime_type)`，
   不在白名单 ⇒ `application/octet-stream`（浏览器只下载不渲染）
3. `openInNewTab` —— 非白名单类型**拒绝**在新标签页渲染

> 为什么要抽成独立模块：这是**安全边界**，必须有单元测试守着，
> 而 SFC 里的局部函数测不了。

**新增 `web/src/utils/previewMime.spec.ts`（12 条）**。

### 3.4 回归测试

**新增 `backend/src/test/java/com/example/edam/controller/DocumentSvgXssTest.java`（9 条）**：

| 用例 | 断言 |
| --- | --- |
| 上传 SVG（`image/svg+xml`） | 400，且**绝不**落到 Service |
| 上传 `.html`（`text/html`） | 400 |
| 上传 `.svg` 但 MIME 谎报 `image/png` | 400（**后缀分支也要挡**） |
| 正常 PNG / PDF | 仍然放行（别把功能改坏了） |
| `isInlineSafe` 对 SVG / HTML / text/* | 一律 false |
| `isInlineSafe` 对 PDF / 位图 | 仍然 true |
| `Content-Disposition` | 非白名单类型一律 `attachment` |
| 落库 MIME 按后缀 | SVG / HTML ⇒ `application/octet-stream` |

> **"后缀分支也要挡"这条用例在写的过程中就抓到了一个真 bug**：
> 我最初把 SVG 排除放在 MIME 分支里，
> 而 MIME 分支命中就 `return true` ⇒ 后缀检查根本没机会执行
> ⇒ `image/png` + `payload.svg` 能混进来。
> 测试直接报 NPE（说明请求**到了** Service，文件会真的进库）。

> ⚠️ 这也意味着：**本次改动没有在真 MySQL 上验证过**。

已做的降低风险措施：
