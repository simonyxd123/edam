## 1. [§2] Docker 后端镜像的 HEALTHCHECK 探活端口是错的

### 1.1 问题

```dockerfile
# docker/backend.Dockerfile（修复前）
HEALTHCHECK ... CMD curl -fsS http://localhost:8080/api/v1/health/live || exit 1
EXPOSE 8080
```

而后端实际监听 **8092**（`application.yml:5`，全链路统一端口）。

⇒ 任何"直接 `docker run` 后端镜像"的地方，healthcheck **永远失败**
⇒ 容器被标 `unhealthy`
⇒ `depends_on: condition: service_healthy` 的编排会**永远等下去**。

**为什么 K8s 生产没事**：K8s 用的是 `helm/edam/templates/deployment.yaml` 里的
livenessProbe/readinessProbe（走 `backend.service.port`，值是对的），
**Dockerfile 的 HEALTHCHECK 在 K8s 下被忽略**。

### 1.2 修法

HEALTHCHECK 与 EXPOSE 都改成 8092。

### 1.3 顺带修：**让这个漂移以后能被自动发现**

报告 §2 指出：`dev/db/_validate_ports.py` 的 9 处端口来源里**没有 Dockerfile**
⇒ 这个漂移不会被端口一致性校验挡住 —— 这正是它能活到现在的原因。

⇒ 把 Dockerfile 加进校验脚本的来源列表（现在 11 处）：

```python
find_port(read(DOCKERFILE),
          [r'HEALTHCHECK[\s\S]*?CMD curl -fsS http://localhost:(\d+)'],
          'dockerfile HEALTHCHECK probe port', ports)
find_port(read(DOCKERFILE),
          [r'EXPOSE\s+(\d+)'],
          'dockerfile EXPOSE port', ports)
```

**验证过它真的能抓到**：把 HEALTHCHECK 改回 8080 ⇒ 脚本报
`❌ 端口不一致：['8080', '8092']`，退出码 1；改回 8092 ⇒ `✅ 全部一致`，退出码 0。

## 2. [§5] 5 个 DB 校验脚本只挂在死掉的 GitLab 流水线

### 2.1 问题

仓库同时有 `.github/workflows/`（会跑）和 `.gitlab-ci.yml`（**不会跑** ——
`git remote` 是 github.com）。

而这 5 个校验脚本**只在 `.gitlab-ci.yml` 里**：

```
dev/db/_validate_model_schema.py   model 字段 ↔ 运行时 schema
dev/db/_validate_migrations.py     迁移链自洽性
dev/db/_validate_fk_types.py       全新库上外键两端类型兼容
dev/db/_validate_ports.py          端口一致性
dev/db/_validate_mysql_port.py     MySQL 端口一致性
```

⇒ **端口一致性校验、模型↔表列对账、迁移合法性校验、FK 类型校验、MySQL 端口校验，
在真正会跑的 CI 里全部缺席。**

CLAUDE.md 写着"仓库里有端口一致性校验"，但那个校验实际上没在跑。

### 2.2 修法

接进 `.github/workflows/ci.yml` 的 `db-migration` job（**在跑迁移之前**）：

```yaml
- name: 静态校验（model↔schema / 迁移链 / 外键类型 / 端口）
  run: |
    set -e
    python dev/db/_validate_model_schema.py
    python dev/db/_validate_migrations.py
    python dev/db/_validate_fk_types.py
    python dev/db/_validate_ports.py
    python dev/db/_validate_mysql_port.py
```

放在迁移**之前**是有意的：静态校验不需要真库，能提前抓到
"Unknown column"（model↔schema 不匹配）与
"Error 3780 are incompatible"（FK 两端类型不兼容）——
这两类问题在 CI 里排查起来最费时间。

### 2.3 顺带修：表数量阈值 20 → 35

同一 job 里原来写的是 `-lt 20`，而 README / CLAUDE.md / `doc/database_schema.md`
都写着 **35 张表** ⇒ 缺 15 张表也照样绿灯。⇒ 改成 35（与 `.gitlab-ci.yml` 一致）。

### 2.4 顺带修：这 5 个脚本在 Windows 上**跑不起来**

5 个脚本都打印 ✅ / ❌。Windows 默认编码是 GBK，打这些字符会抛
`UnicodeEncodeError` —— **而且是在校验通过之后**（最后那行 print 崩掉），
于是"校验通过"被报成"脚本报错"，退出码非 0 ⇒ CI 变红、开发本地也跑不出结果。

⇒ 5 个脚本都加了：

```python
def _force_utf8_stdout():
    """让脚本在 GBK 控制台（Windows 默认）上也能跑。"""
    try:
        sys.stdout.reconfigure(encoding='utf-8')
    except (AttributeError, ValueError):
        pass
```

验证：5 个脚本在默认 GBK 控制台（不设 `PYTHONIOENCODING`）下退出码全为 0。

## 3. [§4] CI 里三个 job 引用不存在的文件或跑在错的目录

### 3.1 SonarQube —— 跑在没有 pom.xml 的目录

```yaml
# 修复前：在仓库根目录跑 mvn
run: mvn -B org.sonarsource.scanner.maven:sonar-maven-plugin:sonar \
        -Dsonar.projectKey=edam-backend \
        -Dsonar.sources=backend/src/main
```

仓库根目录**没有 pom.xml**（在 `backend/`）⇒ 这个 job 必然失败。
而且仓库里也**没有 `sonar-project.properties`**。

⇒ 加 `working-directory: backend` + 新建 `backend/sonar-project.properties`
（`sonar.sources=src/main/java` 等）。

### 3.2 Snyk —— 三个 action 全都扫了空气

`snyk/actions/{maven,python,node}` 是 **docker action**，
在 workspace 根目录跑 `snyk` —— 而根目录**没有** pom.xml / package.json /
requirements.txt（分别在 `backend/` `web/` `worker/`）。

**已核对 action.yml：这三个 action 都没有 `working-directory` 输入**
（只有 `command` / `args` / `json`），所以只能用 `args` 里的 `--file=` 指定清单文件：

```yaml
- name: 后端 Maven 依赖扫描
  uses: snyk/actions/maven@master
  with:
    args: --severity-threshold=high --fail-on=upgradable --file=backend/pom.xml
# worker 是 src/ 布局、没有 setup.py ⇒ 扫 requirements.txt
- name: Worker Python 依赖扫描
  uses: snyk/actions/python@master
  with:
    args: --severity-threshold=high --fail-on=upgradable --file=worker/requirements.txt
- name: 前端 npm 依赖扫描
  uses: snyk/actions/node@master
  with:
    args: --severity-threshold=high --fail-on=upgradable --file=web/package.json
```

### 3.3 ZAP —— 扫的是一个空端口

```yaml
# 修复前
target: 'http://localhost:8092/api/v1'   # 但这个 job 没有起任何服务
rules_file_name: '.zap/rules.tsv'          # 且这个文件不存在
```

⇒ 扫的是**空端口**，而且 ZAP 找不到规则文件。

**修法**：起服务再扫。用 `dev/mock/server.py`（纯标准库，不需要 MySQL/RabbitMQ）：

```yaml
- name: 启动 mock API（ZAP 要有活的目标才能扫）
  run: |
    nohup python dev/mock/server.py > /tmp/mock.log 2>&1 &
    for i in $(seq 1 30); do
      if curl -fsS http://localhost:4010/health/live > /dev/null 2>&1; then
        echo "mock API 已就绪"; exit 0
      fi
      sleep 1
    done
    echo "mock API 启动失败："; cat /tmp/mock.log; exit 1
```

**本地验证过 mock server 真的能起、真的服务 `/health/live`**：

```
$ python dev/mock/server.py &
$ curl -sS -w "HTTP %{http_code}\n" http://localhost:4010/health/live
{"status": "alive", "uptime_sec": 100, "pid": 1}
```

（端口是 **4010**，不是 9090 —— 这是我改的过程中查 `dev/mock/server.py` 确认的。）

同时**去掉了 `rules_file_name`** —— 仓库里没有 `.zap/rules.tsv`，
指定一个不存在的文件会让 ZAP 直接失败；用 ZAP 自带的默认规则。

### 3.4 Trivy —— 扫的不是会发布的镜像

```yaml
# 修复前
image-ref: 'docker.io/library/openjdk:17-jdk-slim'
```

这个镜像仓库里**根本不用**（`docker/backend.Dockerfile` 用的是
`eclipse-temurin:17-jre-jammy`）⇒ 扫了一个不会发布的东西。

⇒ 改成矩阵，扫**实际会发布的三个运行时镜像的基底**：

| 镜像 | 对应 Dockerfile |
| --- | --- |
| `eclipse-temurin:17-jre-jammy` | `docker/backend.Dockerfile` |
| `python:3.10-slim-bookworm` | `docker/worker.Dockerfile` |
| `nginx:1.25-alpine` | `docker/web.Dockerfile` |

### 3.5 SBOM —— 引用了一个不存在的 Action

```yaml
# 修复前
uses: cyclonedx/cyclonedx-maven-plugin@v2.7.9
```

**已核对**：该仓库是 **Maven 插件**，根目录**没有 `action.yml`**（不是 GitHub Action），
而且 tag 也不对 —— 真实 tag 是 `cyclonedx-maven-plugin-2.7.9`（没有 `v` 前缀）。

⇒ 改成在 `backend/` 里直接跑 `mvn cyclonedx:makeBom`。

Python 那侧 `cyclonedx-py -e .` 也不行 —— worker 是 `src/` 布局、
**没有 setup.py / pyproject.toml** ⇒ `-e .`（editable install）跑不起来。
⇒ 改用 `cyclonedx-py requirements worker/requirements.txt`
（**已核对 cyclonedx-bom 4.4.0 的 CLI 确实有 `requirements` 子命令**，
且它接受 `requirements_file` 位置参数）。

### 3.6 覆盖率阈值 95 → 100

```bash
# 修复前
COVERAGE=$(grep -oP '已覆盖.*?\(\K[\d.]+(?=%)' modify/controller-coverage.md | head -1)
if [ "$(echo "$COVERAGE < 95" | bc -l)" = "1" ]; then
```

两个问题：

1. **`grep -P`（PCRE）在部分 runner 镜像上不可用** ——
   GNU grep 需编译时带 `--enable-pcre`。没有的话这一步直接"读不到覆盖率"
   ⇒ 报错 ⇒ CI 红。
2. **阈值写的是 95，而 README / CLAUDE.md / openapi.yaml 都承诺 100%**
   ⇒ 95%~100% 之间掉下去 CI 是绿的，**承诺与门限不一致**。

⇒ 改用 Python 解析（runner 上本来就有 python3），阈值提到 100：

```yaml
- name: 校验覆盖率必须 = 100%
  run: |
    python3 - <<'PYEOF'
    import re, sys
    text = open('modify/controller-coverage.md', encoding='utf-8').read()
    m = re.search(r'已覆盖\s*\|\s*\d+\s*\(\s*([\d.]+)\s*%', text)
    if not m:
        print('ERROR: 无法从 modify/controller-coverage.md 读取覆盖率'); sys.exit(1)
    coverage = float(m.group(1))
    print(f'当前 OpenAPI Controller 覆盖率: {coverage}%')
    if coverage < 100.0:
        print(f'ERROR: 覆盖率 {coverage}% 低于 100% 阈值'); sys.exit(1)
    PYEOF
```

**验证过两种情况**：100.0% ⇒ 打印 PASS、退出码 0；
94.9% ⇒ 报错、退出码 1。

## 4. [§6 §7] 前端不再把凭据打进浏览器控制台

### 4.1 报告记的两条

| 位置 | 问题 |
| --- | --- |
| `VideoDetail.vue:112` | `console.log('[VideoDetail] m3u8 URL:', fullUrl)` —— `fullUrl` 带着 `?token=<播放 JWT>` |
| `client.ts:139` | `console.warn('[client] session invalid, ...', error.config?.url)` |

播放 token 由 `POST /playback/{id}/token` 签发，带 `scope=playback` +
`video_id` 绑定，**10 分钟有效**，可直接换取该视频的 m3u8 / 分片 / **AES 密钥**。

违反的规则：**日志中不得打印 token 本身（连哈希都不打）**。

### 4.2 修法

**① m3u8 URL** —— 复用已有的 `redactTokenFromUrl`（`utils/hlsError.ts` 里本来就有）：

```ts
console.log('[VideoDetail] m3u8 URL:', redactTokenFromUrl(fullUrl));
```

**② HLS 事件对象** —— `log(e, d?)` 的第二个参数允许把整个事件对象打出来，
而 hls.js 的事件对象里带着**分片 URL / 密钥 URL**（后面跟着 token）。
⇒ **在类型层面就不给传对象的机会**：签名改成 `log(e: string)`。

**③ hls.js 的错误消息** —— 这是**报告没写到的一条**，而且更隐蔽：

hls.js 的 key-loader 源码：

```js
return Promise.reject(createKeyLoadError(
  frag, ErrorDetails.KEY_LOAD_ERROR,
  new Error("Invalid key URI: \"" + uri + "\"")));
```

那个 `uri` 就是后端改写过的密钥地址
（`/api/v1/playback/{id}/key?token=<播放 JWT>`）
⇒ **`data.error.message` 里带着可用的播放凭据**，
而它会流进 ①控制台日志 ②用户看到的错误文案 ⇒ **两处都泄**。

⇒ 新增 `redactTokenFromText()`，对**任意文本**打码：

```ts
export function redactTokenFromText(text?: string): string | undefined {
  if (!text) return undefined;
  return text.replace(/([?&]token=)[^"'\s&]*/gi, '$1***');
}
```

`describePlaybackError` 的 `reason` 改用它；`VideoDetail.vue` 里
`JSON.stringify({..., error: data.error?.message, ...})` 改成用已打码的 `errInfo.reason`。

### 4.3 报告**没写到**的一条：axios 错误对象带着**登录 JWT**

这是这轮最值得说的发现。报告 §7 说 `error.config?.url` 是相对路径、
"这条本身不泄 token"——**对 url 而言成立**。

但 axios 的错误对象里有 `config.headers`，而 `web/src/api/client.ts:55`
正是在那里塞登录 JWT：

```ts
config.headers.Authorization = `Bearer ${token}`;
```

⇒ **每一个出错的前端请求，`console.error('...', e)` 都会把登录 JWT 打进控制台。**

**实测确认**（临时探针，已删除）：

```
--- JSON.stringify(error) 里出现 SECRET 了吗： true
--- error.config.headers.Authorization = Bearer SUPER_SECRET_LOGIN_JWT
```

前端有 **11 处** `console.error/warn('...', e)` 直接打错误对象。

⇒ 新增 `web/src/utils/safeLog.ts`：

```ts
export function safeError(e: unknown): Record<string, unknown>
export function redactSecrets(value: unknown, depth = 0): unknown
```

`safeError` 只挑排障需要的字段（状态码 / 方法 / URL / detail / reason），
**整个 headers、request、response 都不进摘要** —— 丢得比打码更彻底。

⇒ 11 处全部改成 `safeError(e)`。

### 4.4 前端 403 提示看不出哪里越界

（这轮做的越权转授整改顺带修的，列在这里便于对照）

`client.ts` 的 403 分支原来统一弹 `"没有权限执行该操作"`，
把后端可操作的 `detail` 丢掉了。⇒ 改成优先显示 `data?.detail`。

### 4.5 回归测试

| 文件 | 用例 | 覆盖 |
| --- | --- | --- |
| `web/src/utils/safeLog.spec.ts`（新增） | 12 | Authorization 头打码、Cookie 头打码、URL token 打码、裸 JWT 打码、request/response 丢弃、保留排障字段、非对象错误、循环引用不栈溢出 |
| `web/src/utils/hlsError.spec.ts`（扩充） | +5 | `"Invalid key URI"` 消息里的 token 打码、`describePlaybackError.reason` 已打码、`formatPlaybackError` 文案里无 token |

**端到端验证**（临时探针，已删除）：

## 5. [§9] secret 没配就失败 ⇒ workflow 长期红着

### 5.1 问题

`security-scan.yml` 有 4 个 job 依赖 secrets（`SNYK_TOKEN` / `SONAR_TOKEN` /
`SONAR_HOST_URL` / `GITLEAKS_LICENSE`）。**secret 没配时 job 直接失败**（不是跳过）
⇒ 整个 workflow 长期红着 ⇒ 没人去修 ⇒ **安全扫描实际等于没有**。

这与本仓库踩过两次的"CI 红了没人发现"是同一个失效模式
（见 `worker/src/edam_worker/config.py:224-235` 的注释：
worker 因为 import 删错，从 2026-10-23 到 2026-10-29 一次都没起来过）。

### 5.2 修法

**不配 secret 就跑不了的扫描，等于没扫描。**
所以每个依赖外部服务的 job 都加 `if: secrets.X != ''` ——
**secret 配了就跑，没配就跳过**（跳过是绿的，失败是红的 —— 别搞反）：

```yaml
snyk-scan:
  if: ${{ secrets.SNYK_TOKEN != '' }}
sast-scan:
  if: ${{ secrets.SONAR_TOKEN != '' && secrets.SONAR_HOST_URL != '' }}
```

另外每个 job 的注释里都写清"它到底在扫什么"，
免得又出现"看着在扫、其实扫的是空气"。
