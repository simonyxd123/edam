## 一、为什么这 8 项值得单独排一次

它们有一个共同点：**表面上是"没接线"，实际上是"静默失效"**。

| 现象 | 真实后果 |
|---|---|
| WebAuthn / SSO 登录写死权限码 | 管理员登录被降级成普通员工；无角色用户反拿到 3 条权限 |
| 密级由客户端声明 | 任何人都能把资产声明成 L1 公开 ⇒ 全站可见 |
| 回调 URL 拼成 `/api/v1/api/v1` | 视频状态**永远**不回写，转码完成了点播放还是 404 |
| 回调重试路由键对不上 | 失败的通知**直接消失**，既不重试也不进死信 |
| `/watermarks/extract` 返回"没查到" | 运维据此认定"这个文件是干净的" —— **把扫描失败说成干净** |
| `PUT /notifications/preferences` 原样回显 | 用户以为设置保存了，其实什么都没存 |
| 国密 `parseSm3Token` 借道 jjwt | 任何 GS256 token 都解析不出来 |
| pHash 两套不兼容实现 | 指纹对不上，匹配率 ≈ 0，**且不报任何错** |

最后两条最阴险 —— 它们不会让任何东西崩，只是**安静地给出一个错误的答案**。
一个把扫描失败说成"干净"的接口，比没有接口更糟。

## 二、逐项处置

### 1. WebAuthn / SSO 登录绕过 RBAC（`1dfc773`）

**问题**：`WebAuthnController` 与 `SsoUserProvisioning` 签发 JWT 时写死了
`ROLE_EMPLOYEE` + 三条固定权限码。JWT 里的 `permissions` 就是
`@PreAuthorize("hasAuthority(...)")` 的唯一判据 —— 写死等于这两条登录路径
**完全绕过了 RBAC**。

**修法**：

- 新增 `TokenIssuanceService`：四个签发点（密码登录 / 刷新 / WebAuthn / SSO）
  统一走它，角色与权限码一律读 `sys_user_role` → `sys_role` →
  `sys_role_permission` → `sys_permission`
- 账号状态检查（锁定 / 禁用）抽到 `LoginAttemptService`，三条登录路径共用 ——
  此前 WebAuthn / SSO 完全没查状态，**离职账号照样能换到有效 JWT**
- WebAuthn 登录补 MFA 校验、补 `refresh_token` 落 Redis（此前只生成不存，
  `/auth/refresh` 必然失败）、补登录限流（端点匿名，不限流就能枚举工号）
- SSO 新开通用户在 RBAC 表里真的给一个角色
- `SecurityConfig` 放开 `/auth/webauthn/login/**`，与 openapi 契约对齐

### 2. 密级服务端裁决（`5b1c3b6`）

**问题**：`classification_lv` 一个字节都没校验，非法值还被 `default -> 1`
静默降级成 **L1 公开**。

**修法**：最终密级 = **max(服务端基线, 客户端声明)** —— 客户端可以往严里选，
不能往松里选。

- 基线 = 文件名关键词 / 文件大小 / 上传者部门
  - 新增 `SysDept` 实体 —— Java 侧此前**没有**部门模型，
    "按上传者部门定密级"这条规则等于从未生效
  - 部门规则改**包含匹配** —— 原先是全等匹配（`"法务"`），
    而 `sys_dept` 里叫「法务部」，一条都命中不了
- 自动识别**封顶 L3** —— L4 绝密只能由人显式声明或事后人工调整，
  否则一个 6GB 培训视频会变成谁也看不见的资产
- 删掉 `DataClassificationService` 里"用户手动选择的密级优先"的短路 ——
  那条短路正是"密级由客户端决定"的根源
- 新增 `PATCH /classification/{videos|documents}/{id}` 人工调整密级
  （门 `classification:manage`，此前该权限码 Java 侧零引用），reason 必填
- 上传响应回传**实际落库**的密级，前端在服务端抬高时如实提示用户

### 3. 文档处理状态不回写 + 回调 URL 拼错（`b7364ee`）

**问题 A**：`BACKEND_BASE_URL` 在 helm / ops 的 env 里**带了** context-path，
代码又习惯性地拼一次 `/api/v1` ⇒ `/api/v1/api/v1/videos/1/status` ⇒ 404 ⇒
被当成"其它 4xx" ⇒ `PermanentWorkerError` ⇒ **视频状态永远不回写**。

**问题 B**：文档处理根本没有回调端点，`watermark_status` / `preview_status`
永远停在 pending。

**修法**：新增 `config.backend_api_url()` 统一收口（两种写法都对）；
新增 `PATCH /documents/{doc_id}/status`，鉴权与视频侧完全一致；
水印与预览两个状态**分开**报；状态与路径**必须在上传成功之后**才置 ready。
Worker 回调令牌校验抽成 `WorkerTokenVerifier` —— 这类安全关键代码不能复制两份。

### 4. q.watermark 支线 + 两套不兼容的指纹实现（`81c444a`）

**问题 A**：`q.watermark` 被声明、被绑定、被消费、被监控 —— 但**没有生产者**。
真实的盲水印嵌入走的是 `q.document.preprocess`。留着一条永远是空的队列，
运维看监控会以为这条链路是活的 ⇒ 整条支线删除。

**问题 B**：pHash 有两套互不兼容的实现（imagehash 带高通滤波 vs 手写 DCT 不带），
指纹对不上，**匹配率 ≈ 0 且不报任何错** ⇒ 新增 `fingerprint/phash.py` 作为
**唯一实现**，两边都调它。`fingerprint.json` 的存储格式**保持不变**
（已落盘的数据靠它）。

**问题 C**：盲水印也有两套（`mode="bit"` vs `mode="bytes"`，互相读不出来）
⇒ `DocWatermarkService` 改为委托 `WatermarkProcessor`。

另：新增 `POST /ops/leak-detect`，让泄露比对不再零引用。

### 5. 盲水印提取：把"假没查到"换成真提取（`35ceefd`）

**问题**：`POST /watermarks/extract` 返回 `confidence=0.0` +
`matched_users=[]`，而且**什么都没扫过**。

**修法**：后端把文件字节转发给 Worker 的 `/internal/watermark/extract`
（受 `WORKER_TOKEN` 保护，fail-closed），按水印文本
`{上传者ID}|{文档ID}|{时间戳}` 反查文档与上传者。
三态必须分清：提取到 → 有匹配用户；没提取到 → 有效结论；
**提取失败 → 503，绝不伪装成"没查到泄露"**。

### 6. 通知 / Webhook（`0a0d0ce`）

**问题 A（真 bug）**：重试消息路由键不匹配 → broker 静默丢弃 ⇒
**失败的通知直接消失**。同时退避延迟从来没生效（消费者忽略 `retry_at_ms`）。

**问题 B**：`POST /webhooks` 造假 secret 和假 ID 返回 201，**什么都不落库**；
回调地址缺 SSRF 防护；注销 / 读投递历史缺归属校验；
`PUT /notifications/preferences` **原样回显请求体**。

**修法**：路由键改对；新增**按退避档位的延迟队列**（每个档位一个固定 TTL
的队列，到期后由 broker 死信回重试队列 —— 不用"一个队列 + per-message TTL"
是因为那会**队头阻塞**）；回调注册真落库（secret 明文只返回一次，库里存哈希）；
回调地址拒绝内网 / 回环 / 元数据服务；一切读写带 owner 条件；
通知偏好真写库，通知列表 / 标记已读真查真改。

### 7. 国密链路（`0acf0e0`）

**问题**：`SmJwtTokenProvider` **完全不能用** —— jjwt 不认识 GS256、
claim 名对不上（且没有 permissions）、payload 手工拼 JSON 不转义。
而且零调用（标着 `@Deprecated`）。

**修法**：`edam.jwt.algorithm=GS256` 时 `JwtTokenProvider` 内部择一，
**所有调用方一行都不用改**；验签按 token header 里的 `alg` 派发
（切换期间新旧 token 并存，不会把在线用户踢下线）；
`JwtAuthenticationFilter` 收敛到 provider；补 `exp` 过期校验
（手工解析绕开了 jjwt 的过期检查，不查就等于**永不过期的 token**）。

## 四、遗留（明确没做的，附原因）

| 项 | 为什么没做 |
|---|---|
| 按密级切换存储层加密算法（SM4） | 存储层加密走的是统一的 AES-256-GCM，切算法要动密钥管理与已有密文，**不是能顺手改的**；且国密商用需商密许可 |
| 国密密码模块 | 商用合规要求密码机 / 软密码模块 + 商密许可，普通 SM3-HMAC 不满足 |
| 回调投递的触发入口 | 签名需要 secret **明文**，而 `webhook` 表只有 `secret_hash` —— 可签名的密钥存储方案需要单独设计（加密落库 or 密钥管理服务） |
| 通知的生产者 | "什么时候该通知用户"是产品决策，不是代码缺陷 |
| 按观看用户入库指纹（`video_fingerprint` 表） | 需要在播放链路上按用户抽帧并回传，是一条新链路 |
| 帧指纹比对 / Office 隐写提取 | 需要新的算法实现，不是接线 |
