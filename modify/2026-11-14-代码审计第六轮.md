## 1. 【high】JWT 签名密钥的默认值写在仓库里 —— 没有任何守卫

### 1.1 现象

JWT 是**无状态自证**的：服务端只验签，不查库。签名密钥一旦泄漏，攻击者可以**自己签出任意 token**：

```json
{"sub":"1","permissions":["*:*"],"exp":1893456000}
```

⇒ 这不是"绕过某个端点"，是**整个系统的鉴权被绕过**。

而这个仓库里，密钥的默认值是**明文写在配置里**的：

| 位置 | 值 | 何时会被真正用上 |
| --- | --- | --- |
| `backend/.../application.yml:120` | `${JWT_SECRET:dev-jwt-secret-must-be-at-least-256-bits-long-for-hmac-sha256}` | 忘了注入环境变量时**照样能启动** |
| `helm/edam/values.yaml`（base） | `change-me-in-production-must-be-256-bit` | 直接用 base chart 部署时 |
| `gitops/overlays/prod/values.yaml` | `REPLACE_FROM_VAULT` | 占位符没被替换时，**生产就用它当签名密钥** |

这些值**都在 git 里** ⇒ 任何能读到这个仓库的人都能伪造管理员 token。

项目里其实**已经有**这个模式的先例：`admin-password` 留空时**不创建任何默认账号**（fail-closed）。
但 JWT 密钥没有对应的守卫 —— 它默认**有一个公开值兜底**。

### 1.2 修法

新增 `JwtSecretGuard`（`@Component`，`@PostConstruct`）：

| 规则 | 行为 |
| --- | --- |
| 密钥为空 / 短于 32 字节 | **一律拒绝启动**（任何 profile） |
| 生产 profile + 命中已知占位符 | **拒绝启动**（fail-closed） |
| 非生产 profile + 命中已知占位符 | 响亮告警但不拒绝（本地开发与单测要用这些值） |
| 真实随机密钥 | 放行 |

已知占位符清单里包含 application.yml 的兜底值、helm base 的值、prod overlay 的
`REPLACE_FROM_VAULT`，以及常见写法（`changeme` / `secret` / `jwt-secret` …）。

> **日志里绝不打印密钥本身，也不打印它的哈希** —— 只打印"命中了哪个已知占位符"
> （那些值本来就在仓库里，不构成泄漏）。

### 1.3 这条的连带影响

生产部署前必须把 `REPLACE_FROM_VAULT` 换成真值，否则**后端启动即失败** ——
这是**故意的**：它把"忘了换密钥"从"悄悄跑在一个公开密钥上"变成"部署当场报错"。
⇒ 见 §13 运维待办。

## 2. 【high】PDF / Excel 的"水印"是明文 —— 而且指纹可以随便改

### 2.1 现象

盲水印 supposed 藏在频域里看不见，但**文档类根本不是这么实现的**：

```python
# worker/src/edam_worker/processors/watermark.py
# PDF：写进文档属性
writer.add_metadata({"/Title": f"Doc {text[:32]}",
                      "/Producer": f"EDAM Watermark 3.1.0 | {text}"})
# Excel：写进文档属性
wb.properties.creator = f"EDAM-{text[:100]}"
wb.properties.description = f"watermark: {text}"
```

指纹文本就是 `{uploader_id}|{doc_id}|{timestamp}`。于是：

1. **溯源信息主动泄露** —— 收件人打开"文件 → 属性"就能看到
   **是谁**、**哪份文档**、**什么时候**上传的。这对一份"防泄密"系统是反直觉的：
   它把溯源信息直接递给了每一个拿到文件的人。
2. **指纹可以被随手改写**（伪造）—— 而且第五轮加的一致性校验挡不住：
   指纹里的 uploader_id 与文档的上传者**一致**时，校验通过。
3. **指纹可以被直接删掉**（抹除）—— 改一下文档属性，溯源就没了。

补充：`_extract_pdf` 只读 `/Producer`，所以提取与嵌入是对称的 ——
**对称不等于安全**，它只说明这条明文信道是通的。

### 2.2 本轮补上的：**指纹登记比对**（第五轮 §3.3 的残留缺口）

第五轮留下了一个明确的缺口：

> 知道目标 `doc_id` 与 `uploader_id` 的人仍能伪造出一致的指纹 ——
> 因为系统里**没有"这份文档当初嵌的是哪串文本"的登记**。

本轮把这份登记建起来了：

```
Worker 嵌入水印
   └─ 拿到实际嵌入的文本 watermark_text
        └─ 随状态回调 PATCH /documents/{id}/status 回传 watermark_fingerprint
             └─ 后端落进 watermark_cache（这张表此前一直空着、没有任何写入方）
                  └─ 提取时拿提取到的文本与登记值比对
                       ├─ 一致   ⇒ 出结论
                       ├─ 不一致 ⇒ 判定为伪造，不给出匹配用户
                       └─ 无记录 ⇒ 历史文档，照常按老逻辑出结论
```

实现：

| 文件 | 作用 |
| --- | --- |
| `model/WatermarkCache.java`（新） | 表 `watermark_cache` 的实体 |
| `repository/WatermarkCacheRepository.java`（新） | MP 仓库 |
| `service/WatermarkRegistryService.java`（新） | 登记 / 比对 / 查询 |
| `controller/DocumentController.java` | 状态回调里登记指纹 |
| `controller/WatermarkController.java` | 提取时比对；`/watermarks/cache` 端点终于返回真实数据 |
| `worker/.../processors/document.py` | 把实际嵌入的文本回传后端 |

两点实现细节：

- **登记表的 TTL 不能用"缓存"语义**：建表时 `ttl_sec` 默认 86400（1 天），
  但这里存的是**取证证据** —— 泄露文件可能在几个月后才被发现，
  按 1 天保留会让溯源能力随时间**静默衰减** ⇒ 写入时显式给 10 年。
- **历史文档兼容**：上线前处理过的文档没有登记记录，比对结果为 `UNKNOWN`，
  **照常按老逻辑出结论**（第五轮的一致性校验仍然生效），只在日志里留一条"无登记"。
  不能因为上线了新功能就让历史文档查不出人。

### 2.3 残留缺口（不能假装没有）

登记比对解决的是**伪造**（改写指纹会被识破），**解决不了抹除**：

- 明文信道就在文件里，删掉属性里的那串字，文件就"干净"了 ——
  而登记比对此时只会说"提取不到指纹"（不是"被抹除"）。
- 真正要堵住，需要把指纹从明文信道挪走（例如 PDF 逐页渲染成图后走 DCT 盲水印，
  Office 走真正的自定义 XML 部件）。这是一个**跨 Worker 的重写**，
  不适合塞进一轮以"修 bug"为主的审计。

⇒ 已写进 `README.md` 的已知限制与 `doc/database_schema.md` §4.3。

## 3. 【high】水印嵌入失败 ⇒ 静默产出"无指纹原件"，状态却报 ready

### 3.1 现象

PDF / Word / Excel 三条嵌入路径都是同一个模式：

```python
except Exception as e:
    log.error("pdf_watermark_failed", error=str(e))
    import shutil
    shutil.copy(input_path, output_path)      # ← 复制原文件
```

于是：

1. 嵌入失败时**原文照常流转**，文件**完全没有指纹**；
2. 流水线接着照常上传、并把 `watermark_status` 报成 **2（ready）**
   ⇒ 系统认定"已加水印"；
3. 只有一行 `log.error`，**没有任何告警、没有任何指标**。

⇒ **溯源链无声断裂**。一份本该带指纹的机密文件以"已加水印"的状态流了出去，
而系统里显示一切正常。在一个用来**追责**的系统里，这是最不能接受的一类失败。

### 3.2 修法

失败一律抛 `PermanentWorkerError`：

- 不重试（重转 3 遍结果一样，只是白烧 CPU —— 这正是 `PermanentWorkerError` 的用途）；
- 文档处理失败、状态报 **3（failed）**、任务记 `failed_permanent`；
- **不产出任何文件**（连原件的拷贝都没有）⇒ 没有指纹的文档**不会被放行**。

失败关闭（fail-closed）在这里是正确取舍：宁可让用户看到"处理失败"，
也不能让一份"看起来处理好了、其实没指纹"的文档流出去。

> 图片路径不受影响：`embed_image` 只在 `blind_watermark` 没装时退到 LSB 隐写
> （LSB 极脆弱，裁掉顶部 1~2 行就能抹掉，但它至少**有**指纹）。

## 4. 【medium】盲水印密码硬编码为 1

### 4.1 现象

```python
bwm = WaterMark(password_wm=1, password_img=1)   # embed
bwm = WaterMark(password_wm=1, password_img=1)   # extract
```

三处（`embed_image` / `_extract_image` / `DocWatermarkService`）全是 1。

`password_wm` 决定 DCT 系数带的选取与打乱方式，它同时是**提取的门槛**。
写成 1 意味着：

- 任何拿到开源 `blind-watermark` 库的人都能**从泄露文件里提取出指纹**
  （直接知道是谁传的）；
- 也能**自己往文件里嵌入任意指纹**（伪造）；
- 还能**用错误指纹覆盖掉真指纹**（抹除）。

⇒ 这层"水印"只挡不懂行的人。

### 4.2 修法

密码改为**部署配置**：`EDAM_WATERMARK_PASSWORD`（整数 1..999，默认仍是 1）。

**默认保持 1 是刻意的**：本功能上线前嵌入的水印用的就是 1，
直接换密码会让那些文件从此提取不出来。
⇒ 提取时**先试配置的密码，再退回 1**，两者都取不到才算提取失败。

生产环境应当通过环境变量注入一个非默认值（见 §13）。

## 5. 【medium】管理员重置密码后，被自动锁定的账号依然登不进去

### 5.1 现象

第五轮给账号锁定加了时间窗（`locked_until`），但**重置密码这条路没跟上**：

```java
// PasswordService.resetPassword（改前）
user.setPasswordHash(newHash);
user.setPasswordChangedAt(...);
user.setMustChangePassword(true);
userRepository.updateById(user);      // ← 锁定状态一个字没动
```

用户连续输错 5 次被自动锁住 ⇒ 管理员给他重置了密码 ⇒ **他依然登不进去**
（`assertLoginAllowed` 照旧抛 `AccountLockedException`）。
管理员看到"重置成功"，用户还是进不去，只能再来找管理员。

### 5.2 修法

`resetPassword` 里顺带**解锁"被自动锁定"的账号**（`locked_until` 非空 = 有到期时间），
并把失败计数归零。

**管理员手动锁定的账号（`locked_until` 为空）不解** —— 那是管理员刻意为之
（疑似泄密调查中等），要放人请走 `PUT /users/{id}` 把状态改回 active。
**禁用的账号（status=2）也不动** —— 禁用不是锁定的副作用。

## 6. 【medium】改密 / 重置密码不吊销已签发的 refresh_token

### 6.1 现象

改密的典型动机是"**密码可能已经泄露了**"。而 `refresh_token` 的有效期是 **7 天**：

> 偷到 refresh_token 的人，在用户改完密码之后**照样能一直换出新的 access_token** ——
> 改密码这个动作对攻击者毫无影响。

管理员重置密码同理。而 `revokeAllForUser` 这个能力**早就有了**（`/users/{id}/revoke-keys`），
只是改密路径没调用它。

### 6.2 修法

- 自助改密（`AuthService.changePassword`）成功 ⇒ 吊销该用户全部 refresh_token；
- 管理员重置密码（`UserController.resetPassword`）⇒ 同样吊销。

代价：用户自己当前的会话也失效了（access_token 还能用到过期，之后必须重新登录）。
这是安全上正确的取舍，前端也同步改了提示（见 §10）。

## 7. 【medium】泄露告警链路会抛异常 —— 管理员收不到实时告警

### 7.1 现象

```java
String message = String.format(
    "... 疑似用户: %d ... 匹配置信度: %.1f%% ... 匹配帧数: %d/%d ...",
    detection.getDetectionId(),
    detection.getMatchedUserId(),      // ← 可空
    detection.getMatchScore() * 100,   // ← 可空
    detection.getMatchedFrames(),
    detection.getTotalFrames());
```

`leak_detection.matched_user_id` 这一列**是可空的**（"检测到泄露但匹配不到具体观看者"
是合法情形）。而 `String.format("%d", null)` 会抛 `IllegalFormatConversionException`。

后果：`handleDetectionResult` 在这里断掉 ⇒

- `notificationController.broadcastLeakAlert(detection)` **不会执行**
  ⇒ 管理员**收不到实时告警**；
- 异常继续上抛给调用方。

### 7.2 修法

改用可空安全的格式化（空值显示"未知"），不再让告警链路被格式化异常打断。

## 8. 【low】登出不清 `refresh:user:<id>` 索引成员

`logout()` 只删了 `refresh:<token>` 这一个键，`refresh:user:<id>` 集合里的成员**留着不走**：

- 集合只增不减 ⇒ Redis 内存缓慢泄漏；
- 紧急吊销时要把这一堆早已失效的 token 挨个删一遍。

修法：登出时先查出这张卡属于谁，再把它从索引集合里摘掉。

## 9. 【low】`SsrfGuard` 漏掉 `100.64.0.0/10`

私网表里没有 CGNAT 段（`100.64.0.0/10`，Tailscale 与部分云厂商的内网地址用它）。
用它当 Webhook 回调地址可以打到企业自己的组网内部。已补进 `isPrivateIpv4`。

> SSRF 守卫的整体评价：**相当扎实** —— 协议白名单、IPv4/IPv6 双查、
> 域名解析后再查一遍、投递前**再查一次**（压 DNS 重绑定窗口）、
> HTTP 客户端显式 `followRedirects(NEVER)`（挡跳转绕过）。
> 唯一明说的残留缺口是 DNS 重绑定本身（代码注释里写清楚了，没有假装没有）。

## 10. 【low】前端仍在发 `X-User-Id` —— 一个"看起来能用"的可伪造身份头

后端早就改成从 **JWT principal** 取当前用户（`@CurrentUserId` →
`CurrentUserArgumentResolver`），这个头**后端一个地方都不读**。
但前端 `api/client.ts` 与 `views/Documents.vue` 一直在发它。

留着它的坏处不是"多发了一个没用的头"，而是**它是个陷阱**：
任何时候有人照着旧代码写一个 `@RequestHeader("X-User-Id") Long userId`，
客户端就能随便改这个头冒充任意用户 —— 那就是现成的越权。
⇒ 前端不再发这个头，并在代码里写明为什么不能加回来。

顺带把改密后的前端提示改成"密码已修改成功，请用新密码重新登录"
（配合 §6 的会话吊销：不说清楚的话，用户会在 access_token 过期后被莫名其妙踢回登录页）。

## 11. 【low·未修】泄露告警其实只写日志、从不外发

`LeakDetectionAlertService.sendSecurityAlert` 的实现是：

```java
// 实际生产：通过 HTTP POST 发送
log.info("security_alert_sent message={}", message.replace("\n", " | "));
```

配置项 `edam.alert.webhook.security` 就算配了，也**只会被打进日志**。
法务 / HR 通知（`notifyLegalAndHR`）同理。

⇒ **P1 级别的泄露告警不会到达安全团队**，除非有人天天盯日志。

**本轮未修**：真正的外发需要知道告警通道（钉钉 / 企微 / 邮件）与鉴权方式，
这属于**产品与运维决策**，不是代码缺陷 —— 擅自发到某个地址可能造成更严重的问题。
⇒ 记在这里作为待办。

## 14. 运维侧待办

| 项 | 说明 |
| --- | --- |
| **JWT 密钥守卫会让占位符部署直接启动失败** | 这是**故意的**（§1）。生产必须先注入真实密钥再部署 —— `gitops/overlays/prod/values.yaml` 里的 `REPLACE_FROM_VAULT` 必须被 External Secrets 覆盖，否则后端起不来。**部署顺序要注意** |
| **注入 `EDAM_WATERMARK_PASSWORD`** | 建议在 staging / prod 注入一个非 1 的值（1..999）。⚠️ 换密码后，**换密码之前嵌入的水印仍可提取**（提取端会自动退回 1 尝试）；但**换密码之后**嵌入的水印，旧密码就解不开了 —— 两个值只能二选一，**不要在已有文档的生产环境里随手换** |
| **历史文档没有指纹登记** | 登记比对对上线前处理过的文档返回 `UNKNOWN` ⇒ 走老逻辑（一致性校验仍然生效）。要让历史文档也纳入登记，需要一次性回填脚本（用 MinIO 上现有的水印产物重新提取） |
| **泄露告警通道未定** | §11 —— 需要产品/运维决定告警发到哪里 |
| **新增的 `watermark_cache` 写入方** | 该表此前无写入方，现在是**取证证据表** ⇒ 备份策略要覆盖它，且**不要**按"缓存"配置 TTL 清理 |
