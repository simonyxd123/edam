# 代码审计与整改（v3.4.2）

> 日期：2026-11-08
> 范围：v3.4.1 发版后回头审一遍**已上线代码**
> 方案书章节：5.4 细粒度权限与外发管控 / 5.6 密级与可见性 / 13.1 会话与密钥生命周期

## 1. 为什么又审一遍

v3.4.1 修的是「**写好但没接线**」的八项功能。这次回头审的是**已经在线上跑着的代码**，
找的是另一类问题 —— 特征都更隐蔽：

- **接口返回成功、界面弹「成功」，但底层什么都没发生**
- **前端按权限过滤了菜单，后端却没设门** —— 绕过菜单直接调 API 就行

这两类问题的共同点：**编译不报错、测试不报警、页面看起来正常**。

## 2. 审计方法

1. **端点全量清点**：扫全部 `@RestController`，列出每个端点的
   `(METHOD, path, @PreAuthorize, 类级 @PreAuthorize)`，与权限目录对账。
2. **权限码 ↔ 端点对账**：46 条权限码里，哪些真的有端点读它
   （结果：25 条生效、21 条不生效）。
3. **前后端契约对账**：逐个 Controller 的 `@RequestBody` DTO，
   检查多词字段有没有标 `@JsonProperty`（本仓库没有全局命名策略）。
4. **"承诺 vs 实现"对账**：管理员手册里写的每一条能力，回代码里找实现。
5. **审计切面 / 迁移 / 索引 / Worker / 前端** 逐项过。

> 并行派了 4 个子代理分头审（认证与令牌 / 密级与 ACL / Worker / Webhook 与审计切面），
> 全部被上游 429 打断，没拿到结果 —— 本文只写**我自己核过并改掉的**，
> 没核过的部分没有写进来。

## 3. 改了什么

### 3.1 四个端点漏了 `@PreAuthorize`

| 端点 | 漏掉的后果 | 补的门 |
|---|---|---|
| `GET /audit/logs`、`/operation-types`、`/resource-types`、`/{log_id}` | **全公司操作审计日志** —— 谁在哪个 IP、用什么 UA、预览了哪个 L4 文档、外发给了哪个外部邮箱 | `audit:read` |
| `GET /users`、`GET /users/{id}` | 全公司员工名册（工号 / 姓名 / 邮箱 / 部门 / MFA 开关 / 登录失败次数 / 最后登录时间与 IP） | `user:read` |
| `GET /admin/backups` | 备份清单（今天返回空列表 —— 这是个**等着被填上的洞**，谁来实现备份列表谁就会不小心暴露给全体员工） | `admin:backup` |
| `GET /rbac/users/{id}/permissions` | 任意用户的有效权限清单 | `user:read or role:read` |

**为什么这四个必须补，而读接口不用一个个补**：
这两层权限是**分工**的，不是叠加的 ——

- **RBAC（角色层）** 管"写"和**非资产数据**；
- **ACL（资源层）** 管"读资产"（密级 + 显式授权）。

`GET /videos` / `GET /documents` 之所以不用角色门，是因为它们的可见性由
`applyVisibility` 按密级 + ACL 判定 —— 那是设计。而**审计日志 / 员工名册 /
备份清单 / 权限清单不是资产**，没有任何 ACL 覆盖它们，只能靠角色门。

**这四个权限码本来就在权限目录里**，`dept_manager` / `auditor` 也早就授权了 ——
端点只是忘了写注解。补门不影响既有角色，只是把"本来该有"的门关上。

> 前端 `MainLayout.vue` 早就按 `audit:read` 过滤「审计日志」菜单了 ——
> 缺的只是后端这一半。补上后前后端口径一致。

**回归测试**：新增 `EndpointAuthorizationTest`（3 个用例）

- 每个端点要么有 `@PreAuthorize`（方法级或类级），要么在**例外清单**里
  写明"这里靠什么鉴权"（token scope / ACL / 匿名 / 探针 / Worker 回调 …）
- 关键端点的门不能被悄悄改弱（`audit:read` / `user:read` / `admin:backup` …）
- 例外清单里不许有僵尸条目（端点删了或加上门了，清单也要跟着改）

以后再加端点忘了设门 ⇒ **测试红**。

### 3.2 「紧急吊销」是空实现

`POST /users/{id}/revoke-keys` 原先只打了一条日志就返回 204 ——
**token 一个都没作废**。管理员点「紧急吊销」，弹成功提示，然后什么都没发生。

- `sys_session.revoked` 字段、`SysSessionRepository.revokeAllByUserId` 全是死代码
- 前端**根本没有**这个按钮（只有手册里有）

**修法**：

1. Redis 维护「用户 → 其 refresh_token 集合」索引
   （原先只有 `refresh:<token>` → userId，**没法按用户反查** ——
   只有 `KEYS refresh:*` 全库扫描这种下策，那在生产上会阻塞 Redis）
2. 吊销 = 取出索引里的 token 逐个作废 + `sys_session.revoked = 1` 留痕
   + 写 audit
3. 前端补上「紧急吊销」按钮

**口径必须写准**（手册已按此改）：

| 凭证 | 吊销后 |
|---|---|
| refresh_token | **立即作废** ⇒ 续期通道当场断掉 |
| 已签发的 access_token | 无状态 JWT、服务端无黑名单 ⇒ 最多再活一个 TTL（默认 **10 分钟**） |

早先手册写的"立即失效"是过度承诺。JWT 无状态就是这个代价，不是实现偷懒。

### 3.3 refresh 不查账号状态、refresh_token 不轮换

- **不查状态**：管理员把离职员工禁用（status=2）之后，他手上的 refresh_token
  照样能换出新的 access_token ——「禁用」只是个页面上的标记，管不住人。
  现在 `/auth/refresh` 也走 `assertLoginAllowed`（与密码登录 / WebAuthn 同一套判定）。
- **不轮换**：一张泄露的 refresh_token 能在整个 7 天 TTL 里无限续期，
  **没有失效点、没有重放检测**。现在**每次刷新轮换**：旧的当场作废，
  响应里回一张新的。前端 `client.ts` 已经兼容（响应里有 `refresh_token` 就写回 localStorage）。

### 3.4 外发审批模块

| 问题 | 现象 | 修法 |
|---|---|---|
| 请求 DTO 缺 `@JsonProperty` | 前端发 `doc_id` / `external_recipient` / `valid_hours` **全绑不上** ⇒ 「发起外发审批」在界面上**从来就没成功过**（恒 400），而且不报错、不进日志 | 逐个标注 snake_case |
| 入参不校验 | 缺 `external_recipient` ⇒ NPE → **500**；缺 `reason` / `valid_hours` ⇒ 撞库里的 NOT NULL → **500** | 入口统一校验，非法一律 **400** |
| 审批意见不保存 | `comment` 收了却从不写；`distribution_approval_decision` 表**零引用** ⇒ 谁批的、什么时候、批语是什么**全都查不到** | 写决策流水表；新增 `GET /distribution/approvals/{id}/decisions` |
| 没有状态机 | 已驳回的申请能被再"批准"一次；已撤销的能被再撤销 | 只允许 `pending` 决策 / `pending`·`approved` 撤销，否则 **409** |
| 可以自审自批 | 有 `distribution:approve` 的人能审批**自己**提交的申请 ⇒ 审批环节形同虚设 | 申请人 ≠ 审批人，否则 **403** |
| 驳回可以不写理由 | 事后追责只剩"被拒了"三个字 | 驳回时 `comment` 为空 ⇒ **400** |

外发审批是"把资产送到公司外面"这道闸，闸门每次开合必须留痕 ——
决策流水表此前是空的，等于没有证据链。

### 3.5 工具 bug：`sync_openapi_permissions.py`

`--write` 此前会：

1. 给**已有** `x-required-permission` 行的 operation **再插一行** ⇒ 同一个 operation
   出现两个同名 YAML key（解析器只认最后一个，规范文件不可审阅）
2. 只认**方法级** `@PreAuthorize` ⇒ 类级门（`ClassificationController`）被整段漏掉
3. 多权限表达式（`hasAuthority('a') or hasAuthority('b')`）只取**第一个** ⇒
   规范里的契约被悄悄削弱

现在三处都修了：就地改写不重复插入、认类级门、取完整表达式。

## 5. 明确没做的事

| 项 | 为什么 |
|---|---|
| **access_token 即时吊销**（服务端黑名单） | 要在每个请求上多打一次 Redis，且要定"Redis 挂了 fail-open 还是 fail-closed"。当前口径（≤10 分钟）在这个系统里可接受 —— 会话超时本来就是 10 分钟。要做的话建议单独一版 |
| **真正的外发链接端点** | 产品决策（自建外发门户？走现有 OA？）。手工册已按代码写清边界，不再假装有 |
| **让 22 条未生效的权限码生效** | 逐个补 `@PreAuthorize` 会改变现有角色的实际行为（例如给 `GET /tags` 补 `tag:read` 会把 auditor 挡在门外 —— auditor 没有这一条）。这是权限数据决策，不该在一次 bugfix 里顺手改（现为 21 条） |
| **补 `sys_session` 的写入方** | 现在只有吊销侧读它。会话落库需要 IP / UA / 设备指纹等字段的接线，属于独立一版的事。吊销路径已经接上，将来会话落库就自动生效 |
| **Worker / Webhook / 国密链路的深度审计** | 并行的 4 个子代理被上游 429 打断，这几块**这轮没有深审**。v3.4.1 已经动过它们，风险相对低，但**不能算审过了** |

## 7. 上线前必做

1. **通知普通员工重新登录** —— JWT 里的权限码是登录时的快照。
   尤其现在审计日志 / 用户名册有了门，旧 token 里虽然也没有 `audit:read`，
   但为了让新加的端点门生效，统一重登一次最省事。
2. **`/auth/refresh` 的响应多了一个 `refresh_token` 字段** ——
   前端已兼容（`web/src/api/client.ts`），但**如果有第三方客户端**在调这个接口，
   它们必须把新字段写回存储，否则第二次续期就会失败（旧 token 已作废）。
   这是本次唯一的**破坏性变更**，务必确认。
3. 无新迁移（`distribution_approval_decision` 表在 v3.2 就建好了，
   本次只是把它接上写入方）。
