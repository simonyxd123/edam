## 一、同步方式

采用 **最小侵入式追加 + 头部版本号更新** 策略：

| 操作 | 位置 | 风险等级 |
|------|------|----------|
| 修改头部版本号 | 段 1（"版本：v3.0（终稿）"） | 极低（字符串替换） |
| 更新修订说明文本 | 段 2 | 极低 |
| 追加附录 C | 文档末尾（原 附录 B 之后） | 低（python-docx 自动应用样式） |

**为什么不用直接编辑 XML**：document.xml 含 736 段落、复杂表格、嵌入字体表、媒体引用、跨章节锚点；直接编辑字符串替换风险高、可能破坏 Word 渲染。

**为什么不用 python-docx 全量重生成**：会丢失原 docx 的 Title/Heading 1/Heading 2/List Bullet 样式继承 + 表格样式 + 页眉页脚。

**采用方案的好处**：保留全部原样式（Title/Heading 1/Heading 2/Heading 3/List Bullet）+ 表格 10 张 + 媒体 4 张 + 字体表 + 页眉页脚不变；新增内容应用 docx 内置样式。

## 四、为何不修改正文，只追加附录 C

方案书正文（章 1-17 + 附录 A/B）已包含 v2.0 评审的全部 16 项修复（含 5.1.7 移动端、5.3.5 法律衔接、6.3.2 缓存、9.4 Vault、4.1.2 SHA256、6.4 消息队列分级等）。v3.1 增量修复主要在「细化文档」（OpenAPI / ER / drawio）层面，**未涉及主方案书正文方案的实质变更**。

因此，**追加附录 C 是最合适的同步方式**：

1. **避免误改正文**：正文已正确，无需动
2. **保留完整审计链**：评审 → 修复 → 同步记录清晰可追溯
3. **样式一致**：附录 C 使用原 docx 内置 Heading 1/2/3、List Bullet 样式，与原文档视觉统一
4. **可机器解析**：附录 C 用结构化文本（章节号 + 项目符号），后续可提取为变更日志
