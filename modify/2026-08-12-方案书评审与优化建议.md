## 二、问题清单（按严重性分级）

> 标记说明：**P0** = 必须修复（影响方案能否成立）；**P1** = 强烈建议修复（影响实施质量）；**P2** = 建议优化（影响可读性与长期可维护性）。

### 2.1 P0 级 — 安全方案存在可绕过风险

#### P0-1 HLS + AES-128 ≠ DRM，被当作"防文件窃取"防线

- **现状**（4.2 节）：使用 `hls_key_url` 指向后端密钥接口，前端通过 GET 请求获取密钥解密 .ts。
- **风险**：
  - 任何用户可在浏览器开发者工具 → Network 直接抓取 .ts 分片，下载到本地用 `openssl` 即可解密拼接为原始 MP4。
  - AES-128 密钥从密钥接口明文返回给前端，密钥一旦被脚本拦截即等同于明文分发。
- **修订建议**：
  - 明确定位：HLS+AES-128 是 **"传输加密 + 轻度防下载"**，不是 DRM，不要在文档中宣称"防文件窃取"。
  - 如需 DRM 能力，应引入 Widevine（Chrome/Android）、FairPlay（Safari/iOS）、PlayReady（Edge）。即使是开源方案，也可考虑 `shaka-packager` + Widevine 集成。
  - 即使保留 AES-128，密钥接口必须改为 **短时签名 URL + 证书绑定 + 一次性密钥**，并在响应头禁止缓存。

#### P0-2 DWT 频域盲水印在视频上鲁棒性不足

- **现状**（4.4 节、5.3 节）：用 DWT 在视频帧频域嵌入水印，称"抗裁剪、抗录屏"。
- **风险**：
  - 视频一旦被 H.264/H.265 重编码（这是录屏/转发的天然步骤），DWT 系数会被压缩破坏，水印基本失效。
  - `blind-watermark` 库本身仅支持**图片频域水印**，视频水印是按帧嵌入，帧间不同步，重编码后帧错位导致提取失败。
- **修订建议**：
  - 明确区分："视频盲水印" vs "图片盲水印" vs "PDF 盲水印"，每种算法独立描述。
  - 视频盲水印必须 **帧间冗余嵌入 + 抗压缩编码**，或者转向 **视频指纹（video fingerprinting）/ 感知哈希（pHash）** 做泄露追踪，而非依赖不可靠的频域水印。
  - 5.3 节"复用 Python + OpenCV 频域盲水印算法"应注明 OpenCV 不做频域水印，实际依赖 `blind-watermark`（DCT）或自研 DWT 算法。

#### P0-3 驱动层透明加密一句话带过，工作量被严重低估

- **现状**（5.1 节）："在员工办公终端部署轻量级底层驱动……保存瞬间自动 AES-256/SM4 加密"。
- **风险**：
  - 文件系统透明加密驱动在 Windows 上是 **内核 minifilter 驱动**，开发 + 测试 + 兼容性 + 驱动签名通常 **6-12 人月**起步。
  - 跨平台（Windows / macOS / Linux）需独立实现，macOS 用 Endpoint Security 框架，Linux 用 FUSE，均涉及内核接口。
  - 驱动签名（WHQL / Apple Notarization）流程长；驱动 bug 会蓝屏/丢数据，影响范围极大。
- **修订建议**：
  - 5.1 节必须扩充为独立小节，描述：
    - 驱动类型与平台覆盖（Windows minifilter / macOS ESF / Linux FUSE）
    - 密钥分发与回收（KMIP？自建 KMS？）
    - 离线容忍（员工出差离线办公如何处理？）
    - 驱动签名与升级方案
    - 失败回退（驱动崩溃后系统保护模式）
  - **评估采购第三方方案**：如天喻、深信服、IP-guard 的透明加密模块，可显著降低自研风险。

#### P0-4 终端"防开发者工具"是装饰性安全

- **现状**（4.3 节、第八章）：禁用右键、禁用 F12、MutationObserver 防删除。
- **风险**：
  - 现代浏览器提供大量绕过方式：手机浏览器、无障碍工具、HAR 抓包、外部录屏、硬件采集卡、内存 dump。
  - MutationObserver 只能防止 DOM 删除，无法防止 CSS `display:none` / `visibility:hidden` 隐藏水印。
- **修订建议**：
  - 删除"防 DevTools"作为安全防线的描述，归类为"防误操作"。
  - 将其作为 P2 体验优化保留，并标注"仅降低初级用户截屏风险，无法防御定向攻击"。

#### P0-5 Token 中携带 PII 与 Token 设计混淆

- **现状**（4.1、4.3 节）：Token 包含"视频ID + 过期时间 + 随机盐值"，前端播放器从 Token 中解析用户工号/姓名。
- **风险**：
  - MD5 + 简单拼接的 Token 易被构造重放。
  - 用户 PII（工号/姓名）不应放在客户端可解析的 Token 中，应由后端接口按需下发。
  - secure_link 的 secret_key 写在 Nginx 配置中，配置泄露 = 全盘崩溃，没有密钥轮转机制说明。
- **修订建议**：
  - Token 设计改用 **签名 JWT** 或服务端不透明 Token；PII 不放进 Token，由 `/api/user/me` 在播放时单独下发并加防重放 nonce。
  - 增加 **secret_key 密钥轮转** 方案（双密钥灰度、定期轮换、HSM 存储）。

#### P0-6 合规风险完全未覆盖

- **缺失内容**：
  - 《个人信息保护法》：员工姓名、工号、操作日志属于个人信息，监控/水印需要告知。
  - 《劳动法》《劳动合同法》：单方监控需员工同意，部分场景需职代会/工会。
  - **网络安全等级保护**：涉密系统通常需等保三级，方案中未提测评与备案。
  - **国密合规**：仅提 SM4，应配套 SM2（密钥交换/签名）+ SM3（哈希）形成完整套件，并明确"商用密码使用许可"。
  - **数据出境**：MinIO 多地域、CDN 海外节点、跨国员工访问可能触发数据出境。
- **修订建议**：新增 **"第十三章 合规与法务"**，覆盖：
  - 个人信息处理告知与授权流程
  - 等保测评级别与备案节奏
  - 国密合规路径
  - 跨境数据流评估
  - 员工告知模板（附件）

### 2.2 P1 级 — 实施可行性与性能问题

#### P1-1 工期严重低估

| 阶段 | 方案工期 | 建议工期 | 说明 |
| --- | --- | --- | --- |
| POC 验证 | 2-3 周 | **4-6 周** | 视频频域盲水印鲁棒性实验需要大量样本，驱动 POC 至少 4 周。 |
| 核心开发 | 4-6 周 | **10-12 周** | 后端 + 权限中心 + 流媒体网关 + 文档网关 + 异步流水线，远不止 4-6 周。 |
| 驱动集成 | 3-4 周 | **12-16 周** | 内核驱动 + 跨平台 + 签名 + 灰度，按"人月"计量。 |
| 测试上线 | 2-3 周 | **4-6 周** | 全链路压测 + 渗透测试 + 灰度 + 培训。 |
| **总计** | **11-16 周** | **30-40 周（7-10 个月）** | 与"两个月交付"的承诺完全不符。 |

#### P1-2 "高风险视频/高密级文档"定义缺失

- **现状**（6.3 节）：盲水印按需触发，但"高风险/高密级"未定义。
- **修订建议**：增加密级分类模型（如 L1-L4）与触发规则矩阵，每个资源打标时强制选择密级。

#### P1-3 CDN 与 HLS AES-128 的兼容性问题未说明

- **现状**（10.2 节）：风险应对中提"CDN 分发"，但密钥接口会绕过 CDN 回源。
- **风险**：
  - 公共 CDN 缓存 .ts 分片可降低源站压力，但密钥接口必须回源到业务后端校验 Session。
  - 一旦 CDN 节点被入侵/越权访问，.ts 分片可被批量下载。
- **修订建议**：
  - 增加 **私有 CDN + 防盗链（Referer / UA / Token 校验）** 方案。
  - 密钥接口通过边缘函数（Cloudflare Worker / 自建边缘）下沉，减少回源。

#### P1-4 缓存策略缺失

- **现状**（6.3 节）：盲水印缓存用 Redis，但 TTL、淘汰策略、容量上限未定义。
- **风险**：高热度员工 × 高频视频 → 缓存膨胀 / 缓存击穿。
- **修订建议**：明确 LRU + TTL + 容量上限，并提供缓存预热与冷启动策略。

#### P1-5 数据库与日志治理

- **现状**（7.2 节）：仅说"百万级毫秒响应"。
- **缺失**：
  - play_log 海量增长（按观看次数记），未提分库分表、冷热分层、归档。
  - ER 图与外键关系缺失。
  - 没有数据生命周期（保留 90 天？永久？）策略。
- **修订建议**：新增 **"数据治理"** 子章节。

#### P1-6 可观测性盲点

- **现状**（第九章）：仅 3 个监控指标。
- **缺失**：
  - **链路追踪**：用户上传→MQ→Worker→MinIO 全链路 SkyWalking / Jaeger。
  - **日志聚合**：ELK / Loki。
  - **告警分级**：P0/P1/P2 告警通道（钉钉/企微/电话）与响应 SLA。
  - **SLO 定义**：可用性 99.9%、鉴权失败率 < 0.1%、转码成功率 > 99.5%。
- **修订建议**：第九章扩充为完整 **"SRE 与可观测性"** 章节。

## 三、优化建议（按章节给出具体修改）

### 第三章 核心技术栈 — 增补项

| 类别 | 现状 | 建议补充 |

### 第四章 视频防泄密 — 重构建议

1. **4.1 节拆分为 4.1.1 鉴权、4.1.2 Token 设计、4.1.3 Nginx 配置**，并加入密钥轮转章节。
2. **4.2 节明确分级**："传输加密（必备）/ DRM（按需）/ 离线导出管控（待评估）"。
3. **4.4 节改名为"视频帧指纹"或"视频频域水印（含局限性说明）"**，不要宣称"抗录屏"。

### 第五章 文档防泄密 — 重构建议

1. **5.1 节拆分为独立子章节**，描述驱动类型、平台覆盖、签名、离线容忍、回退方案。
2. **5.3 节按文件类型细分**：图片水印 / PDF 水印 / Word 隐写 / Excel 隐写，分别说明算法。
3. **5.5 节补充移动端管控**：iOS / Android 邮件附件、AirDrop、IM 文件转发如何处理。

### 第六章 异步处理流水线 — 增补项

- 增加 **失败重试与死信队列** 策略。
- 增加 **任务幂等性** 设计（同一上传多次触发不能重复处理）。
- 增加 **优先级动态调整** 机制（VIP 用户任务插队）。

### 第八章 安全策略总览 — 重构建议

- 用一张矩阵图替代文字罗列，明确"层级 × 资产类型 × 控制点 × 失效后果"。
- 增加 **零信任原则** 说明：默认不信任任何请求，每次鉴权。

### 第十一章 实施计划 — 关键修订

- 工期改为 **7-10 个月**，分 6 个阶段（POC → 视频模块 → 文档模块 → 驱动 → 集成测试 → 上线）。
- 增加 **外部依赖风险**：Python 库版本兼容性、OpenCV 编译依赖、SM4 国密库采购。
